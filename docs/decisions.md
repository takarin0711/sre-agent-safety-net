# 設計判断ログ

採用した案と、検討して採らなかった案を、理由とともに記録する。追記のみ。
「なぜこの構成なのか」を後から説明できることが、この PoC の主要な成果物である。

書式: `## D-nnn タイトル` / 状態 / 文脈 / 決定 / 理由 / 採らなかった案 / 影響。

---

## D-001 エージェントフレームワークを導入しない

**状態**: 採用（2026-09-04）

**文脈**: エージェント本体を LangGraph 等のフレームワークで組むか、素の Python + OpenAI SDK で書くか。

**決定**: 素の Python + OpenAI SDK。LiteLLM Proxy に OpenAI 互換エンドポイントとして接続する。

**理由**: 本 PoC の検証対象は「各層が異常を検知・遮断すること」であって、エージェントの賢さではない。
フレームワークを挟むと、観測された挙動がフレームワークのリトライ・例外処理によるものなのか、
検証したい層によるものなのか切り分けられなくなる。層の責務を曖昧にする要素は排除する。

**採らなかった案**: LangGraph（Phase 5 の中断・再開を状態機械として表現しやすい利点はあるが、
上記の切り分け問題が上回る）。Claude Agent SDK（LiteLLM Proxy 経由のマルチデプロイ構成との相性が未確認）。

**影響**: Phase 5 の中断・再開は自前で状態を持つ必要がある。Phase 5 の設計時に再検討の余地あり。

## D-002 ポリシー判定を Pydantic ではなく OPA に置く

**状態**: 採用（2026-09-04）

**文脈**: 「本番環境での `kubectl delete pvc` を禁止する」判定は、Pydantic のカスタムバリデータでも書ける。

**決定**: 構造検証（第2層 / Pydantic）と権限判定（第3層 / OPA）を分離する。

**理由**: 「構造が正しい」と「内容が安全」は別の関心事。バリデータにポリシーを書くと、
ポリシーがアプリケーションコードに埋没し、監査もレビューも単体テストも困難になる。
Rego として外部化すれば `opa test` で単体テスト可能になり、ポリシーの変更がアプリのデプロイと切り離せる。

**採らなかった案**: Pydantic バリデータ内での判定（実装は最短だが、上記の監査性を失う）。

**影響**: OPA サーバというコンポーネントが1つ増える。エージェント → OPA は HTTP 呼び出しになるため、
OPA 自体の可用性が新たな単一障害点になる。この扱いは Phase 3 の設計で決める。

## D-003 フェイルオーバーを同一モデルのマルチ地理圏で構成する

**状態**: 採用（2026-09-04）

**文脈**: 第1層のフェイルオーバー先として、別プロバイダ / 同一プロバイダの別モデル / 同一モデルの別リージョンが候補。

**決定**: Amazon Bedrock 上の同一モデルを、複数の地理圏にまたがって配置する。

> **2026-09-04 修正**: 当初は「複数リージョン」としていたが、Bedrock の Claude は Claude 3 Haiku を除き
> 推論プロファイル経由でしか呼べず、単一リージョンを名指しする構成が取れないことが判明した（[D-008](#d-008-モデルは-claude-sonnet-4-6-を-jp--us-プロファイルで使う)）。
> 障害単位を**リージョンから地理圏へ**修正する。同一モデルであるという本項の主旨は変わらない。

**理由**: フェイルオーバー先でモデルが変わると、「応答品質が変わった」という交絡が入り、
可用性だけを純粋に検証できなくなる。同一モデルなら出力特性が保たれるため、
第2層以降の検証結果にフェイルオーバーの影響が混入しない。
また、リージョン障害は SRE として現実的かつ説明しやすい障害単位である。

**採らなかった案**:
- 別プロバイダ間（プロバイダ全断まで守れるが、モデルが変わるため上記の交絡が入る）
- 同一プロバイダの別モデル（キー1本で済むが同上）
- クラウド → ローカル（Ollama）（セットアップが重く、PoC の焦点がぼやける）

**影響**: プロバイダ全断のシナリオは本 PoC では検証しない。実運用化時に別プロバイダを
第3の fallback として積む余地は残す（LiteLLM の fallbacks はリスト指定なので拡張可能）。

なお調査の副産物として、Bedrock 上に OpenAI（`us.openai.gpt-5.6-*`）と xAI（`us.xai.grok-4.6`）の
モデルが提供されていることが判明した。**別ベンダーへのフォールバックが Bedrock 内で完結する**ため、
別クラウドのアカウントもキーも用意せずに config へ 1 エントリ追加するだけで実現できる。
Phase 1 のスコープは広げないが、Phase 5 の拡張余地として記録しておく。

## D-004 地理圏間のフェイルオーバーは AWS に任せず、LiteLLM 層で明示的に制御する

**状態**: 採用（2026-09-04） / 一部要調査

**文脈**: Bedrock 自体にもリージョンをまたいで推論をルーティングする仕組み（クロスリージョン推論プロファイル）があり、
これを使えば LiteLLM 側でフェイルオーバーを組まなくても、AWS 側でリージョンを跨いだ処理が期待できる。

**決定**: LiteLLM 層で明示的に primary / fallback を定義する。

**理由**:
1. **観測可能性**。AWS 側で自動ルーティングされると、いつどちらのリージョンが応答したかを
   アプリケーション側から確定的に観測しづらい。PoC は「フェイルオーバーしたことを証明する」のが目的であり、
   証明できない仕組みは検証にならない。
2. **プロバイダ非依存**。将来 Bedrock 以外を fallback に積む際、同じ仕組みで扱える。
3. **思想の一貫性**。第2層・第3層と同じく「エージェントの外側の、我々が制御できる層で守る」形になる。

**採らなかった案**: クロスリージョン推論プロファイルに委譲（運用は楽だが上記1が致命的）。

**調査結果（2026-09-04）**: 推論プロファイルは「使うかどうか選べるもの」ではなく、
Claude 3 Haiku を除く全 Claude モデルで**必須**だった。したがって本項の決定は
「プロファイルに委譲するか否か」ではなく「**プロファイルの地理圏をまたぐ部分を誰が制御するか**」の話になる。

決定自体は維持する。地理圏**内**のルーティングは AWS に委ね、地理圏**間**のフェイルオーバーを
LiteLLM が明示的に制御する。ただし理由の重心は変わった。AWS が `global.` プロファイルという形で
既に広範なフェイルオーバーを提供している以上、**第1層が可用性に対して追加する価値は限定的**であり、
第1層の本当の価値は観測可能性・ベンダー非依存性・第2層以降との一貫性にある。
この論点は Phase 1 の考察として result.md に記録する。

## D-005 障害注入はエラー応答のモックで行う

**状態**: 採用（2026-09-04）

**文脈**: 第1層の異常系をどう再現するか。API キー無効化 / 到達不能ホスト / ネットワーク遅延注入 / エラー応答のモックが候補。

**決定**: primary 側を、任意のステータスコードを返すモックエンドポイントに差し替えて障害を注入する。

**理由**: 429 / 500 / タイムアウトをエラー種別ごとに撃ち分けられ、再現性が高い。
LiteLLM のリトライ・フォールバック・クールダウンはエラー種別によって挙動が変わるため、
種別を制御できることが検証の前提になる。

**採らなかった案**:
- API キー無効化（手軽だが 401 認証エラーのみで、レートリミットやサーバ障害を再現できない）
- toxiproxy（最も実態に近いが、コンポーネントが増え PoC が重くなる。必要になった時点で追加）

**影響**: モックサーバというコンポーネントが1つ増える。配置場所は Phase 1 の設計を参照。

## D-006 障害注入サーバをルート直下の `mocks/` に置く

**状態**: 採用（2026-09-04）

**文脈**: D-005 で採用したエラー応答モックの実体をどこに置くか。当初合意したディレクトリ構成には該当する置き場がなかった。

**決定**: ルート直下に `mocks/` を追加し、`mocks/fault_injector.py` を置く。標準ライブラリのみで実装する。

**理由**: 障害注入は Phase 1 に限らず Phase 5 の E2E でも使う横断的な検証部品であり、
特定の層のディレクトリ（`litellm/` や `agents/`）に置くと所属が誤解される。
外部依存を持たせないのは、検証部品自体が壊れて検証がブロックされる事態を避けるため。

**採らなかった案**: `litellm/` 配下に同梱（LiteLLM の設定と検証部品が混ざる）、
FastAPI での実装（依存が増え、モックサーバ自体のセットアップが検証の障害になりうる）。

**影響**: ルート構成に `mocks/` が加わる。README とディレクトリ構成の記述を更新済み。

## D-007 リージョンとモデル ID は config に直書きし、環境変数には秘密情報だけを置く

**状態**: 採用（2026-09-04）

**文脈**: `litellm/config.yaml` のリージョン・モデル ID を環境変数化するか、直接書くか。

**決定**: リージョンとモデル ID は config に直書きする。環境変数は AWS クレデンシャルと master key のみ。

**理由**:
1. リージョンとモデル ID は秘密情報ではなく、むしろ**構成そのもの**なので、
   config を読めば primary / fallback の対応が一目で分かる状態が望ましい（監査性）。
2. LiteLLM の `os.environ/` 解決が `model` フィールドに対しても効くかは未確認であり、
   検証の本筋と関係ない不確実性を持ち込みたくない。
3. クロスリージョン推論プロファイル ID を使う場合、リージョンごとにプレフィックスが異なるため
   「1つの環境変数を両方で使い回す」構造がそもそも成立しない可能性がある。

**採らなかった案**: 全パラメータの環境変数化（上記2・3の不確実性を抱え込む）。

**影響**: リージョンを変える際は config.yaml と config.fault.yaml の両方を編集する必要がある。
PoC の規模では許容する。

## D-008 モデルは claude-sonnet-4-6 を `jp.` / `us.` プロファイルで使う

**状態**: 採用（2026-09-04）

**文脈**: Phase 1 実施手順1（モデルアクセス調査）の結果、以下が判明した。

- Bedrock の Claude で `ON_DEMAND`（基盤モデル ID の直接呼び出し）が可能なのは
  `anthropic.claude-3-haiku-20240307-v1:0` のみ。それ以外はすべて推論プロファイル必須。
- ap-northeast-1 には `jp.` プレフィックスの**日本国内限定プロファイル**が存在する。
- Sonnet 5 / Opus 5 / Fable 5 は東京では `global.` プロファイルしか無い。
- `claude-sonnet-4-6` は東京に `jp.`、us-east-2 に `us.` の両方が ACTIVE で存在する。

**決定**: `claude-sonnet-4-6` を採用し、primary を `jp.anthropic.claude-sonnet-4-6`（東京エンドポイント）、
fallback を `us.anthropic.claude-sonnet-4-6`（オハイオエンドポイント）とする。

**理由**:
1. **`global.` を避けられる。** `global.` プロファイルは AWS 側が全球ルーティングするため、
   `global.` → `us.` というフォールバックは US が global の部分集合となり、
   現実には起きない状況を検証することになる。`jp.` → `us.` なら包含関係がなく、構成として筋が通る。
2. **同一モデルを保てる。** 両者は同じ `claude-sonnet-4-6` であり、変わるのは推論の地理圏だけ。
   D-003 の主旨（応答品質の交絡を排除する）が維持される。
3. **実運用にそのまま使える。** 「日本国内で推論し、国内が捌けなければ US 圏へ退避する」は
   国内企業の本番構成として現実的で、データ所在の説明も付く。
4. **能力が十分。** Phase 2 の構造化 JSON 出力、Phase 3 の SRE 判断に耐える。

**採らなかった案**:
- **Sonnet 5**: 東京に `global.` しか無く、上記1の入れ子問題が起きる。
- **Claude 3 Haiku（ON_DEMAND）**: リージョン単位で 1 対 1 になり観測は最も厳密だが、
  Phase 2 以降の構造化出力が実運用と乖離し、PoC の結論の転用性が落ちる。
- **`global.` を 2 つのリージョンエンドポイントから叩く**: 障害単位が「リージョンエンドポイント」になり
  それ自体は成立するが、`jp.` / `us.` が使える以上こちらを選ぶ理由がない。
- **`apac.` プロファイル**: `claude-sonnet-4-6` には存在しない（`apac.` があるのは Claude 3 系と Sonnet 4）。

**影響**:
- 地理圏**内**のどの物理リージョンが応答したかは観測できない。判定基準は
  「`jp.` デプロイと `us.` デプロイのどちらが応答したか」で満たす（design.md 第5章・第6章）。
- コストを抑えたい場合は `claude-haiku-4-5-20251001-v1:0` が同じく `jp.` / `us.` の両方を持つため、
  config の 2 行を書き換えるだけで差し替えられる。

## D-009: 第1層の判定エビデンスは「LiteLLM のヘッダ」と「障害注入側のアクセスログ」の2系統で取る

**日付**: 2026-09-29
**状態**: 採用

**背景**:
design.md 第6章は「確実に取得できる手段を最低1つエビデンスとして採用する」としていたが、
Phase 1 の F-04 で **`x-litellm-attempted-retries` が実際には 2 回リトライしているのに 0 を返す**
ことが判明した（[phase1 result.md](phases/phase1-litellm/result.md) 考察1）。
ヘッダだけを信じると「リトライは起きていない」と誤った結論に至る。

**決定**:
第1層の検証エビデンスは以下の 2 系統を必須とする。

1. **LiteLLM のレスポンスヘッダ** — `x-litellm-model-id`（どのデプロイが応答したか）と
   `x-litellm-attempted-fallbacks`（フォールバックの有無）。
2. **障害注入側のアクセスログ** — primary が実際に何回叩かれ、どのステータスを返したか。

**理由**:
- 1 は「結果」しか語らない。primary が試行されずに fallback へ直行した場合と、
  試行して失敗した場合を区別できない。
- 2 がなければ、シナリオ間で Router の cooldown 状態が持ち越されて
  「500 を一度も発生させていないのにフォールバックした」ログを正しい結果と誤認する
  （実際に F-01 → F-02 で発生させてしまった）。
- `mocks/fault_injector.py` は障害注入装置であると同時に**観測装置**として位置づける。

**影響**:
- 各シナリオの前に `docker compose restart litellm` を挟み、Router の内部状態を初期化する。
  これを検証手順に明記する。
- `x-litellm-attempted-retries` はエビデンスとして使わない。
- `GET /health` もエビデンスとして使わない。推論が全滅している状態で
  `unhealthy_count: 0` を返すことを実測した。
- Phase 3（OPA）以降も、層の内部状態を持つコンポーネントを検証する際は
  同じくリセット手順と「層の外側からの裏取り」を組み込む。

## D-010 第2層はインプロセスのライブラリとして実装し、HTTP 境界を持たせない

**日付**: 2026-09-29
**状態**: 採用

**文脈**: [architecture.md](architecture.md) の設計原則2 は「層をまたぐデータは JSON、層の実装は互いに import しない」
と定めている。これを字義どおりに読むと、第2層（Pydantic）もエージェントから import できず、
第1層・第3層と同じく独立したサービスとして立てる必要があるように見える。
Phase 2 の着手前にこの解釈を確定させる必要があった。

**決定**: 第2層はエージェントと同一プロセスで動くライブラリとする（`agents/schemas.py` + `agents/validation.py`）。
`docker-compose.yml` に第2層のコンテナは置かない。設計原則2 の「互いに import しない」は
**第1層・第3層の実装コードを import しない**という意味であり、第2層には適用しない。

**理由**:
1. **Pydantic はライブラリであって、サービスとして切り出す意味がない。** 検証は純関数であり、
   ネットワーク越しにしても得られるものは無く、レイテンシと障害点だけが増える。
2. **「層自体のダウン」という障害モードを持たないことが第2層の性質である。** 第1層は別プロセス、
   第3層は HTTP 越しなので層そのものが落ちうるが、第2層はエージェントが動いていれば必ず動く。
   この非対称性は隠さず、設計の帰結として明示する（Phase 2 design.md 2.1 の比較表）。
3. **境界は import の有無ではなくデータの形で担保する。** 層をまたぐデータは Pydantic モデル
   （= JSON 化可能な構造）に限り、第2層は第1層・第3層の実装を一切知らない。
   入力は `str | None`、出力は型付きオブジェクトであり、この契約は HTTP 境界がなくても成立する。

**採らなかった案**:
- **第2層を独立したバリデーションサービスにする**（原則2 の字義には最も忠実だが、
  検証したい対象（構造保証が決定的に働くこと）に何も足さず、HTTP という新たな失敗要因を持ち込む）。
- **第2層を第3層（OPA）に寄せて Rego でスキーマ検証まで行う**（層が 1 つ減るが、
  [D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) の分離を逆方向に崩す）。

**影響**:
- Phase 2 の異常系は「層の障害」ではなく「**入力の異常**」の注入になる。Phase 1 とシナリオ設計の性質が異なる。
- [D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る)
  の「層の外側からの裏取り」は第2層には原則として不要（入力と出力を我々が完全に握っているため）。
  ただし第1層を経由する経路検証では、第1層側の裏取りが引き続き必要。
- 第3層の可用性が単一障害点になる問題（[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) の影響欄）は、
  第2層には存在しない。Phase 3 でこの非対称性を踏まえて設計する。

## D-011 構造化出力の強制を第2層の代替としない

**日付**: 2026-09-29
**状態**: 採用

**文脈**: Bedrock / LiteLLM 側には `response_format`（JSON スキーマ指定）や tool use によって
モデル出力の構造を強制する仕組みがある。これを使えば壊れた JSON は出てこなくなり、
第2層は不要ではないか、という問いが当然出る。

**決定**: Phase 2 のベースラインは**プロンプトによるスキーマ提示のみ**とし、構造化出力の強制は使わない。
強制を入れた場合との比較は独立したシナリオ（C-01）として実施し、考察材料に留める。

**理由**:
1. **強制は「確率を下げる対策」であり、「決定的に遮断する仕組み」ではない。**
   本 PoC の主張は後者であり（[architecture.md](architecture.md) 脅威モデル）、
   前者で後者を置き換えたら主張そのものが崩れる。
2. **強制では原理的に守れない異常が残る。** フィールド間の相互依存（`kubectl_scale` なのに
   `replicas` が無い）、語彙の逸脱、そして「構造は正しいが内容が危険」は
   スキーマ強制の外側にある。第2層は落とし、第3層に渡すべきものは渡す必要がある。
3. **ベースラインに強制を入れると、検知能力が測れない。** 壊れた入力が来ないなら
   第2層が壊れた入力を止められるかは検証できない。検証のためには壊れた入力が届く構成が必要。
4. **プロバイダ依存を持ち込まない。** 強制の可否と挙動はモデル・プロバイダごとに異なる。
   第1層でベンダー非依存性を確保した（[D-004](#d-004-地理圏間のフェイルオーバーは-aws-に任せずlitellm-層で明示的に制御する)）のに、
   第2層の前提をプロバイダ機能に寄せるのは一貫しない。

**採らなかった案**:
- **ベースラインで強制を有効にする**（実運用の通過率は上がるが、上記 1〜3 により検証が成立しない）。
- **強制を一切扱わない**（提案として弱い。「なぜ強制で足りないのか」に答えられる必要がある）。

**影響**: 実運用への提言では「強制と第2層は排他ではなく併用する」形になる。
強制で構文レベルの異常の発生率を下げ、それでも通る異常を第2層が決定的に止める。
この二段構成の妥当性は Phase 2 の result.md で C-01 の結果とともに述べる。

## D-012 `ValidationError` からの自動修復リトライを入れない

**日付**: 2026-09-29
**状態**: 採用

**文脈**: 第2層で構造破壊を検知したとき、エラー内容をプロンプトに戻して LLM に再生成させる
「修復リトライ」は実装が容易で、実運用では通過率を大きく上げる。これを PoC に入れるか。

**決定**: 入れない。`ValidationError` は即座にエスカレーションイベントとなり、人間へのハンドオフに向かう。

**理由**:
1. **修復が成功すると「検知の決定性」が測れなくなる。** 判定基準は「壊れた入力が必ず止まること」であり、
   リトライを挟むと最終結果が確率的になり、何を証明したのか言えなくなる。
   [D-001](#d-001-エージェントフレームワークを導入しない) でフレームワークを排した理由と同じ構造の問題である。
2. **`x-litellm-attempted-retries` の教訓**（[D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る)）。
   層が自分の内部でリトライすると、外から見た挙動と内部の実態が乖離する。
   第1層で既に経験した混乱を第2層で再現する必要はない。
3. **リトライ回数・打ち切り条件・コストという新たな設計事項が発生する。** Phase 2 の検証対象ではない。

**採らなかった案**: 1 回だけの修復リトライ（実運用では妥当な設定だが、上記 1 により PoC のベースラインには置けない）。

**影響**: PoC では第2層の失敗が即ハンドオフになるため、実運用よりエスカレーション頻度が高く出る。
「修復リトライを 1 回入れる」は実運用への提言として result.md に書く。
その際、修復リトライは**第2層の内側ではなくエージェント側のループとして置く**（層の責務を汚さない）ことを併記する。

## D-013 第2層は役割名 JSON Validator で呼ぶ（実装名で呼ばない）

**日付**: 2026-09-29
**状態**: 採用

**文脈**: 第2層をこれまで「Pydantic」と呼んでいた。第1層「LiteLLM」・第3層「OPA」と並べると
統一されて見えるが、第2層だけは**層の名前が実装ライブラリの名前になっている**。
Phase 2 の実装に入る前に呼称を確定させる必要があった。

**決定**: 第2層は役割名 **JSON Validator** で呼ぶ。実装は Pydantic v2 のままとし、
実装名は「実装」として併記する。第1層・第3層は製品名（LiteLLM / OPA）で呼び続ける。

**理由**:
1. **検証対象が実装固有ではない。** Phase 2 の判定基準は「構造破壊を決定的に検知し、
   理由を特定できること」であり、Pydantic 固有の何かではない。strict な JSON スキーマ検証ができれば
   他の実装でも成立する。層の名前が実装名だと、結論が Pydantic の話に見えてしまう。
2. **[D-011](#d-011-構造化出力の強制を第2層の代替としない) との整合。** 「第2層の前提をプロバイダ機能に寄せるのは一貫しない」と書いた直後に
   層をライブラリ名で呼んでいるのは、その主張を弱める。
3. **提案としての強度。** 「Pydantic で守る」は実装の話、「JSON Validator 層を置く」は設計の話である。
   本 PoC の成果物は後者でなければ転用が効かない。

**第1層・第3層を製品名のままにする理由**（対称にしない判断）:
検証対象の性質が実際に非対称である。第1層で得た知見は Router の cooldown、
`x-litellm-attempted-retries` の不正確さ、ヘッダによる観測といった**LiteLLM 固有の事象**であり
（[D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る)）、
第3層の成果物は Rego ポリシーそのものである（[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く)）。
これらは製品名で呼ぶ方が実態に合う。第2層だけが実装に依存しない層であり、
呼称の非対称性はその違いをそのまま反映したものである。

**採らなかった案**:
- **全層を役割名に統一する**（Model Gateway / JSON Validator / Policy Engine）。
  見た目は最も整うが、上記のとおり第1層・第3層では製品固有の知見が検証結果の本体であり、
  役割名にすると何を検証したのかが曖昧になる。完了済みの Phase 1 の result.md と
  エビデンス全体の書き換えも必要になる。
- **「構造検証層」など日本語の役割名にする**（識別子（`layer2_json_validator`）と表記が揃わない）。

**影響**:
- ドキュメントの呼称を「第2層 (JSON Validator)」に統一した（README / CLAUDE.md / architecture.md /
  TODO.md / Phase 2 の design.md・result.md）。「Pydantic」の記述は**実装固有の挙動を指す箇所だけ**に残す
  （`strict=True` の効き方、`model_validate_json()` の例外正規化など）。
- `EscalationEvent.layer` の値は `layer2_pydantic` → **`layer2_json_validator`**。
- **D-001〜D-012 の既存記述は変更しない。** decisions.md は追記のみの運用であり
  （[docs/README.md](README.md) 運用ルール3）、過去の判断の文面を後から書き換えると
  「いつ何を決めたか」が追えなくなる。[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) のタイトルなど、
  既存エントリに残る「Pydantic」は第2層の読み替えとして扱う。
- ディレクトリ名 `docs/phases/phase2-pydantic/` は**変更しない**。
  `phase1-litellm` / `phase3-opa` と同じく実装で場所を示す命名であり、
  層の呼称とは別の関心事である。完了済み Phase 1 の result.md からの相互リンクも壊さずに済む。

## D-014 異常系の検証では「障害注入が効いていること」を層の外側から必ず確認する

**日付**: 2026-09-29
**状態**: 採用

**文脈**:
Phase 2 の R-01（第1層が 200 を返し、content だけが壊れている経路）の初回実行で、
10 シナリオすべてが終了コード 0 になった。原因は第2層ではなく
**fault-injector コンテナが起動していなかった**ことで、primary が接続不能になった結果
第1層が実 Bedrock にフォールバックし、**正常なアクションが返って検証が通過**していた
（[phase2 result.md](phases/phase2-pydantic/result.md) 考察3）。

[D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る) は
「層が自己申告する値を鵜呑みにしない」ための 2 系統化だった。今回起きたのはそれとは別の失敗で、
**注入したはずの異常が届いていない**という、検証の前提そのものが崩れるパターンである。

**決定**:
異常系シナリオでは、判定の前に以下を必ず確認する。確認できないシナリオは結果を採用しない。

1. **障害注入コンポーネントが稼働していること**（コンテナの状態）。
2. **注入した異常が実際にエージェントまで届いたこと**（injector のアクセスログに該当リクエストがある）。
3. **フォールバック等で別経路に逃げていないこと**（`x-litellm-attempted-fallbacks` / `x-litellm-model-id`）。

**理由**:
- **注入の失敗は「エラー」ではなく「成功」として現れる。** テストが落ちるなら気づけるが、
  このケースは全件が正常終了する。何も表示されないことが症状なので、能動的に確認するしかない。
- **多層防御では、上位層が下位層の障害注入を打ち消しうる。** 第1層のフォールバックは
  可用性のための正しい挙動であり、同時に「第2層に壊れた入力を届ける」という意図を無効化する。
  層を重ねるほどこの干渉は起きやすくなる。
- 検証の結論が「合格」で揃っているときほど疑う必要がある。

**採らなかった案**:
- **障害注入時はフォールバックを無効にする**（干渉は消えるが、本番に近い構成から離れる。
  また「第1層が何もしていないこと」を示せなくなり、Phase 2 の判定基準3 が検証できない）。
- **エージェント側で注入状態を検知する**（設計原則1「エージェントは自分が守られていることを知らない」に反する）。

**影響**:
- Phase 3 以降の design.md には、シナリオごとに「注入が効いていることの確認手段」を明記する。
- Phase 3 では、OPA の `allow` がポリシー評価の結果であって
  デフォルト値やエラーの握り潰しでないことを、層の外側から裏取りする手順を入れる。
- 検証スクリプトは、注入コンポーネントの稼働確認に失敗したらそのシナリオを
  **無効として明示的に記録する**（黙って続行しない）。

## D-015 第3層は Fail-Closed とし、OPA の可用性対策を PoC では採らない

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) の影響欄に「OPA 自体の可用性が新たな単一障害点になる。
この扱いは Phase 3 の設計で決める」と書いた宿題。第3層は第2層と違って HTTP 境界を持つため
（[D-010](#d-010-第2層はインプロセスのライブラリとして実装しhttp-境界を持たせない)）、
**層そのものが落ちる**という障害モードが存在する。冗長化・サイドカー化・WASM 埋め込み・
判定結果のローカルキャッシュなど、可用性を上げる手段は複数ある。

**決定**:
可用性対策は採らない。OPA が評価できないときは **Fail-Closed**（実行に進まず、人間へハンドオフ）とする。
「評価して拒否された（deny）」と「評価できなかった（unavailable）」は別の状態として区別し、
前者は戻り値、後者は例外（`PolicyUnavailableError`）で表現する。エージェント側でのリトライも入れない。

**理由**:
1. **単一障害点であることは隠すより示すほうが成果物として価値がある。** 本 PoC は
   「各層が期待どおり異常を検知・遮断するか」を実証するものであり
   （[architecture.md](architecture.md) 設計原則4「安全網の限界を明示する」）、
   第3層の可用性が全体の実行可能性を握るという構造そのものが検証結果である。
2. **deny と unavailable を取り違えると、人間に見せるものが変わる。** Handoff 仕様書では
   前者が通知パターン3（承認ボタンつき＝人間が判断して実行しうる）、後者がパターン4
   （ボタンなし＝そもそも安全性が不明）に対応する。両方を `allow: false` に潰すと、
   **安全性が不明な操作に承認ボタンを出す**ことになりかねない。
3. **リトライは検知の決定性を壊す。** [D-012](#d-012-validationerror-からの自動修復リトライを入れない) と同じ構造の問題で、
   「評価不能だったが最終的に通った」が確率的に起きると、Fail-Closed が効いていることを証明できない。
4. 可用性対策を入れると、X 系（第3層の障害）シナリオが**注入しても発火しなくなる**。
   Phase 2 で「上位層の正しい挙動が下位層の障害注入を打ち消す」ことを経験している
   （[D-014](#d-014-異常系の検証では障害注入が効いていることを層の外側から必ず確認する)）。

**採らなかった案**:
- **OPA をサイドカーとして同一 Pod に置く**（実運用では妥当。ネットワーク障害の面は減るが、
  PoC では「OPA を落とせること」自体が検証手段なので利点にならない）。
- **判定結果をローカルにキャッシュして OPA 停止中も判定する**（可用性は上がるが、
  ポリシー変更の反映が不確定になり、監査可能性を失う。deny を許可に化けさせる経路も作りうる）。
- **Fail-Open（評価不能なら実行を許す）**（可用性のためにこれを採る実装は現実に存在するが、
  本 PoC の主張と正面から矛盾する）。
- **エージェント側で短いリトライを入れる**（実運用では妥当。提言として result.md に書く）。

**影響**:
- 第3層の障害は**そのまま業務の停止**になる。実運用への提言では、サイドカー化・
  ポリシーの bundle 配布・短いリトライ・ヘルスチェックによる早期検知をセットで述べる必要がある。
- Phase 5 の E2E では「第3層が落ちている間は何も実行できない」状態が観測されるはずで、
  これを異常ではなく設計どおりの挙動として扱う。

## D-016 ポリシー評価の入力に Trace ID を含めるが、Rego からは参照しない

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
Phase 2 の積み残しに「`EscalationEvent` に相関 ID が無く、第1層のログと突き合わせられない」があり、
Phase 4 で追加する予定だった。一方 Handoff 仕様書の運用原則2 は
「**ボタンの `value` には Trace ID のみを格納し、実行内容はサーバ側のストアから取得する**」と定めており、
これは第3層が拒否した時点で Trace ID が確定していることを前提にしている。
また [D-014](#d-014-異常系の検証では障害注入が効いていることを層の外側から必ず確認する) は
第3層の判定を層の外側から裏取りすることを求めており、そのための突合キーが要る。

**決定**:
Trace ID を Phase 4 ではなく **Phase 3 で導入**する。粒度は「1 インシデント処理 = 1 Trace ID」。
OPA へ渡す `input` は `{"action": {...}, "trace_id": "..."}` のエンベロープとし、
**Rego は `input.trace_id` を参照しない**（判定材料と監査キーを構造的に分離する）。

**理由**:
1. **Trace ID が無いと第3層の検証自体が成立しない。** OPA の Decision Log と
   エージェントのログを突合できなければ、「`allow: true` はポリシーが許可した結果である」ことを
   層の外側から示せない。Phase 4 の都合ではなく Phase 3 の判定基準の都合である。
2. **`input` に入れるのが最も確実に Decision Log に残る方法である。** OPA は評価した `input` を
   そのまま Decision Log に記録するため、エージェント側の実装に依存せず突合キーが残る。
   HTTP ヘッダに載せる方法では Decision Log に現れない可能性がある。
3. **Rego が参照しないことを明示するのが重要。** 参照した瞬間、Trace ID の値によって判定が
   変わりうることになり、ポリシーの決定性（判定基準5）が原理的に崩れる。
   「入力に含まれるが判定には使わない」という制約を設計判断として固定する。

**採らなかった案**:
- **`input` をアクションそのもの（フラット）に保ち、Trace ID はヘッダで渡す**
  （Phase 2 の判定基準5「`model_dump()` がそのまま `input` になる」に最も忠実だが、
  Decision Log に残る保証がない。エンベロープにしても `input.action` が
  `model_dump(mode="json")` そのものである点は変わらない）。
- **Trace ID を `ProposedAction` のフィールドにする**（LLM が出力する値ではないものを
  LLM 出力のスキーマに混ぜることになり、第2層の責務が濁る）。
- **Phase 4 まで導入を先送りする**（上記 1 により、第3層の裏取りが弱いまま合格判定を出すことになる）。

**影響**:
- 第2層の構造化ログと `EscalationEvent` の形が変わる（`trace_id` が増える）。
  Phase 2 の判定結果は変わらないが、**Phase 2 の `assets/` は上書きせずそのまま残す**
  （エビデンスのファイル名を使い回さないのと同じ理由）。
- Phase 4 のステートストアはこの Trace ID をキーにする。Slack のボタン `value` に入る値も同じもの。

## D-017 OPA の応答を無検証で信じない（decision も strict に検証する）

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
第2層は「LLM の出力を信じない」層である。では**第3層の応答**は信じてよいか。
`allow` は実行可否そのものなので、ここが素通りすると多層防御の最後の 1 枚が無効になる。
OPA の応答には、ポリシー未ロード（`result` が返らない＝undefined）、Rego のバグによる型の逸脱、
`allow: true` なのに違反が列挙されている自己矛盾、といった状態がありうる。

**決定**:
OPA の応答を第2層と同じ厳密さで検証する。`PolicyDecision` を `strict=True` / `extra="forbid"` で定義し、
`OpaResponse.model_validate_json()` で受ける。以下はすべて **評価不能**（Fail-Closed）として扱い、
`allow` には倒さない。

- `result` が無い（undefined）
- `allow` が真偽値でない / `violated_rules` の要素が規定の形でない / 未知のキーがある
- `allow: false` なのに理由が空、`allow: true` なのに違反が非空（自己矛盾）

**理由**:
1. **undefined を `allow: false` に潰すと、パターン3 とパターン4 の区別が失われる**
   （[D-015](#d-015-第3層は-fail-closed-としopa-の可用性対策を-poc-では採らない) 理由2）。
   「ポリシーが拒否した」と「ポリシーが存在しない」は人間に見せるべきものが違う。
   そのため Rego 側に `default allow := false` を書かず、undefined を undefined のまま表面化させる。
2. **理由なき拒否は設計原則3 違反であり、ポリシー側のバグである。** 通過させても拒否として
   扱っても実害はないように見えるが、エスカレーションで人間が判断できないため、検知して直すべき異常である。
3. **`extra="forbid"` にしておくと、Rego の返すキーが増えたときに気づける。**
   黙って無視すると、将来の「条件つき許可」のような拡張を見落とす。
4. Phase 2 の知見（strict は JSON 入力と Python 入力で挙動が違う。`model_validate(dict)` は
   enum に実インスタンスを要求する）をそのまま適用し、`response.json()` → `model_validate(dict)` の
   2 段にしない。

**採らなかった案**:
- **`response.json()["result"]["allow"]` を直接読む**（実装は最短だが、上記の異常がすべて
  `KeyError` か素通りになる。素通りが `allow: true` 側に出た場合が最悪）。
- **エンベロープにも `extra="forbid"` を付ける**（OPA が `decision_id` / `metrics` / `provenance` を
  足すため運用できない。エンベロープは「層をまたぐデータ」ではなく OPA の API 表現なので
  `extra="ignore"` とし、中身の decision だけを forbid する）。

**影響**:
- ポリシーの出力形（`decision` 文書のキー）がエージェント側のスキーマと**二重管理**になる。
  片方だけ変えると Fail-Closed する。これは事故ではなく設計どおりの挙動だが、
  変更時の手順として result.md に明記する。実運用では Rego の出力を JSON Schema として
  共有する方法（あるいは OPA の bundle にスキーマを同梱する方法）を提言に書く。

## D-018 注入が効いていることの確認は「注入器の状態」ではなく「リクエストが通った経路」で行う

**日付**: 2026-09-30
**状態**: 採用（[D-014](#d-014-異常系の検証では障害注入が効いていることを層の外側から必ず確認する) の改訂）

**文脈**:
Phase 3 の B / P / N-01 系の初回実行で、9 シナリオ中 4 件が**期待どおりの終了コードを返した**。
しかし第1層のヘッダは全件 `x-litellm-model-id=primary-jp` で、fault-injector ではなく
実 Bedrock が応答していた。fixture は 1 件も使われていなかった
（[phase3 result.md](phases/phase3-opa/result.md) 考察1）。

原因は `docker compose restart litellm` である。**`restart` はコンテナを作り直さないため、
`command` に埋め込まれた `${LITELLM_CONFIG_FILE}` も環境変数も更新されない。**
Phase 1 の知見「シナリオ切り替えのたびに `restart litellm`」は Router の cooldown を消すためのもので、
設定そのものを切り替える用途には足りなかった。

[D-014](#d-014-異常系の検証では障害注入が効いていることを層の外側から必ず確認する) は確認項目の
1 番目に「障害注入コンポーネントが稼働していること（コンテナの状態）」を挙げていた。
今回、injector は**正常に稼働していた**。稼働していたが、誰もそこにリクエストを送っていなかった。

**決定**:
異常系シナリオの前提確認は、**リクエストが実際にその経路を通ったことの証拠**で行う。
注入器の稼働確認は補助であって、単独では前提確認として採用しない。

- 第1層を経由する経路: `x-litellm-model-id` が注入先を指していること、かつ
  `x-litellm-attempted-fallbacks` が 0 であること。
- 第3層を壊す経路: 当該エンドポイントを直接叩いた生の応答（`curl`）をシナリオごとに記録する。
- 設定を切り替えるときは **`docker compose up -d --force-recreate`** を使う。`restart` は状態の初期化にのみ使う。

**理由**:
1. **注入の失敗は「偽の合格」だけでなく「偽の不合格」としても現れる。** Phase 2 では全件が
   静かに正常終了した（[D-014](#d-014-異常系の検証では障害注入が効いていることを層の外側から必ず確認する)）。
   Phase 3 では逆に、期待と違う終了コードが出たことで気づけた。**どちらに転ぶかは運**であり、
   検知を運に任せてはいけない。
2. **もっとも危険なのは「偶然一致した合格」である。** 今回、本番 PVC 削除の fixture を流したつもりの
   B-01 は終了コード 0（allow）で終わっていた。注入器の稼働だけを確認していたら、
   **「第3層が本番の PVC 削除を許可した」という誤った結論**を記録していた。
3. **稼働していることと使われていることは別である。** コンポーネントの状態確認は
   「注入が可能な状態か」しか語らない。検証が必要としているのは「注入が届いたか」である。

**採らなかった案**:
- **シナリオごとに注入器のアクセスログの件数を比較する**（経路は確認できるが、
  実行のたびに累積するため差分管理が要る。ヘッダ 1 つで判別できるなら不要）。
- **エージェント側で経路を検査する**（設計原則1 に反する。[D-014](#d-014-異常系の検証では障害注入が効いていることを層の外側から必ず確認する) と同じ理由）。

**影響**:
- Phase 3 の検証スクリプトは、経路が確認できないシナリオを **VOID として記録して結果を採用しない**
  （[step3-VOID-injection-not-effective-summary.txt](phases/phase3-opa/assets/step3-VOID-injection-not-effective-summary.txt) に残した）。
- Phase 4・5 でも、Slack の送出経路・承認経路について「届いたことの証拠」を先に決めてから実行する。
- CLAUDE.md の「よく使うコマンド」に `--force-recreate` を明記する。

## D-019 エスカレーションの送出はインプロセス、受信は独立プロセスにする

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
[D-010](#d-010-第2層はインプロセスのライブラリとして実装しhttp-境界を持たせない) で
「第2層はインプロセス、第3層は別プロセス」という非対称を整理した。
エスカレーション層はどちらか。Handoff 仕様書の図1 は通知を「【App 主導】」と書き、
図3 は「App プロセスは待機せず解放」と書いている。**送出と受信で必要な形が違う**。

**決定**:
ひとつの層の中で形を分ける。**送出（`slack/notifier.py`）はエージェントと同一プロセスの
ライブラリ**として import し、**受信（`slack/handler.py`）は独立した常駐プロセス**にする。
ハンドオフ経路は `agents/escalation.py` に 1 本化し、各層（第2層・第3層）は通知先を知らない。

**理由**:
1. **送出の失敗をそのインシデント処理の結果に反映させる必要がある。** 別プロセスに投げっぱなしにすると、
   「遮断はしたが人間に届いていない」を終了コードに出せない（[D-022](#d-022-通知の失敗を遮断の成立と分けて表面化させる)）。
2. **受信は数分〜数時間後に来る。** エージェントのプロセスは既に終了している。
   承認を待つ主体はエージェントではなく、ストアと常駐プロセスである。
3. **層は通知先を知らないままにできる。** `validate_action()` / `evaluate_action()` は
   `escalate(event)` を呼ぶだけで、Slack の存在を知らない。通知層を差し替えても層の実装は変わらない
   ([architecture.md](architecture.md) 設計原則2)。

**採らなかった案**:
- **送出も独立プロセスにする（イベントをキューに積む）**（実運用では妥当。PoC では
  「届かなかったこと」を検知する経路が 1 段増え、何を検証しているのかが曖昧になる）。
- **各層から直接 Slack SDK を呼ぶ**（層が通知先を知ることになり、設計原則2 に反する。
  ハンドオフ経路も 3 本に分かれる）。

**影響**:
- `agents/` → `slack/`（送出）と `slack/` → `agents/`（受信）の双方向依存になる。
  循環を避けるため `slack/handler.py` は誰からも import されない終端に置き、
  実行層を `agents/execution.py` に切り出す。
- handler が落ちていると、ボタンを押しても何も起きず**エージェント側に記録が残らない**。
  この単一障害点は隠さず N-02 で観測する。

## D-020 承認内容はストアから復元し、復元時に第2層で再検証する

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
Handoff 仕様書 運用原則2 は「ボタンの `value` には Trace ID のみを格納し、
実行内容はサーバ側のストアから取得する」と定める（ペイロード改変による任意コマンド実行の防止）。
一方、ストアはこの PoC で初めて登場する**可変の永続状態**であり、
承認までの数分〜数時間のあいだ、エージェントのプロセスの外に置かれる。

**決定**:
`value` は Trace ID のみとし、実行内容は必ずストアから復元する。そのうえで、
**復元したアクションを実行の直前に `ProposedAction.model_validate_json()` で再検証する**。
検証に失敗したエントリは実行せず、`ValidationError` として扱う。

**理由**:
1. **第2層は「LLM の出力を信じない」層だった。時間をまたいで保存されたデータも同じ扱いにするのが一貫している。**
   [D-017](#d-017-opa-の応答を無検証で信じないdecision-も-strict-に検証する) で
   「OPA の応答も信じない」と決めたのと同じ構造の判断である。
2. **再検証のコストは関数呼び出し 1 回で、失敗は安全側に倒れる。** 実行されないだけで、
   ストアの記録も監査も残る。
3. **ストアの改変をすべて防げるわけではない**（型として正しい別アクションに書き換えられれば通る）。
   だからこそ、**何が防げて何が防げないかを実測して示す**（N-01）。
   防げない範囲は「ストアへの書き込み権限を持つ者は実行内容を決められる」であり、
   これは第3層が input の真正性を検証できないこと（Phase 3 N-01）と同じ種類の限界である。

**採らなかった案**:
- **`value` にアクションの JSON を入れる**（ストアが不要になるが、署名検証を突破されたときに
  任意コマンドが実行できる。仕様書が明示的に禁じている）。
- **ストアから読んだ dict をそのまま実行層に渡す**（実装は最短だが、
  ストアだけが信頼済みの領域になる。Pydantic を通す一貫性が崩れる）。
- **承認時に第3層へ再問い合わせして整合を取る**（[D-023](#d-023-承認時に第3層へ再問い合わせせず-policy_override-として記録する) で別途否定した）。

**影響**:
- ストアのレコードが壊れると承認できなくなる（安全側の故障）。T-07 で挙動を固定する。
- 監査の正本はストアの原文であり、**マスキングは送出先にのみ適用する**。
  ストアにマスキングをかけると、後から「何が起きたか」を追えなくなる。

## D-021 確認強度と承認権限を操作の種別で出し分けない

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
Handoff 仕様書 運用原則3 は「本番の PVC/PV 削除については Modal でリソース名を手入力させる」、
付帯要件の RBAC は「Production 破壊的操作は上位ロール」と定める。
どちらも実装すると、通知層に `if environment == "production" and operation in destructive:` が生まれる。
これは Phase 3 の判定基準7（`production` / `kubectl_delete_*` による条件分岐を `agents/` に書かない）が
禁じたものと同じ形であり、**ポリシーの判定が `agents/` から `slack/` に移っただけ**になる。

**決定**:
確認強度（confirm）と承認権限（RBAC）を、操作の種別・環境で出し分けない。

- confirm ダイアログは**すべての承認ボタンに一律で**付ける。
- 承認権限は**承認者リストに含まれるかどうか**の一律判定とする。
- **値を文面に埋め込むのはよい。値で分岐するのはだめ。** 対象環境やリソース名を confirm の
  文言に表示するのは「提示」であり、判定ではない（CLAUDE.md が `schemas.py` / `prompts.py` に
  認めている例外と同じ線引き）。
- Modal によるリソース名の手入力は Phase 4 では扱わず、提言に回す。

**理由**:
1. **判定の語彙が 2 箇所に分かれると、必ず食い違う。** 第3層のポリシーを緩めても
   通知層の分岐が残れば強い確認が出続け、逆も起きる。二重管理は
   [D-017](#d-017-opa-の応答を無検証で信じないdecision-も-strict-に検証する) の影響欄で
   既に問題として認識している（decision のスキーマ）。ここで新たに増やさない。
2. **分岐が無ければ、事故が構造的に起こらない。** 「パターン4 にボタンが出た」
   「本番なのに confirm が出なかった」は、条件が 1 つ（`kind == "policy_denied"`）なら発生し得ない。
3. **出し分けが必要なら、危険度は第3層が既に `violated_rules` として返している。**
   Rego 側に承認要件（`required_approver_role` 等）を持たせるのが筋であり、
   通知層で推測し直すのは責務の重複である。
4. **Modal の前提（confirm の形骸化）は 1 回の PoC では観測できない。**
   検証できないものを実装しても、判定基準を作れない。

**採らなかった案**:
- **仕様書どおり Modal と多段ロールを実装する**（実運用では妥当。PoC では上記の二重管理を招く）。
- **確認強度の対応表を `slack/` の設定ファイルに外出しする**（`agents/` からは消えるが、
  ポリシーの語彙が `opa/` と `slack/` に分かれる点は変わらない）。

**影響**:
- 仕様書の運用原則3 後段と RBAC の一部は Phase 4 では未実装のまま残る。
  **実装しない理由を result.md の提言に書き、Rego 側に承認要件を持たせる案を示す。**
- Phase 5 で承認要件をポリシー由来にする場合、`decision` 文書にキーが増えるため
  `PolicyDecision` の `extra="forbid"` によって Fail-Closed する。変更手順に注意が要る。

## D-022 通知の失敗を遮断の成立と分けて表面化させる

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
Slack への送出が失敗しても、第2層・第3層の判定は成立している。アクションは実行されておらず、
ログとストアには残っている。失敗しているのは「人間に届けること」だけである。
一方、運用上これはもっとも危険な状態になりうる。**止めたことを誰も知らない**からである。
Phase 3 までの終了コードは 0 / 1 / 2 / 3 / 4 で、この状態を表現できない。

**決定**:
送出の失敗を **終了コード 5** として追加し、遮断の成立（3 / 4）と区別する。重さの順は 5 > 4 > 3 > 1 > 0。
送出の例外は握り潰さず `event=slack.failed` を出力し、ストアの `status` を `failed`、
`message_ts` を NULL のままにする。**自動再送はしない。** 別経路（PagerDuty 等）も実装しない。
`SLACK_BOT_TOKEN` 未設定は障害ではなく構成として扱い、`event=slack.skipped` を出して終了コードを変えない。

**理由**:
1. **「遮断できた」と「遮断できたが誰も知らない」は別の状態である。** 同じ終了コードに潰すと、
   シナリオ実行スクリプトからも運用からも区別できない。
   [D-015](#d-015-第3層は-fail-closed-としopa-の可用性対策を-poc-では採らない) で
   deny と評価不能を分けたのと同じ理由である。
2. **自動再送は検知の決定性を壊す。** 「最終的に届いた」が確率的に起きると、
   E 系（送出障害）で何を観測しているのか言えなくなる
   （[D-012](#d-012-validationerror-からの自動修復リトライを入れない) と同じ構造）。
3. **Slack が単一障害点であることは、隠すより示すほうが成果物として価値がある**
   （[D-015](#d-015-第3層は-fail-closed-としopa-の可用性対策を-poc-では採らない) 理由1 と同じ）。
   別経路を実装すると、E 系が注入しても発火しなくなる。
4. **`SLACK_BOT_TOKEN` 未設定で終了コードを変えないのは、Phase 1〜3 の経路を再現するため。**
   未設定を失敗にすると、過去フェーズのシナリオが全部 5 で終わる。

**採らなかった案**:
- **送出失敗でも 3 / 4 のままにし、ログにだけ残す**（沈黙に近い。終了コードしか見ない
  実行スクリプトでは検知できない）。
- **送出失敗を最優先の失敗として 1 に倒す**（第1層・第2層の失敗と混ざる）。
- **短いリトライを入れる**（実運用では妥当。提言に書く）。

**影響**:
- `--repeat` の戻り値の意味が変わる（最も重いものが 5 になりうる）。
- E 系では終了コード 5 と「実行層のログが無いこと」を**同時に**確認する必要がある。
  片方だけでは「遮断は成立している」と言えない。
- 実運用への提言に「Critical は別経路へフォールバックする」「短いリトライを入れる」を必ず書く。
  PoC で実装しないことと、実運用で不要であることは別である。

## D-023 承認時に第3層へ再問い合わせせず `policy_override` として記録する

**日付**: 2026-09-30
**状態**: 採用

**文脈**:
人間が承認するのは「第3層が `allow: false` を返したアクション」である。
実行の直前に OPA へ問い合わせ直せば、当然また deny が返る。
一方、Handoff 仕様書の付帯要件は、この状況を **`policy_override`（ポリシー違反を人間が上書きした事実）**
として監査に残すことを求めている。また TOCTOU（承認待ちのあいだにインフラの状態が変わる）への
対策として、実行前の再評価には一定の合理性もある。

**決定**:
承認・実行時に第3層へは再問い合わせしない。監査に `override_kind` を記録し、
Phase 4 の承認は全件 `policy_override` になる。`normal_approval` との区別はスキーマに残す。
TOCTOU は再評価ではなく、**承認時刻と実行時刻の差**（閾値 5 分）で扱う。

**理由**:
1. **再問い合わせしても答えは変わらない。** deny されたから承認フローに入っているのであり、
   結果が同じ問い合わせを挟むと「なぜ deny なのに実行するのか」の説明が二重になる。
   人間の承認がポリシーを上書きしたという事実こそが記録すべきものである。
2. **OPA の Decision Log には override が残らない**（Phase 3 提言7）。
   実行側で記録しなければ、**どこにも残らない**。
3. **`normal_approval` を今のうちにスキーマに残すのは、後から意味を変えないため。**
   Phase 5 で「deny ではないが人間の確認を挟む」経路が出てきたとき、
   既存レコードの `policy_override` の意味が変わってしまうことを避ける。
4. **TOCTOU は「ポリシーが変わったか」ではなく「世界が変わったか」の問題である。**
   OPA に聞いても分からない（第3層はクラスタの現在状態を見ていない）。経過時間で扱うのが素直である。

**採らなかった案**:
- **実行直前に再評価し、まだ deny なら実行しない**（承認フローが成立しなくなる。
  人間の承認に意味が無くなる）。
- **再評価してポリシーが変わっていたら通常の実行として扱う**（ポリシーの差し替えで
  override の記録が消えるため、監査としては劣化する）。
- **TOCTOU で第3層に再問い合わせする**（理由4 のとおり、第3層はクラスタの現在状態を知らない）。

**影響**:
- 監査ログの `override_kind` は Phase 4 では常に `policy_override` になる。
  これは「区別が機能していない」のではなく、Phase 4 の承認対象が `policy_denied` だけだからである
  （`validation_failed` / `policy_unavailable` はストアに入らない）。
- 実運用では、承認から実行までの経過時間の閾値（本 PoC では 5 分）を
  対象システムの変化速度に合わせて決める必要がある。提言に書く。

## D-024 受信と実行を分けず、Slack の再送を二重押下と同じ経路で弾く

**日付**: 2026-10-01
**状態**: 採用

**文脈**:
別途の仕様書「Slack Handoff ルーター実装仕様書」は、受信（署名検証・RBAC・ステート更新）と
実行（インフラコマンドの発行）を **SQS で分離**する構成を採っている。理由は Slack の 3 秒ルールで、
Webhook の応答が 3 秒を超えると Slack はタイムアウトとみなし、**同じペイロードを再送する**
（`X-Slack-Retry-Num` / `X-Slack-Retry-Reason` が付く）。K8s API の応答が遅いと、
同一プロセスで実行まで行う構成はこの制約を超えうる。

本 PoC の実行層は **dry-run の構造化ログを 1 行出すだけ**であり、3 秒に対して桁が 5 つ違う。

**決定**:
受信と実行を分けない。`slack/handler.py` が署名検証からステート遷移・実行層の呼び出し・
`chat.update` までを 1 プロセスで行う。そのうえで:

- **`ack()` を最初に呼ぶ**（署名検証の直後、ストアに触る前）。
- **Slack の再送を異常として扱わない。** 二重押下と同じ経路（ストアの CAS）で弾く。
- **二重実行の検証はこの再送を主軸にする**（G-06）。実機の連打（A-03）は補助に回す。
- **分離しない前提が崩れる条件を design.md に明記する**（3.14）: 実行が実 API 呼び出しになった時点で成立しない。

**理由**:
1. **キューを増やすと、検証対象が「キューの挙動」に移る。** SQS を置けば at-least-once 配信と
   可視性タイムアウトの検証が必要になり、Phase 4 の判定基準（押した内容と実行内容の一致・ステートの一貫性）が
   インフラの性質で曇る。[D-001](#d-001-エージェントフレームワークを導入しない)（切り分けを曖昧にする要素を排除する）と同じ判断である。
2. **再送は、キューを置かなくても起きる。** 仕様書は at-least-once を SQS の性質として説明しているが、
   **Slack の 3 秒ルール自体が同じ構造の二重配信を生む**。したがってキューの有無に関わらず
   冪等性は必要であり、本 PoC はその最小形（ストアの CAS 1 つ）で成立することを示せる。
3. **再送のほうが連打より決定的に再現できる。** 実機の二重押下はタイミング依存で、
   「たまたま競合しなかった」合格になりうる。再送ヘッダつきの同一 payload なら pytest で固定でき、
   判定基準を決定的に保てる（Phase 2・3 で単体を主軸にしてきた方針と同じ）。

**採らなかった案**:
- **仕様書どおりキューで分離する**（実運用では妥当。PoC では理由1 のとおり検証対象がぼやける）。
- **同一プロセスのまま、実行をスレッドに逃がす**（3 秒は守れるが、ack と実行の順序が
  観測しづらくなり、G-06 の「実行は 1 回だけ」をログで示しにくい）。
- **再送を `X-Slack-Retry-Num` の有無で弾く**（ヘッダに依存した防御になる。
  ヘッダが無い二重押下は素通りする。**冪等性はストアで担保すべきで、ヘッダは観測の材料に留める**）。

**影響**:
- Phase 5 で実行が実 API 呼び出しになるなら、**そこで分離の設計が要る**。
  本 PoC の構成をそのまま実運用に持ち込まないことを提言に明記する。
- ステートの語彙に `execution_failed`（確定的な失敗・再試行可）と
  `unknown`（実行有無が不明・再試行不可）を**到達しないまま定義しておく**
  （design.md 3.5.1）。タイムアウトした実行を一律に「失敗」として再試行可能にすると、
  非冪等な操作で二重実行を招く。語彙を後から足すと既存レコードの意味が変わるため、
  [D-023](#d-023-承認時に第3層へ再問い合わせせず-policy_override-として記録する) と同じ理由で先に決める。

## D-025 承認期限の判定を満了ジョブではなく承認の条件付き更新に含める

**日付**: 2026-10-01
**状態**: 採用（[phase4 design.md](phases/phase4-slack/design.md) 3.5 の改訂）

**文脈**:
design.md 3.5 のステート表は、有効期限の責務を満了ジョブ（`slack/expire.py`）に置いていた。
`pending` のまま `expires_at` を過ぎたエントリをジョブが走査して `expired` に遷移させる、
という素直な設計である。

実装して気づいたのは、**「期限は過ぎたが、ジョブがまだ掃いていない」窓で承認が通る**ことだった。
ジョブを数分おきに走らせる前提なら、その窓は数分ある。インシデント対応で承認が遅れて届くのは
まさにこの窓であり、**もっとも起こりやすいタイミングで期限が効かない**。

**決定**:
承認期限の判定を、承認の条件付き更新（CAS）と同じ 1 文に入れる。

```sql
UPDATE pending_actions SET status = 'approved', ...
 WHERE trace_id = ? AND status = 'pending' AND expires_at > ?
```

**却下は期限後も受け付ける。** 承認と却下を対称に扱わない。

満了ジョブの責務は「期限切れを**人間に知らせる**こと」（元メッセージの更新と二次エスカレーション）
に限定し、**承認可否の判定からは外す**。

**理由**:
1. **期限切れは満了ジョブの都合ではなく、承認可否の条件そのものである。**
   ジョブは「期限切れを人間に伝える」ために走るのであって、
   ジョブが走ったかどうかで実行してよいかが変わるのはおかしい。
2. **チェックと更新を分けると窓ができる。** 期限を見てから `UPDATE` する実装でも TOCTOU は残る。
   1 文に入れれば、窓は原理的に存在しない（T-03）。
3. **承認と却下は非対称である。** 人間が明示的に「やるな」と言う操作は、いつ押されても安全側に働く。
   対称に扱うと「期限が切れたので却下できません」という、安全性を下げる方向の挙動になる。
4. **同じ理由で、表示する期限も実効値にする必要がある。** 承認期限（TTL）と TOCTOU 閾値は
   独立に設定できるため、実効的な承認窓は**短いほう**で決まる。TTL 15 分を表示しながら
   TOCTOU 5 分で `stale` に倒れる状態を実機で踏んだ。表示は
   `min(承認期限, 提案時刻 + TOCTOU 閾値)` とする。

**採らなかった案**:
- **満了ジョブの実行間隔を短くする**（窓は縮むが消えない。間隔を 0 にはできない）。
- **`approve()` の中で期限を見てから `UPDATE` する**（理由2 のとおり窓が残る）。
- **却下も期限で弾く**（対称で実装は単純になるが、理由3 のとおり安全性を下げる）。

**影響**:
- ステート遷移の表（design.md 3.5）は「期限切れ = 満了ジョブの責務」ではなくなる。
  ジョブは**通知の責務だけ**を持つ。
- TTL と TOCTOU 閾値を 2 つの設定として残すなら、**表示は必ず実効値**にする（phase4 提言6）。
- Phase 5 で承認窓の意味が変わる（承認待ちのあいだにクラスタの状態が変わりうる）。
  TOCTOU 閾値を経過時間で測ることの妥当性は、実クラスタで再検討する。

## D-026 実行層を本物にする。破壊的操作の禁止は「実クラスタ」に限定する

**日付**: 2026-10-01
**状態**: 採用（[CLAUDE.md](../CLAUDE.md) の禁止事項の改訂）

**文脈**:
Phase 1〜4 の実行層は構造化ログを 1 行出すだけだった（`execute_dry_run()`）。
CLAUDE.md は「PoC では実際の破壊的操作を実行しない」と定めており、これは正しい規律として機能してきた。

しかしその結果、**到達できない領域が残った**。Handoff 仕様書の通知パターン5（実行時エラー・再試行）、
ステートの `execution_failed` と `unknown`、承認待ちの間に対象が変わる TOCTOU、
そして Phase 3 提言5 の「第3層が許可してもクラスタ側の RBAC が止める」。
いずれも Phase 4 の design.md が「実行層が dry-run のため注入できない」として明示的に先送りしている。

**決定**:
禁止の対象を**実クラスタ**に限定する。使い捨ての kind クラスタに対しては、実際に API を発行する。

- 対象は `kind create cluster` で作り、**`kind delete cluster` で丸ごと消せるもの**に限る。
- 既存クラスタへの接続は行わない。kubeconfig は検証用に生成したものだけを使う。
- 権限は ServiceAccount の RBAC で絞る（phase5 design.md 3.10）。クラスタ管理者権限では実行しない。
- `ProposedAction.dry_run` は **server-side dry-run** に対応づける。クライアント側で「送らない」のではなく、
  API サーバまで届けて認可と検証を通し、永続化だけさせない。

**理由**:
1. **「止めたこと」は 4 フェーズ分証明したが、「通したこと」は一度も証明していない。**
   実行層がログ 1 行である限り、`allow: true` の意味は「ログが出た」でしかない。
   多層防御の主張は、通したものが実際に効果を持つことと対になっていなければ成立しない。
2. **実行の失敗は、エラーを模擬しても再現できない種類の性質を持つ。**
   「実行されたかどうかが分からない」状態（[D-028](#d-028-実行結果を-3-分類し実行有無が不明なものを自動再試行しない)）は、
   モックでは「分からないふりをする」ことしかできない。実際に API サーバまで届いた上で
   クライアントが結果を知らない状態を作らないと、検証したことにならない。
3. **RBAC は模擬できない。** 「第3層が許可しても実行できない」という多層防御の最後の 1 枚は、
   本物の認可が拒否して初めて示せる。403 を自分で生成したら、それは自作自演である。
4. **壊すために作る環境なので、壊れてよい。** 元の禁止事項が守ろうとしていたのは
   「検証のために本番相当の資産を壊さないこと」であり、**使い捨てのクラスタはその対象ではない**。
   規律の意図を保ったまま、適用範囲を正確にする。

**採らなかった案**:
- **dry-run のまま Phase 5 を終える**（Phase 4 が先送りした項目がすべて未検証のまま残り、
  E2E フェーズの意味が「通しで流した」だけになる）。
- **実行層をモックサーバに向ける**（理由2・3 のとおり、検証したいものがちょうど落ちる。
  第1層の障害注入がモックで足りたのは、検証対象が「LiteLLM の挙動」だったためで、
  ここでの検証対象は「クラスタが実際にどうなったか」である）。
- **既存の開発クラスタを使う**（消せない。`kind delete cluster` で原状復帰できることが前提条件）。

**影響**:
- CLAUDE.md の「注意点」を改訂する。**実クラスタへの `kubectl delete` を発行しないことは変えない。**
- `assets/` に kubeconfig・ServiceAccount トークン・CA 証明書を貼らない運用が追加で必要になる
  （docs/README.md 運用ルール2 の Phase 5 版）。
- 終了コード 0 の意味が「dry-run ログまで到達」から「実クラスタで成功」に変わる。
  Phase 1〜4 の assets と終了コードを直接比較しない（phase5 design.md 3.12）。

**実測（2026-10-01）**: kind v0.33.0 / `kindest/node:v1.37.0`（ダイジェスト固定）で実施。
`kind delete cluster` → 再構築を**着手前に**確認した。server-side dry-run は `delete` にも効き、
`dryRun=All` で **200 が返り監査ログにも残る一方リソースは変化しない**（確認事項4）。
`dry_run` は Phase 2 から存在しながら 4 フェーズぶん意味を持っていなかったフィールドで、
ここで初めて実体を得た（phase5 result.md 考察6）。

## D-027 Slack の受信プロセスに実行権限を持たせない（受信と実行を分離する）

**日付**: 2026-10-01
**状態**: 採用（[D-024](#d-024-受信と実行を分けずslack-の再送を二重押下と同じ経路で弾く) の前提が崩れたことによる差し替え）

**文脈**:
[D-024](#d-024-受信と実行を分けずslack-の再送を二重押下と同じ経路で弾く) は受信（`slack/handler.py`）と実行を
同一プロセスに置いた。根拠は「実行層が dry-run ログ 1 行で、3 秒ルールに対して桁が 5 つ違う」ことであり、
**崩れる条件も同時に明示していた**（「実行が実 API 呼び出しになった時点で成立しなくなる」）。
[D-026](#d-026-実行層を本物にする破壊的操作の禁止は実クラスタに限定する) で実行が本物になり、その条件が満たされた。

Phase 4 の result.md 提言5 は、この結合をこう表現している。
**「承認ボタンを押せる = handler の権限で実行できる」**。

**決定**:
`slack/handler.py` は**ステートを進めるところまで**で終える。実行は独立した常駐プロセス
（`agents/executor.py`）が、ストアの `approved` を占有してから行う。

- **handler にクラスタの資格情報を与えない。** 構成だけでなく、`slack/handler.py` から
  `agents.execution` / `agents.k8s` / Kubernetes クライアントへの **import 経路が存在しないことを pytest で検査する**。
- executor は `approved` → `executing` の条件付き更新（CAS）で 1 件を占有してから実行する。
- **executor が実行中に落ちた場合、`executing` のまま残る。起動時にこれを `unknown` に倒す**
  （[D-028](#d-028-実行結果を-3-分類し実行有無が不明なものを自動再試行しない)）。`approved` に戻して再実行しない。
- 分離の手段は既存の SQLite のポーリングとし、キュー製品は導入しない。

**理由**:
1. **権限の結合は、3 秒ルールより重い問題である。** 3 秒ルールは遅延の問題だが、
   権限の結合は「インターネットから到達可能な HTTP エンドポイントを持つプロセスが、
   クラスタへの書き込み権限を持つ」という構成の問題である。署名検証を 1 つ間違えたときの
   被害範囲がまったく違う。
2. **分離することで、`executing` という観測可能な状態が生まれる。** 同一プロセスなら
   「実行したが結果を記録する前に落ちた」は追跡できない。ステートを挟むと、
   クラッシュリカバリが「`executing` のまま残っているものは不明」という 1 行の規則になる。
3. **実行の経路が 1 本になる。** 自律経路（`agents/main.py`）と承認・再試行経路（executor）は
   どちらも `agents/execution.py` の同じ関数を呼ぶ。handler がそこに加わらないことで、
   「実行」の意味を持つ場所が 2 つに固定される。
4. **[D-024](#d-024-受信と実行を分けずslack-の再送を二重押下と同じ経路で弾く) の冪等性の設計はそのまま生きる。**
   Slack の再送も二重押下もストアの CAS で弾く構造は変わらない。変わるのは CAS の後に何をするかだけである。

**採らなかった案**:
- **キュー製品（SQS 等）で分離する**（実運用では妥当。PoC では [D-024](#d-024-受信と実行を分けずslack-の再送を二重押下と同じ経路で弾く)
  の理由1 がそのまま残る。検証対象がキューの挙動に移る。置き換える条件は C-01 に書く）。
- **handler のまま実行し、スレッドに逃がす**（3 秒は守れるが、理由1 の権限の問題が一切解決しない）。
- **自律経路も executor 経由にする**（実行の入口が 1 つになり構造は綺麗だが、
  `agents/main.py` の終了コード 0 の意味が「キューに積んだ」に変わり、Phase 1〜4 のエビデンスと
  比較できなくなる。実装後に再評価する — phase5 design.md 未決事項12）。

**影響**:
- ストアのステートに `executing` が増える（既存の値の意味は変わらない）。
- 承認してから実行結果の通知が出るまでに、ポーリング間隔ぶんの遅延が入る。
- **executor が止まっていると、承認は成立するのに実行されない**（phase5 design.md N-03）。
  Slack 上は「承認済み」に見えるため、Phase 4 の N-02（受信の死活監視）と同じ種類の
  監視対象がもう 1 つ増える。

**実測（2026-10-01）**: 分離は権限のために選んだが、**付いてきたのは「落ちたことを観測できる」
という性質**だった（phase5 result.md 考察4）。X-04 で実行中の executor を `SIGKILL` したところ
エントリは `executing` のまま残り、再起動時に `unknown` へ倒れた。
同一プロセスのままなら、この窓は記録にすら現れない。
受信プロセスに kubeconfig が無い状態で承認が成立することも実機で確認した
（R-01 / R-02 / R-04 の `kubeconfig_in_receiver: false`）。

## D-028 実行結果を 3 分類し、実行有無が不明なものを自動再試行しない

**日付**: 2026-10-01
**状態**: 採用（[D-024](#d-024-受信と実行を分けずslack-の再送を二重押下と同じ経路で弾く) で定義だけした語彙の実装）

**文脈**:
Phase 4 はステートの語彙に `execution_failed`（確定的な失敗）と `unknown`（実行有無が不明）を
**到達しないまま**定義した。理由は「後から語彙を足すと既存レコードの意味が変わる」ことだった。
[D-026](#d-026-実行層を本物にする破壊的操作の禁止は実クラスタに限定する) で実行が本物になり、両方に到達する。

実装にあたって決めるべきは、**何をもってどちらに振り分けるか**である。
HTTP の慣習では 5xx は再試行可能とされるが、それは冪等な読み出しを前提にした慣習である。
`kubectl delete pvc` に対して同じ扱いをすると、**1 回目が成功していた場合に二重実行になる**。

**決定**:
分類は **「サーバからの応答があったか」だけ**で行う。操作の種類では分けない。

| 実行層から見えるもの | 解釈 | ステート | 自動再試行 |
| --- | --- | --- | --- |
| 2xx | 実行された | `executed` | — |
| 4xx | **実行されていない**（応答がそう示している） | `execution_failed` | しない（人間が押す） |
| 5xx | **不明** | `unknown` | **しない** |
| 応答なし（timeout / 接続断 / TLS エラー） | **不明** | `unknown` | **しない** |

- **`unknown` は終端とし、再試行ボタンを出さない。** 通知には「クラスタの実際の状態を人間が確認すること」とだけ書く。
- **接続拒否も `unknown` に倒す。** 「接続が拒否されたのだから届いていない」は多くの場合正しいが、
  クライアントは「接続前の失敗」と「送信後に切られた」を常に区別できるとは限らない。
- **操作ごとの冪等性で再試行可否を変えない。**

**理由**:
1. **誤りのコストが非対称である。** 過剰に `unknown` に倒すコストは「人間がクラスタを見に行く」だけで、
   逆の誤り（実行済みのものを再試行する）のコストは非冪等な破壊操作の二重実行である。
   非対称なコストに対しては、安定して重いほうを避ける。第3層の Fail-Closed
   （[D-015](#d-015-第3層は-fail-closed-としopa-の可用性対策を-poc-では採らない)）と同じ形の判断である。
2. **`unknown` に再試行ボタンを出すのは、パターン4 に承認ボタンを出すのと同じ誤りである。**
   評価できていない操作に承認ボタンを出さない（Phase 4 判定基準2）のと、
   実行有無が分からない操作に再試行ボタンを出さないのは、**まったく同じ構造の規律**である。
   どちらも、不確実性を UI で確実性に見せかける行為にあたる。
3. **操作ごとの冪等性を実行層や通知層に書くと、[D-021](#d-021-確認強度と承認権限を操作の種別で出し分けない) が禁じた形になる。**
   `if operation == "kubectl_delete_pvc"` を通知層に書いた時点で、ポリシーの語彙が漏れる。
   冪等性をポリシーとして持たせるなら Rego 側である（提言に書く）。
4. **分類の根拠を文字列解析に依存させない。** これが
   [D-030](#d-030-実行層は-kubectl-のサブプロセスではなく-kubernetes-api-クライアントで実装する) の理由でもある。

**採らなかった案**:
- **5xx を `execution_failed`（再試行可）にする**（HTTP の慣習どおりだが、理由1 のとおり
  非冪等な操作で二重実行を招く。慣習は冪等な読み出しを前提にしている）。
- **操作ごとに冪等性の表を持ち、冪等なものだけ自動再試行する**（理由3。
  加えて「冪等である」の判定自体が状況依存である — 同名のリソースが再作成されていれば
  `delete` は冪等ではない）。
- **`unknown` に対して自動で状態確認（read）を行い、実行有無を判定する**
  （読めた時点の状態が、実行の結果なのか第三者の操作の結果なのかを区別できない。
  判定できないものを判定したことにする実装は、[D-012](#d-012-validationerror-からの自動修復リトライを入れない) と同じ理由で採らない）。

**影響**:
- ステートに `abandoned`（実行を試みたあと人間が中止した）を足す。
  `rejected`（実行を試みていない状態での却下）と混ぜない。
- 終了コードに 6（確定的な失敗）と 7（実行有無が不明）を足す。**7 を最重とする。**
  唯一「今の状態が分からない」状態だからである。
- `EXECUTION_TIMEOUT_SECONDS` が **`unknown` の発生率を直接決める値**になる。
  これまでの層の `timeout` とは性格が違い、短すぎると実行されたものを「不明」と記録する。

**実測（2026-10-01）**: 「実行されたのに不明」が実例として出た。プロキシが上流へ要求を転送し、
API サーバが 200 を返して **Deployment の `generation` が 2 から 3 に変わった**うえで、
応答だけがクライアントに届かなかった（X-01b）。記録は `unknown`、終了コードは 7。
**5xx や無応答を「失敗・再試行可」としていたら、本番の Deployment を 2 回再起動していた。**

ただし design.md 3.11 が「もっとも重要な注入」とした X-01（タイムアウトを極小にする）は、
**設計どおりには効かなかった**。kind は localhost にあり実測の max が 20.9 ms のため、
それより短いタイムアウトは**リクエストが届く前に**切れる。
要るのは「早く諦めること」ではなく「送った後に切ること」だった（result.md 考察2）。

## D-029 再開はエージェントの思考ではなく、承認済みアクションの実行から行う

**日付**: 2026-10-01
**状態**: 採用（[D-001](#d-001-エージェントフレームワークを導入しない)「Phase 5 の設計時に再検討の余地あり」への結論）

**文脈**:
[D-001](#d-001-エージェントフレームワークを導入しない) はフレームワークを入れないと決め、
その影響として「Phase 5 の中断・再開は自前で状態を持つ必要がある」と書いた。
LangGraph を採らなかった案として挙げた際の利点も「中断・再開を状態機械として表現しやすい」だった。

Phase 5 でその宿題が来る。ただし**実際に必要なものを見ると、想定していたものと違っていた**。

**決定**:
「再開」とは、**承認済みアクションを実行すること**とする。エージェントの思考は再開しない。
**再開時に LLM を呼び直さない。**

- 中断 = エージェントのプロセスが終了すること（Phase 3 から不変）。
- 再開 = ストアの `event_json` から `ProposedAction` を復元し、第2層で再検証して実行すること。
- **検証可能な形にする**: 承認から実行までの間に、第1層へのリクエストが 1 本も出ていないことを
  LiteLLM 側のログで確認する（phase5 判定基準8）。

**理由**:
1. **再開時に LLM を呼ぶと、人間が承認した内容と実行される内容が変わりうる。**
   運用原則2（承認内容の同一性保証）は、ボタンの `value` を Trace ID だけに絞り、
   実行内容をストアから復元し、復元時に再検証する（[D-020](#d-020-承認内容はストアから復元し復元時に第2層で再検証する)）
   ところまで徹底している。その経路の末端で LLM に再生成させたら、徹底した意味がすべて消える。
2. **非決定性が戻ってくる。** [D-012](#d-012-validationerror-からの自動修復リトライを入れない)（`ValidationError` から再プロンプトしない）と同じ構造。
3. **思考の再開に必要な機構（チェックポイント・状態機械）は、この再開には要らない。**
   必要なのは「どのアクションを、どの状態まで進めたか」だけであり、**ストアの `status` 1 列で足りる**。

3 が [D-001](#d-001-エージェントフレームワークを導入しない) への回答である。
**checkpointer が解くのは「思考の再開」であって、本 PoC が必要としているのは「アクションの再開」である。**
両者は似た言葉だが、前者は非決定的な計算の途中状態を復元するもので、後者は確定した 1 件の実行を進めるものである。
フレームワークを入れていたら、**承認フローに非決定性を持ち込む選択肢がそこに存在してしまった**。

**採らなかった案**:
- **承認後に LLM へ「承認されたので実行してよい」と伝えて再計画させる**（理由1・2。
  人間が見た提案と実行されるものが別になりうる）。
- **承認前の文脈（messages）をストアに保存し、再開時に続きから推論する**
  （保存するものが増え、マスキングの対象も増える。そして理由1 は解決しない）。
- **LangGraph の checkpointer を導入する**（解いている問題が違う。C-03 で構造比較として記録する）。

**影響**:
- エージェントのマルチターン化・再計画は本 PoC のスコープ外であることが確定する。
- ストアに保存すべきものは `EscalationEvent`（提案 1 件）だけで足りる。会話履歴を持たない。
- **承認の意味が「このアクションを実行してよい」に限定される。**
  「この方針で続けてよい」という承認は本 PoC では表現できない。実運用でそれが必要になる条件は提言に書く。

**実測（2026-10-01）**: 実装に必要だったのはストアの `status` 列 1 つと、そこに `executing` を
足すことだけだった。会話履歴もチェックポイントも要らない。
[D-001](#d-001-エージェントフレームワークを導入しない) は自前実装を不採用の**代償**として
書いていたが、結論としては代償ではなかった。フレームワークを入れていたら
「承認後に再計画させる」という選択肢が存在してしまい、運用原則2 と正面から衝突していた
（result.md 考察11）。**選ばなかったことが設計を守った。**

## D-030 実行層は kubectl のサブプロセスではなく Kubernetes API クライアントで実装する

**日付**: 2026-10-01
**状態**: 採用

**文脈**:
第2層の `Operation` は `kubectl_get` / `kubectl_delete_pod` のように **kubectl のサブコマンド名**を語彙にしている。
素直に読めば実行層は `kubectl` をサブプロセスで起動すればよい。

一方、本フェーズの中心的な主張は
[D-028](#d-028-実行結果を-3-分類し実行有無が不明なものを自動再試行しない)
「実行されたかどうかが分かるか」であり、その判定材料が何から得られるかは設計の根幹になる。

**決定**:
Kubernetes の Python API クライアントを使う。`kubectl` のサブプロセス起動はしない。
`operation × kind` から API 呼び出しへのディスパッチは**表**で持ち、実行層に判定を書かない。

**理由**:
1. **失敗の分類が決定的になる。** HTTP ステータスがそのまま取れるため、
   [D-028](#d-028-実行結果を-3-分類し実行有無が不明なものを自動再試行しない) の 3 分類が
   文字列解析に依存しない。`kubectl` の終了コードと stderr を解析する実装にすると、
   「実行されたかどうか」という本フェーズの主張そのものが確率的になる。
   第2層で `strict=True` を選んだのと同じ理由である。
2. **コマンド文字列を組み立てずに済む。** Phase 4 で「提案アクションをシェルコマンド文字列として
   描画しない」と決めた（通知層の話だが、理由の半分は文字列化そのものにあった）。
   実行層でも、第2層を通った値とはいえ文字列結合を経路に挟まないほうがよい。
3. **server-side dry-run を引数として渡せる**（`dry_run="All"`）。
   フラグの付け忘れがコマンド文字列の組み立てミスとして起きない。

**採らなかった案**:
- **`kubectl` のサブプロセス**（理由1。加えて kubectl のバージョン差が検証の再現性に混ざる）。
- **`httpx` で API サーバを直接叩く**（部品は増えないが、認証・証明書・各リソースのパス組み立てを
  自前で持つことになり、そこのバグが実行結果の分類に混ざる。[D-001](#d-001-エージェントフレームワークを導入しない)
  の「切り分けを曖昧にする要素を排除する」はライブラリを使わないことを意味しない）。

**影響**:
- `requirements.txt` に Kubernetes の Python クライアントが増える。
- **`kubectl_describe` に対応する API が存在しない。** `describe` は kubectl がリソースと Event を
  取得して整形するクライアント側の機能である。read + Event で代替し、
  **語彙が kubectl のサブコマンド名に引きずられている**ことを限界として記録する。
  第2層のスキーマは変えない（変えると Phase 2・3 の fixture とエビデンスが無効になる）。
- **裏取りには `kubectl` を使う。** 実行には使わないが、クラスタ側の状態を層の外側から観測する手段としては使う
  （Phase 3 で `docker compose logs opa` を裏取りに使ったのと同じ位置づけ）。

**実測（2026-10-01）**: 失敗の分類が決定的になるという狙いは達成された（K-04 / K-05 が全件パス）。
副産物として、**`kubectl`（client-go）は平文 HTTP に Bearer トークンを送らないが、
Python クライアントは送る**ことが分かった（実行層の注入プロキシを作る過程で判明）。
同じクラスタに対する「クライアントの安全側の既定」が言語実装によって違う。

## D-031 通知パターン1 を、エージェント側の代替通知で埋める

**日付**: 2026-10-05
**状態**: 採用

**文脈**:
Handoff 仕様書の通知パターン1（インフラ全滅）は【独立経路】と定義されており、
Phase 4 ではスコープ外とした（[phase4 design.md 3.13](phases/phase4-slack/design.md)）。
理由は「エージェントはどのエンドポイントがどう落ちたかを原理的に知らないので、
ここから組み立てると持っていない情報を推測して書くことになる」。
LiteLLM Proxy 自身の `general_settings.alerting` が担うべきもの、とした。

Phase 5 の Z-05 は、その帰結を実測として記録している。
**第1層を全滅させると Slack に 1 件も出ない。** 多層防御のうち、唯一人間に届かない層である。

しかしこの PoC では **`general_settings.alerting` を一度も設定していない**（C-02 は構成の比較どまり）。
つまりパターン1 は「別経路が担う」のではなく、**どこにも存在しない空白**になっていた。

**決定**:
第1層の呼び出しが失敗したとき、エージェントがエスカレーションを 1 件出す。
これを**通知パターン1 の代替**と位置づける。新しいパターン番号は作らない。

- `EscalationEvent.kind` に `request_failed` を足す（第6の `kind`。パターン番号は増やさない）
- `--incident` 経路でのみ出す。`--prompt` 経路（Phase 1）では出さない
- **終了コードは 1 のまま**。第2層の `ValidationError` と分けない

**理由**:
1. **「書けない情報」と「書ける情報」が混ざっていた。** 3.13 が否定したのは
   「どのリージョンがどう落ちたか」という**基盤の状態**であり、これは今も書けない。
   一方「このインシデントは処理されなかった」は、エージェントが推測なしに持っている事実である。
   前者を理由に後者まで出さないことにしていた。
2. **送出経路は第1層に依存していない。** `escalate()` は Slack API を直接叩くだけで、
   LLM にも LiteLLM にも触れない。第1層が全滅していても動く。循環依存は無い。
3. **空白を空白のまま残していた。** 「別経路の責務」という整理は、その別経路が存在して初めて成立する。
   本 PoC では存在しなかったので、D-022 で最悪とした**「止まったことを誰も知らない」状態**が
   第1層にだけ残っていた。
4. **代替のほうが相関 ID で勝る。** C-02 の表で「LiteLLM の alerting はエージェントの `trace_id` を
   知らない」ことを問題として挙げていた。代替通知には `trace_id` が載る。

**採らなかった案**:
- **パターン1 として実装したと記録する**（文面の中身が別物なので、記録が実態より広くなる。
  下の「埋まらないこと」を併記したうえで「代替」と呼ぶ）。
- **新しい通知パターン6 を作る**（コードにパターン番号という実体は無く、持っているのは `kind` だけ
  （[blocks.py](../slack/blocks.py) の対応表にしか現れない）。仕様書に無い番号を増やすと、
  design.md 第0章の「仕様書の項目 → 扱う / 扱わない」の表に対応先の無い行ができる）。
- **終了コード 1 を 2 つに割る**（空いているのは 8 だけで、第1層の失敗は「実行していない」側の
  軽い失敗なのに `EXIT_EXECUTION_UNKNOWN = 7` より重くなる。「値が大きいほど重い」という
  [main.py](../agents/main.py) の規律に反する。1 と 2 の間に割り込ませると Phase 1〜5 の
  result.md と `scripts/e2e.sh` に記録済みの終了コードがすべてずれる。
  第1層か第2層かを区別したいだけなら、ログの `layer` / `kind` で足りる）。
- **LiteLLM の alerting を設定する**（排他ではない。**両方あってよい**。ただしそれは
  基盤の運用通知であって、インシデント 1 件が落ちたことの通知ではない。下の実測を参照）。

**埋まらないこと（代替であって同一ではない）**:
- **集約しない。** 障害中にインシデントが複数走れば、その件数だけ通知が出る。
  LiteLLM の alerting はデプロイ・モデル単位で集約する。
- **基盤の状態は言えない。** 言えるのは「この 1 件が処理されなかった」ことだけ。
  この制約は構造で担保している — 通知の文面は `RequestFailure`（例外の型と文字列）と
  イベントの値だけから組み立てており、**書く材料が無い**。
- **第1層が落ちている最中に Slack も落ちていれば、やはり誰にも届かない**（終了コード 5）。
  多層防御の最外周には、その外側が無い（[phase4 result.md 考察10](phases/phase4-slack/result.md)）。

**影響**:
- `EscalationEvent.kind` が 6 値になる。`_BUILDERS` との網羅性を pytest で強制する
  （足し忘れると送出の直前に `KeyError` で落ちる＝人間に届かない）。
- `call_llm()` の戻り値が `(content, ok)` から `(content, failure)` に変わる。
  **構造化ログは 1 バイトも変えていない**（`request.error` はそのまま。送出は `request.escalated` として足す）。
- スレッド返信の見出しを `*ValidationError の詳細:*` → `*失敗の詳細（全文）:*` にした。
  `errors` に第1層の例外も入るようになったため。**パターン2 の見た目が 1 箇所変わる。**
- Phase 5 の Z-05 は「1 件も出ない」という記録のまま残す（過去の観測は書き換えない）。
  新しい挙動は再実行して別の観測として追記する。

**実測（2026-10-05）**: 再実行で「1 件も出ない」→「1 件出る」を確認した
（[phase5 result.md の追記](phases/phase5-e2e/result.md)）。
終了コードは 1 のまま、承認ボタン無し、ストア未登録、クラスタ無変化。
送出も同時に落とすと終了コード 5 になる（DM 解決・投稿の両方で確認）。

比較のため、**採らなかった案に挙げた LiteLLM 自身の alerting も実際に動かした**（Z-05d）。
`general_settings.alerting` で `llm_exceptions` / `outage_alerts` が確かに飛ぶ。
そのうえで、両者の性質の違いが実測で出た。

| | エージェントの代替通知 | LiteLLM の alerting |
| --- | --- | --- |
| `trace_id` | 載る | **載らない**（本文は `model_group` / `deployment` / 例外文字列） |
| 粒度 | インシデント 1 件ごとに 1 通 | **集約される**（`[Num Alerts: 4]`） |
| マスキング | [`slack/masking.py`](../slack/masking.py) を必ず通る | **通らない。プロンプトの先頭 100 文字がそのまま載る** |

**3 行目は予期していなかった。** 採否は PoC の判定ではなく運用の設計判断だが、
少なくとも「alerting を入れれば基盤の通知は解決する」とは言えない。
`config.yaml` には入れず、[`litellm/config.alerting.yaml`](../litellm/config.alerting.yaml) に分けてある。
