# 設計判断ログ

採用した案と、検討して採らなかった案を、理由とともに記録する。追記のみ。
「なぜこの構成なのか」を後から説明できることが、この PoC の主要な成果物である。

書式: `## D-nnn タイトル` / 状態 / 文脈 / 決定 / 理由 / 採らなかった案 / 影響。

---

## D-001 エージェントフレームワークを導入しない

**状態**: 採用（2026-09-04）

**文脈**: エージェント本体を LangGraph 等のフレームワークで組むか、素の Python + OpenAI SDK で書くか。

**決定**: 素の Python + OpenAI SDK。LiteLLM Proxy に OpenAI 互換エンドポイントとして接続する。

**理由**: 本 PoC の検証対象は「各層が異常を検知・遮断すること」であって、エージェントの賢さではない。
フレームワークを挟むと、観測された挙動がフレームワークのリトライ・例外処理によるものなのか、
検証したい層によるものなのか切り分けられなくなる。層の責務を曖昧にする要素は排除する。

**採らなかった案**: LangGraph（Phase 5 の中断・再開を状態機械として表現しやすい利点はあるが、
上記の切り分け問題が上回る）。Claude Agent SDK（LiteLLM Proxy 経由のマルチデプロイ構成との相性が未確認）。

**影響**: Phase 5 の中断・再開は自前で状態を持つ必要がある。Phase 5 の設計時に再検討の余地あり。

## D-002 ポリシー判定を Pydantic ではなく OPA に置く

**状態**: 採用（2026-09-04）

**文脈**: 「本番環境での `kubectl delete pvc` を禁止する」判定は、Pydantic のカスタムバリデータでも書ける。

**決定**: 構造検証（第2層 / Pydantic）と権限判定（第3層 / OPA）を分離する。

**理由**: 「構造が正しい」と「内容が安全」は別の関心事。バリデータにポリシーを書くと、
ポリシーがアプリケーションコードに埋没し、監査もレビューも単体テストも困難になる。
Rego として外部化すれば `opa test` で単体テスト可能になり、ポリシーの変更がアプリのデプロイと切り離せる。

**採らなかった案**: Pydantic バリデータ内での判定（実装は最短だが、上記の監査性を失う）。

**影響**: OPA サーバというコンポーネントが1つ増える。エージェント → OPA は HTTP 呼び出しになるため、
OPA 自体の可用性が新たな単一障害点になる。この扱いは Phase 3 の設計で決める。

## D-003 フェイルオーバーを同一モデルのマルチ地理圏で構成する

**状態**: 採用（2026-09-04）

**文脈**: 第1層のフェイルオーバー先として、別プロバイダ / 同一プロバイダの別モデル / 同一モデルの別リージョンが候補。

**決定**: Amazon Bedrock 上の同一モデルを、複数の地理圏にまたがって配置する。

> **2026-09-04 修正**: 当初は「複数リージョン」としていたが、Bedrock の Claude は Claude 3 Haiku を除き
> 推論プロファイル経由でしか呼べず、単一リージョンを名指しする構成が取れないことが判明した（[D-008](#d-008-モデルは-claude-sonnet-4-6-を-jp--us-プロファイルで使う)）。
> 障害単位を**リージョンから地理圏へ**修正する。同一モデルであるという本項の主旨は変わらない。

**理由**: フェイルオーバー先でモデルが変わると、「応答品質が変わった」という交絡が入り、
可用性だけを純粋に検証できなくなる。同一モデルなら出力特性が保たれるため、
第2層以降の検証結果にフェイルオーバーの影響が混入しない。
また、リージョン障害は SRE として現実的かつ説明しやすい障害単位である。

**採らなかった案**:
- 別プロバイダ間（プロバイダ全断まで守れるが、モデルが変わるため上記の交絡が入る）
- 同一プロバイダの別モデル（キー1本で済むが同上）
- クラウド → ローカル（Ollama）（セットアップが重く、PoC の焦点がぼやける）

**影響**: プロバイダ全断のシナリオは本 PoC では検証しない。実運用化時に別プロバイダを
第3の fallback として積む余地は残す（LiteLLM の fallbacks はリスト指定なので拡張可能）。

なお調査の副産物として、Bedrock 上に OpenAI（`us.openai.gpt-5.6-*`）と xAI（`us.xai.grok-4.6`）の
モデルが提供されていることが判明した。**別ベンダーへのフォールバックが Bedrock 内で完結する**ため、
別クラウドのアカウントもキーも用意せずに config へ 1 エントリ追加するだけで実現できる。
Phase 1 のスコープは広げないが、Phase 5 の拡張余地として記録しておく。

## D-004 地理圏間のフェイルオーバーは AWS に任せず、LiteLLM 層で明示的に制御する

**状態**: 採用（2026-09-04） / 一部要調査

**文脈**: Bedrock 自体にもリージョンをまたいで推論をルーティングする仕組み（クロスリージョン推論プロファイル）があり、
これを使えば LiteLLM 側でフェイルオーバーを組まなくても、AWS 側でリージョンを跨いだ処理が期待できる。

**決定**: LiteLLM 層で明示的に primary / fallback を定義する。

**理由**:
1. **観測可能性**。AWS 側で自動ルーティングされると、いつどちらのリージョンが応答したかを
   アプリケーション側から確定的に観測しづらい。PoC は「フェイルオーバーしたことを証明する」のが目的であり、
   証明できない仕組みは検証にならない。
2. **プロバイダ非依存**。将来 Bedrock 以外を fallback に積む際、同じ仕組みで扱える。
3. **思想の一貫性**。第2層・第3層と同じく「エージェントの外側の、我々が制御できる層で守る」形になる。

**採らなかった案**: クロスリージョン推論プロファイルに委譲（運用は楽だが上記1が致命的）。

**調査結果（2026-09-04）**: 推論プロファイルは「使うかどうか選べるもの」ではなく、
Claude 3 Haiku を除く全 Claude モデルで**必須**だった。したがって本項の決定は
「プロファイルに委譲するか否か」ではなく「**プロファイルの地理圏をまたぐ部分を誰が制御するか**」の話になる。

決定自体は維持する。地理圏**内**のルーティングは AWS に委ね、地理圏**間**のフェイルオーバーを
LiteLLM が明示的に制御する。ただし理由の重心は変わった。AWS が `global.` プロファイルという形で
既に広範なフェイルオーバーを提供している以上、**第1層が可用性に対して追加する価値は限定的**であり、
第1層の本当の価値は観測可能性・ベンダー非依存性・第2層以降との一貫性にある。
この論点は Phase 1 の考察として result.md に記録する。

## D-005 障害注入はエラー応答のモックで行う

**状態**: 採用（2026-09-04）

**文脈**: 第1層の異常系をどう再現するか。API キー無効化 / 到達不能ホスト / ネットワーク遅延注入 / エラー応答のモックが候補。

**決定**: primary 側を、任意のステータスコードを返すモックエンドポイントに差し替えて障害を注入する。

**理由**: 429 / 500 / タイムアウトをエラー種別ごとに撃ち分けられ、再現性が高い。
LiteLLM のリトライ・フォールバック・クールダウンはエラー種別によって挙動が変わるため、
種別を制御できることが検証の前提になる。

**採らなかった案**:
- API キー無効化（手軽だが 401 認証エラーのみで、レートリミットやサーバ障害を再現できない）
- toxiproxy（最も実態に近いが、コンポーネントが増え PoC が重くなる。必要になった時点で追加）

**影響**: モックサーバというコンポーネントが1つ増える。配置場所は Phase 1 の設計を参照。

## D-006 障害注入サーバをルート直下の `mocks/` に置く

**状態**: 採用（2026-09-04）

**文脈**: D-005 で採用したエラー応答モックの実体をどこに置くか。当初合意したディレクトリ構成には該当する置き場がなかった。

**決定**: ルート直下に `mocks/` を追加し、`mocks/fault_injector.py` を置く。標準ライブラリのみで実装する。

**理由**: 障害注入は Phase 1 に限らず Phase 5 の E2E でも使う横断的な検証部品であり、
特定の層のディレクトリ（`litellm/` や `agents/`）に置くと所属が誤解される。
外部依存を持たせないのは、検証部品自体が壊れて検証がブロックされる事態を避けるため。

**採らなかった案**: `litellm/` 配下に同梱（LiteLLM の設定と検証部品が混ざる）、
FastAPI での実装（依存が増え、モックサーバ自体のセットアップが検証の障害になりうる）。

**影響**: ルート構成に `mocks/` が加わる。README とディレクトリ構成の記述を更新済み。

## D-007 リージョンとモデル ID は config に直書きし、環境変数には秘密情報だけを置く

**状態**: 採用（2026-09-04）

**文脈**: `litellm/config.yaml` のリージョン・モデル ID を環境変数化するか、直接書くか。

**決定**: リージョンとモデル ID は config に直書きする。環境変数は AWS クレデンシャルと master key のみ。

**理由**:
1. リージョンとモデル ID は秘密情報ではなく、むしろ**構成そのもの**なので、
   config を読めば primary / fallback の対応が一目で分かる状態が望ましい（監査性）。
2. LiteLLM の `os.environ/` 解決が `model` フィールドに対しても効くかは未確認であり、
   検証の本筋と関係ない不確実性を持ち込みたくない。
3. クロスリージョン推論プロファイル ID を使う場合、リージョンごとにプレフィックスが異なるため
   「1つの環境変数を両方で使い回す」構造がそもそも成立しない可能性がある。

**採らなかった案**: 全パラメータの環境変数化（上記2・3の不確実性を抱え込む）。

**影響**: リージョンを変える際は config.yaml と config.fault.yaml の両方を編集する必要がある。
PoC の規模では許容する。

## D-008 モデルは claude-sonnet-4-6 を `jp.` / `us.` プロファイルで使う

**状態**: 採用（2026-09-04）

**文脈**: Phase 1 実施手順1（モデルアクセス調査）の結果、以下が判明した。

- Bedrock の Claude で `ON_DEMAND`（基盤モデル ID の直接呼び出し）が可能なのは
  `anthropic.claude-3-haiku-20240307-v1:0` のみ。それ以外はすべて推論プロファイル必須。
- ap-northeast-1 には `jp.` プレフィックスの**日本国内限定プロファイル**が存在する。
- Sonnet 5 / Opus 5 / Fable 5 は東京では `global.` プロファイルしか無い。
- `claude-sonnet-4-6` は東京に `jp.`、us-east-2 に `us.` の両方が ACTIVE で存在する。

**決定**: `claude-sonnet-4-6` を採用し、primary を `jp.anthropic.claude-sonnet-4-6`（東京エンドポイント）、
fallback を `us.anthropic.claude-sonnet-4-6`（オハイオエンドポイント）とする。

**理由**:
1. **`global.` を避けられる。** `global.` プロファイルは AWS 側が全球ルーティングするため、
   `global.` → `us.` というフォールバックは US が global の部分集合となり、
   現実には起きない状況を検証することになる。`jp.` → `us.` なら包含関係がなく、構成として筋が通る。
2. **同一モデルを保てる。** 両者は同じ `claude-sonnet-4-6` であり、変わるのは推論の地理圏だけ。
   D-003 の主旨（応答品質の交絡を排除する）が維持される。
3. **実運用にそのまま使える。** 「日本国内で推論し、国内が捌けなければ US 圏へ退避する」は
   国内企業の本番構成として現実的で、データ所在の説明も付く。
4. **能力が十分。** Phase 2 の構造化 JSON 出力、Phase 3 の SRE 判断に耐える。

**採らなかった案**:
- **Sonnet 5**: 東京に `global.` しか無く、上記1の入れ子問題が起きる。
- **Claude 3 Haiku（ON_DEMAND）**: リージョン単位で 1 対 1 になり観測は最も厳密だが、
  Phase 2 以降の構造化出力が実運用と乖離し、PoC の結論の転用性が落ちる。
- **`global.` を 2 つのリージョンエンドポイントから叩く**: 障害単位が「リージョンエンドポイント」になり
  それ自体は成立するが、`jp.` / `us.` が使える以上こちらを選ぶ理由がない。
- **`apac.` プロファイル**: `claude-sonnet-4-6` には存在しない（`apac.` があるのは Claude 3 系と Sonnet 4）。

**影響**:
- 地理圏**内**のどの物理リージョンが応答したかは観測できない。判定基準は
  「`jp.` デプロイと `us.` デプロイのどちらが応答したか」で満たす（design.md 第5章・第6章）。
- コストを抑えたい場合は `claude-haiku-4-5-20251001-v1:0` が同じく `jp.` / `us.` の両方を持つため、
  config の 2 行を書き換えるだけで差し替えられる。

## D-009: 第1層の判定エビデンスは「LiteLLM のヘッダ」と「障害注入側のアクセスログ」の2系統で取る

**日付**: 2026-09-29
**状態**: 採用

**背景**:
design.md 第6章は「確実に取得できる手段を最低1つエビデンスとして採用する」としていたが、
Phase 1 の F-04 で **`x-litellm-attempted-retries` が実際には 2 回リトライしているのに 0 を返す**
ことが判明した（[phase1 result.md](phases/phase1-litellm/result.md) 考察1）。
ヘッダだけを信じると「リトライは起きていない」と誤った結論に至る。

**決定**:
第1層の検証エビデンスは以下の 2 系統を必須とする。

1. **LiteLLM のレスポンスヘッダ** — `x-litellm-model-id`（どのデプロイが応答したか）と
   `x-litellm-attempted-fallbacks`（フォールバックの有無）。
2. **障害注入側のアクセスログ** — primary が実際に何回叩かれ、どのステータスを返したか。

**理由**:
- 1 は「結果」しか語らない。primary が試行されずに fallback へ直行した場合と、
  試行して失敗した場合を区別できない。
- 2 がなければ、シナリオ間で Router の cooldown 状態が持ち越されて
  「500 を一度も発生させていないのにフォールバックした」ログを正しい結果と誤認する
  （実際に F-01 → F-02 で発生させてしまった）。
- `mocks/fault_injector.py` は障害注入装置であると同時に**観測装置**として位置づける。

**影響**:
- 各シナリオの前に `docker compose restart litellm` を挟み、Router の内部状態を初期化する。
  これを検証手順に明記する。
- `x-litellm-attempted-retries` はエビデンスとして使わない。
- `GET /health` もエビデンスとして使わない。推論が全滅している状態で
  `unhealthy_count: 0` を返すことを実測した。
- Phase 3（OPA）以降も、層の内部状態を持つコンポーネントを検証する際は
  同じくリセット手順と「層の外側からの裏取り」を組み込む。

## D-010 第2層はインプロセスのライブラリとして実装し、HTTP 境界を持たせない

**日付**: 2026-09-29
**状態**: 採用

**文脈**: [architecture.md](architecture.md) の設計原則2 は「層をまたぐデータは JSON、層の実装は互いに import しない」
と定めている。これを字義どおりに読むと、第2層（Pydantic）もエージェントから import できず、
第1層・第3層と同じく独立したサービスとして立てる必要があるように見える。
Phase 2 の着手前にこの解釈を確定させる必要があった。

**決定**: 第2層はエージェントと同一プロセスで動くライブラリとする（`agents/schemas.py` + `agents/validation.py`）。
`docker-compose.yml` に第2層のコンテナは置かない。設計原則2 の「互いに import しない」は
**第1層・第3層の実装コードを import しない**という意味であり、第2層には適用しない。

**理由**:
1. **Pydantic はライブラリであって、サービスとして切り出す意味がない。** 検証は純関数であり、
   ネットワーク越しにしても得られるものは無く、レイテンシと障害点だけが増える。
2. **「層自体のダウン」という障害モードを持たないことが第2層の性質である。** 第1層は別プロセス、
   第3層は HTTP 越しなので層そのものが落ちうるが、第2層はエージェントが動いていれば必ず動く。
   この非対称性は隠さず、設計の帰結として明示する（Phase 2 design.md 2.1 の比較表）。
3. **境界は import の有無ではなくデータの形で担保する。** 層をまたぐデータは Pydantic モデル
   （= JSON 化可能な構造）に限り、第2層は第1層・第3層の実装を一切知らない。
   入力は `str | None`、出力は型付きオブジェクトであり、この契約は HTTP 境界がなくても成立する。

**採らなかった案**:
- **第2層を独立したバリデーションサービスにする**（原則2 の字義には最も忠実だが、
  検証したい対象（構造保証が決定的に働くこと）に何も足さず、HTTP という新たな失敗要因を持ち込む）。
- **第2層を第3層（OPA）に寄せて Rego でスキーマ検証まで行う**（層が 1 つ減るが、
  [D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) の分離を逆方向に崩す）。

**影響**:
- Phase 2 の異常系は「層の障害」ではなく「**入力の異常**」の注入になる。Phase 1 とシナリオ設計の性質が異なる。
- [D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る)
  の「層の外側からの裏取り」は第2層には原則として不要（入力と出力を我々が完全に握っているため）。
  ただし第1層を経由する経路検証では、第1層側の裏取りが引き続き必要。
- 第3層の可用性が単一障害点になる問題（[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) の影響欄）は、
  第2層には存在しない。Phase 3 でこの非対称性を踏まえて設計する。

## D-011 構造化出力の強制を第2層の代替としない

**日付**: 2026-09-29
**状態**: 採用

**文脈**: Bedrock / LiteLLM 側には `response_format`（JSON スキーマ指定）や tool use によって
モデル出力の構造を強制する仕組みがある。これを使えば壊れた JSON は出てこなくなり、
第2層は不要ではないか、という問いが当然出る。

**決定**: Phase 2 のベースラインは**プロンプトによるスキーマ提示のみ**とし、構造化出力の強制は使わない。
強制を入れた場合との比較は独立したシナリオ（C-01）として実施し、考察材料に留める。

**理由**:
1. **強制は「確率を下げる対策」であり、「決定的に遮断する仕組み」ではない。**
   本 PoC の主張は後者であり（[architecture.md](architecture.md) 脅威モデル）、
   前者で後者を置き換えたら主張そのものが崩れる。
2. **強制では原理的に守れない異常が残る。** フィールド間の相互依存（`kubectl_scale` なのに
   `replicas` が無い）、語彙の逸脱、そして「構造は正しいが内容が危険」は
   スキーマ強制の外側にある。第2層は落とし、第3層に渡すべきものは渡す必要がある。
3. **ベースラインに強制を入れると、検知能力が測れない。** 壊れた入力が来ないなら
   第2層が壊れた入力を止められるかは検証できない。検証のためには壊れた入力が届く構成が必要。
4. **プロバイダ依存を持ち込まない。** 強制の可否と挙動はモデル・プロバイダごとに異なる。
   第1層でベンダー非依存性を確保した（[D-004](#d-004-地理圏間のフェイルオーバーは-aws-に任せずlitellm-層で明示的に制御する)）のに、
   第2層の前提をプロバイダ機能に寄せるのは一貫しない。

**採らなかった案**:
- **ベースラインで強制を有効にする**（実運用の通過率は上がるが、上記 1〜3 により検証が成立しない）。
- **強制を一切扱わない**（提案として弱い。「なぜ強制で足りないのか」に答えられる必要がある）。

**影響**: 実運用への提言では「強制と第2層は排他ではなく併用する」形になる。
強制で構文レベルの異常の発生率を下げ、それでも通る異常を第2層が決定的に止める。
この二段構成の妥当性は Phase 2 の result.md で C-01 の結果とともに述べる。

## D-012 `ValidationError` からの自動修復リトライを入れない

**日付**: 2026-09-29
**状態**: 採用

**文脈**: 第2層で構造破壊を検知したとき、エラー内容をプロンプトに戻して LLM に再生成させる
「修復リトライ」は実装が容易で、実運用では通過率を大きく上げる。これを PoC に入れるか。

**決定**: 入れない。`ValidationError` は即座にエスカレーションイベントとなり、人間へのハンドオフに向かう。

**理由**:
1. **修復が成功すると「検知の決定性」が測れなくなる。** 判定基準は「壊れた入力が必ず止まること」であり、
   リトライを挟むと最終結果が確率的になり、何を証明したのか言えなくなる。
   [D-001](#d-001-エージェントフレームワークを導入しない) でフレームワークを排した理由と同じ構造の問題である。
2. **`x-litellm-attempted-retries` の教訓**（[D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る)）。
   層が自分の内部でリトライすると、外から見た挙動と内部の実態が乖離する。
   第1層で既に経験した混乱を第2層で再現する必要はない。
3. **リトライ回数・打ち切り条件・コストという新たな設計事項が発生する。** Phase 2 の検証対象ではない。

**採らなかった案**: 1 回だけの修復リトライ（実運用では妥当な設定だが、上記 1 により PoC のベースラインには置けない）。

**影響**: PoC では第2層の失敗が即ハンドオフになるため、実運用よりエスカレーション頻度が高く出る。
「修復リトライを 1 回入れる」は実運用への提言として result.md に書く。
その際、修復リトライは**第2層の内側ではなくエージェント側のループとして置く**（層の責務を汚さない）ことを併記する。

## D-013 第2層は役割名 JSON Validator で呼ぶ（実装名で呼ばない）

**日付**: 2026-09-29
**状態**: 採用

**文脈**: 第2層をこれまで「Pydantic」と呼んでいた。第1層「LiteLLM」・第3層「OPA」と並べると
統一されて見えるが、第2層だけは**層の名前が実装ライブラリの名前になっている**。
Phase 2 の実装に入る前に呼称を確定させる必要があった。

**決定**: 第2層は役割名 **JSON Validator** で呼ぶ。実装は Pydantic v2 のままとし、
実装名は「実装」として併記する。第1層・第3層は製品名（LiteLLM / OPA）で呼び続ける。

**理由**:
1. **検証対象が実装固有ではない。** Phase 2 の判定基準は「構造破壊を決定的に検知し、
   理由を特定できること」であり、Pydantic 固有の何かではない。strict な JSON スキーマ検証ができれば
   他の実装でも成立する。層の名前が実装名だと、結論が Pydantic の話に見えてしまう。
2. **[D-011](#d-011-構造化出力の強制を第2層の代替としない) との整合。** 「第2層の前提をプロバイダ機能に寄せるのは一貫しない」と書いた直後に
   層をライブラリ名で呼んでいるのは、その主張を弱める。
3. **提案としての強度。** 「Pydantic で守る」は実装の話、「JSON Validator 層を置く」は設計の話である。
   本 PoC の成果物は後者でなければ転用が効かない。

**第1層・第3層を製品名のままにする理由**（対称にしない判断）:
検証対象の性質が実際に非対称である。第1層で得た知見は Router の cooldown、
`x-litellm-attempted-retries` の不正確さ、ヘッダによる観測といった**LiteLLM 固有の事象**であり
（[D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る)）、
第3層の成果物は Rego ポリシーそのものである（[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く)）。
これらは製品名で呼ぶ方が実態に合う。第2層だけが実装に依存しない層であり、
呼称の非対称性はその違いをそのまま反映したものである。

**採らなかった案**:
- **全層を役割名に統一する**（Model Gateway / JSON Validator / Policy Engine）。
  見た目は最も整うが、上記のとおり第1層・第3層では製品固有の知見が検証結果の本体であり、
  役割名にすると何を検証したのかが曖昧になる。完了済みの Phase 1 の result.md と
  エビデンス全体の書き換えも必要になる。
- **「構造検証層」など日本語の役割名にする**（識別子（`layer2_json_validator`）と表記が揃わない）。

**影響**:
- ドキュメントの呼称を「第2層 (JSON Validator)」に統一した（README / CLAUDE.md / architecture.md /
  TODO.md / Phase 2 の design.md・result.md）。「Pydantic」の記述は**実装固有の挙動を指す箇所だけ**に残す
  （`strict=True` の効き方、`model_validate_json()` の例外正規化など）。
- `EscalationEvent.layer` の値は `layer2_pydantic` → **`layer2_json_validator`**。
- **D-001〜D-012 の既存記述は変更しない。** decisions.md は追記のみの運用であり
  （[docs/README.md](README.md) 運用ルール3）、過去の判断の文面を後から書き換えると
  「いつ何を決めたか」が追えなくなる。[D-002](#d-002-ポリシー判定を-pydantic-ではなく-opa-に置く) のタイトルなど、
  既存エントリに残る「Pydantic」は第2層の読み替えとして扱う。
- ディレクトリ名 `docs/phases/phase2-pydantic/` は**変更しない**。
  `phase1-litellm` / `phase3-opa` と同じく実装で場所を示す命名であり、
  層の呼称とは別の関心事である。完了済み Phase 1 の result.md からの相互リンクも壊さずに済む。

## D-014 異常系の検証では「障害注入が効いていること」を層の外側から必ず確認する

**日付**: 2026-09-29
**状態**: 採用

**文脈**:
Phase 2 の R-01（第1層が 200 を返し、content だけが壊れている経路）の初回実行で、
10 シナリオすべてが終了コード 0 になった。原因は第2層ではなく
**fault-injector コンテナが起動していなかった**ことで、primary が接続不能になった結果
第1層が実 Bedrock にフォールバックし、**正常なアクションが返って検証が通過**していた
（[phase2 result.md](phases/phase2-pydantic/result.md) 考察3）。

[D-009](#d-009-第1層の判定エビデンスはlitellm-のヘッダと障害注入側のアクセスログの2系統で取る) は
「層が自己申告する値を鵜呑みにしない」ための 2 系統化だった。今回起きたのはそれとは別の失敗で、
**注入したはずの異常が届いていない**という、検証の前提そのものが崩れるパターンである。

**決定**:
異常系シナリオでは、判定の前に以下を必ず確認する。確認できないシナリオは結果を採用しない。

1. **障害注入コンポーネントが稼働していること**（コンテナの状態）。
2. **注入した異常が実際にエージェントまで届いたこと**（injector のアクセスログに該当リクエストがある）。
3. **フォールバック等で別経路に逃げていないこと**（`x-litellm-attempted-fallbacks` / `x-litellm-model-id`）。

**理由**:
- **注入の失敗は「エラー」ではなく「成功」として現れる。** テストが落ちるなら気づけるが、
  このケースは全件が正常終了する。何も表示されないことが症状なので、能動的に確認するしかない。
- **多層防御では、上位層が下位層の障害注入を打ち消しうる。** 第1層のフォールバックは
  可用性のための正しい挙動であり、同時に「第2層に壊れた入力を届ける」という意図を無効化する。
  層を重ねるほどこの干渉は起きやすくなる。
- 検証の結論が「合格」で揃っているときほど疑う必要がある。

**採らなかった案**:
- **障害注入時はフォールバックを無効にする**（干渉は消えるが、本番に近い構成から離れる。
  また「第1層が何もしていないこと」を示せなくなり、Phase 2 の判定基準3 が検証できない）。
- **エージェント側で注入状態を検知する**（設計原則1「エージェントは自分が守られていることを知らない」に反する）。

**影響**:
- Phase 3 以降の design.md には、シナリオごとに「注入が効いていることの確認手段」を明記する。
- Phase 3 では、OPA の `allow` がポリシー評価の結果であって
  デフォルト値やエラーの握り潰しでないことを、層の外側から裏取りする手順を入れる。
- 検証スクリプトは、注入コンポーネントの稼働確認に失敗したらそのシナリオを
  **無効として明示的に記録する**（黙って続行しない）。
