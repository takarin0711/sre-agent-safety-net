# 検証の規律

Phase 1〜5 で実際に踏んだ失敗から得た知見を、**テーマごとに**集約したもの。
フェーズ別の記述は各 `phases/phaseN-*/result.md` の「考察」が一次情報で、ここはその横断インデックス。

各項目の末尾の `(P1)` 等は、それを踏んだフェーズ。

---

## 検証が静かに正常系になる

**偽の合格を作る失敗。このリポジトリで最も多く踏んだ種類。**

- **障害注入が効いていないと、検証は黙って正常系になる。** injector が起動せず第1層が実 Bedrock に
  フォールバックし、R-01 の全シナリオが終了コード 0 になった。異常系では「注入が届いたこと」を
  層の外側から必ず確認する（[D-014](decisions.md)）。 (P2)
- **確認は「注入器が動いているか」では足りない。** リクエストが実際にその経路を通ったこと
  （`x-litellm-model-id` / 直叩きの生応答）で確認する（[D-018](decisions.md)）。
  注入の失敗は偽の合格にも**偽の不合格**にもなる。どちらに転ぶかは運である。 (P3)
- **上位層の正しい挙動が、下位層の障害注入を打ち消す。** 第1層のフォールバックは可用性としては正しく、
  同時に「第2層に壊れた入力を届ける」意図を無効化する。層を重ねるほどこの干渉は起きやすい。 (P2)
- **揃いすぎた結果は検証の失敗を示唆する。** 権限表の生成スクリプトが全件 `no` を返していた
  （zsh は未クォートの変数を単語分割しない）。 (P5)
- **検証ハーネスが層の判定を取り違える。** E2E 用スクリプトに足した ERR トラップが、
  エージェントの終了コードを捕まえる前に `PIPESTATUS` を上書きし、第3層の `deny`(3) を
  「通過」(0) と報告した。**第3層は正しく止めていて、Slack にも届いていた。**
  嘘をついたのは観測側である。層の出力を加工して受け取る場所は、それ自体が検証対象になる。 (P5)

> **全部合格しているときほど疑う。**
> **層の判定と、それを読み取った値が一致していることまで確認する。**

## 層が自己申告する値を信じない

- **`x-litellm-attempted-retries` は嘘をついた。** 実際に 2 回リトライしていても 0 を返した。
  層の外側（障害注入側）からの裏取りと 2 系統で判定する（[D-009](decisions.md)）。 (P1)
- **ヘルスチェックは可用性の指標にならない。** 推論が全滅していても `unhealthy_count: 0` が返る。
  各層の健全性は実リクエストの成否で測る。 (P1)
- **Slack は失敗しても HTTP 200 を返す**（`ok:false`）。第3層の X-04 と同じ形の罠。
  `slack_sdk` が例外に変換するのを握り潰さないこと。 (P4)
- **OPA の応答も無検証で信じない。** `allow` の型不一致・未知のキー・自己矛盾は
  すべて評価不能に倒す（[D-017](decisions.md)）。 (P3)

## 層の状態と設定

- **層の内部状態はシナリオ間で持ち越される。** LiteLLM Router の cooldown で実際に結果が汚染された。
  状態を持つコンポーネントを検証するときは、シナリオごとのリセット手順を必ず組み込む。 (P1)
- **`docker compose restart` は設定を切り替えない。** コンテナを作り直さないため `command` の
  `${LITELLM_CONFIG_FILE}` も環境変数も古いままになる。設定変更は **`up -d --force-recreate`**、
  `restart` は状態の初期化にのみ使う。 (P3)
- **エビデンスのファイル名は使い回さない。** Phase 1 でブロッカー時のログを後の成功ログで上書きした。 (P1)
- **自動修正ツールは規律を読まない。** `ruff --fix` が「改修しない」と定めた `mocks/fault_injector.py` を
  書き換えていた。変更禁止のファイルを機械的な処理の範囲に入れない運用が要る。 (P5)

## 層が何を検証できないか

各層の限界。ここを上位層で埋めようとすると責務境界が崩れる（[D-002](decisions.md)）。

- **Rego の undefined は allow 側に倒れる。** 必須フィールドが欠けた入力はルールが発火せず通る。
  第2層が先に立っているのは安全上の必要条件であり、整理のための並びではない。
  だからといって Rego に構造検証を書かない。 (P3)
- **第3層は input の真正性を検証できない。** environment と namespace を揃えて詐称されると通る。
  第3層が評価しているのは「エージェントの自己申告」である。 (P3)
- **構造的に正しく意味的に危険な入力は、第2層を通過する**（N-01）。これは欠陥ではなく責務境界の証明。
  ここで止めると第2層がポリシー判定を始めたことになる。 (P2)
- **ポリシーを独立に変更できるということは、独立に壊せるということでもある。**
  `opa/data.json` の 1 行で本番 Pod の削除が `allow: true` になり、止めたのは RBAC だけだった。 (P5)
- **構造化出力の強制は「弱められたスキーマ」しか強制できない。** Bedrock は `minimum` / `maximum` /
  `minLength` / `maxLength` / `pattern` を受け付けない。第2層のスキーマを正本とし、
  強制側はそこから劣化させたコピーとして扱う（[D-011](decisions.md)）。 (P2)
- **「実行されたのに不明」は実在する。** 上流が 200 を返して `generation` が変わったのに
  応答だけが届かない状態を実機で作れた。5xx や無応答を「失敗・再試行可」としていたら二重実行していた
  （[D-028](decisions.md)）。 (P5)

## 実装上の落とし穴

- **Pydantic の strict モードは JSON 入力と Python 入力で挙動が違う。** `model_validate(dict)` は strict だと
  enum に実インスタンスを要求し、素の文字列は `is_instance_of` で落ちる。
  第2層の入口は必ず `model_validate_json()` を通す（`json.loads()` を挟まない）。 (P2)
- **`timeout` を決めるのは出力トークン数の上限であり、それはスキーマの `max_length` で決まる。**
  スキーマを変えたら第1層の `timeout` を見直す（L-01 で 30 → 60 に再決定）。 (P2)
- **`timeout` の決め方は層によって難易度が違う。** 第3層は定常 4 ms 台で `timeout: 3.0` の
  52 倍の余裕があり、実測した結果「変える必要がない」が結論になった。規律は同じでも結論は同じとは限らない。 (P3)
- **Slack は Block Kit の上限超過を黙って切らず `invalid_blocks` で拒否する。**
  切り詰め（`slack/blocks.py` の `truncate()`）は表示の都合ではなく**送出できるかどうか**であり、
  無ければ長い `reason` で通知が全損する。 (P4)
- **`load_kube_config()` を引数なしで呼ぶと kind の admin が拾われる。** RBAC で止まるはずの操作が
  全部通る。専用の `K8S_KUBECONFIG` が未設定なら実行しない。 (P5)
- **bash の ERR トラップは `set +e` でも発火し、トラップ内のコマンドが `PIPESTATUS` を上書きする。**
  `cmd | tee log` の次行で `${PIPESTATUS[0]}` を読む構造では、トラップを外さないと必ず 0 になる。
  **終了コードが分岐そのものである場所では、捕捉区間だけトラップを外す。** (P5)
- **`set -e` + `pipefail` の下では、空振りする `grep` がスクリプトを無言で殺す。**
  ログの出力待ちループで `url="$(grep ... | head -1)"` と書くと、1 周目で終了する。
  待ち合わせの中の `grep` には `|| true` を付ける。無言終了は原因を最も追いにくい失敗である。 (P5)

## 検証環境の作り方

- **押してみなければ出ない不備がある。** 単体テストが全件通った状態で、実機の押下により 4 件出た。
  いずれも「1 回の押下」ではなく**押下と状態の関係**（表示と判定の食い違い、拒否時の応答、
  監査の欠落、期限の窓）に関する不備だった。単体テストは状態を自分で作ってから押すので気づけない。 (P4)
- **検証環境を「楽な形」にすると、障害の発生箇所が動く。** DM にしたことで `conversations.open` が
  1 段増え、E 系で最初に失敗したのは `chat.postMessage` ではなくそこだった。
  同じ理由で `chat.postEphemeral` が DM では使えない（RBAC 拒否が本人に届かない）。 (P4)
- **ローカルで検証すると再現しにくくなる障害がある。** kind は localhost にあり実測 max 20.9 ms なので、
  タイムアウトを縮めても**リクエストが届く前に**切れる。要るのは「早く諦めること」ではなく「送った後に切ること」。 (P5)
- **検証の大半はトンネル無しで回せる。** 署名を自前で計算して `/slack/events` に直接 POST すれば、
  handler の検証経路はそのまま通る。ngrok / cloudflared が要るのは
  「人間が実際に押す」ことを見るシナリオだけ。 (P4)
- **人間の操作を待つ検証は、無音にしてはいけない。** ステート遷移を「変化したときだけ」表示すると、
  承認待ちの間が完全に無音になり、固まっているのか待っているのかが区別できない。
  待ち合わせには残り時間のハートビートを出す。 (P5)
- **実行直後のスナップショットは中途半端な状態を写す。** `rollout restart` の発行から 2 秒後では
  Rolling Update の途中で、新旧の Pod が同時に見える。「実行後」を記録するなら収束を待つ。 (P5)
- **送出の失敗は残るが、受信の失敗は何も残らない。** handler が落ちていると押下の事実が
  監査ログにすら載らない（N-02）。承認待ちの監視は Slack ではなくストア側で行うしかない。 (P4)
