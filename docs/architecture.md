# 全体設計

## 前提とする脅威モデル

このシステムが守ろうとしているのは「LLM が賢くないこと」ではなく、**LLM が確率的であること**である。
どれだけプロンプトを作り込んでも、以下は一定確率で発生し続ける。

| 想定する事象 | 具体例 | 従来のプロンプト改善で防げるか |
| --- | --- | --- |
| LLM 呼び出しの失敗 | プロバイダ障害、レートリミット、リージョン障害 | 防げない（外部要因） |
| 出力構造の破壊 | JSON に自然言語が混入、クォート閉じ漏れ、必須キー欠落 | 確率を下げられるが 0 にはできない |
| 危険な操作の提案 | 本番環境への `kubectl delete pvc` を「妥当」と判断する | 確率を下げられるが 0 にはできない |

いずれも「発生確率を下げる」対策ではなく、**発生を前提に決定的な仕組みで遮断する**方針をとる。
確率的な部品（LLM）を、決定的な部品（Proxy / 型検証 / ポリシーエンジン）で挟み込むのが本 PoC の主張である。

## 設計原則

1. **エージェントは自分が守られていることを知らない。**
   フェイルオーバーもポリシー判定も、エージェントのプロンプトとコードの外側で完結させる。
   エージェント側に「フェイルオーバーしてください」「危険なコマンドは避けてください」と書いた時点で、
   その防御は確率的なものに退化する。
2. **各層は単独で無効化・差し替え・テストできる。**
   層をまたぐデータは JSON、層の実装は互いに import しない。
3. **拒否は必ず理由とセットで返す。**
   `allow: false` だけでは人間が判断できず、エスカレーションが機能しない。
4. **安全網の限界を明示する。**
   どの層も突破された場合、あるいは全層が機能しない場合に何が起きるかを設計に含める。
   「全部の系が落ちたら明示的にエラーを返して止まる」ことも検証対象である。

## 層構成

```
   ユーザ入力
       │
       ▼
┌───────────────┐
│  SRE Agent    │  LLM に「何をすべきか」を考えさせる。ここだけが確率的。
└───────┬───────┘
        │
  ┌─────▼──────────────────────────────────────┐
  │ 第1層  LiteLLM Proxy         [可用性]       │
  │  論理モデル名 → 実デプロイの解決とフェイルオーバー │
  └─────┬──────────────────────────────────────┘
        │ LLM 出力（生テキスト / JSON 文字列）
  ┌─────▼──────────────────────────────────────┐
  │ 第2層  Pydantic              [構造保証]     │
  │  スキーマに合致しない出力を ValidationError 化  │
  └─────┬──────────────────────────────────────┘
        │ 検証済みアクション（型付きオブジェクト）
  ┌─────▼──────────────────────────────────────┐
  │ 第3層  OPA / Rego            [権限判定]     │
  │  実行してよいかを決定的に判定                  │
  └─────┬──────────────────────────────────────┘
        │ allow: true
        ▼
    実行層（PoC ではログ出力 / dry-run のみ）

  いずれかの層で異常 ──▶ エスカレーション層  Slack Handoff
                          Block Kit で人間に提示し、承認 / 却下 を待つ
```

## 層の責務と境界

| 層 | 入力 | 出力 | 責務 | 責務でないもの |
| --- | --- | --- | --- | --- |
| 第1層 | OpenAI 互換のリクエスト | OpenAI 互換のレスポンス | LLM 呼び出しを成功させる | 中身の妥当性 |
| 第2層 | LLM 出力の文字列 | 型付きオブジェクト or `ValidationError` | 構造が仕様どおりであることの保証 | 内容が安全かどうか |
| 第3層 | 型付きオブジェクト | `allow` + 理由 | 実行してよいかの判定 | 実行そのもの |
| エスカレーション | 各層の失敗イベント | 人間の判断（承認 / 却下） | 人間への引き渡しと結果の受け取り | 自動的な回復 |

**第2層と第3層の分離が重要**である。「構造が正しいこと」と「内容が安全なこと」は別の関心事であり、
Pydantic のバリデータに `kubectl delete` の禁止を書き始めた時点で、
ポリシーがコードに埋没して監査もテストも不可能になる。ポリシーは Rego として外に出し、
`opa test` で単体テストできる状態を保つ。

## 層間インターフェース

層をまたぐデータはすべて JSON で表現する。詳細なスキーマは Phase 2 で `agents/schemas.py` に定義するが、
設計上の約束は以下。

- **第1層 → 第2層**: OpenAI 互換レスポンスの `choices[0].message.content`（文字列）。
  この時点では信頼できる構造を一切仮定しない。
- **第2層 → 第3層**: エージェントが実行しようとするアクションを表す型付きオブジェクト。
  最低限、対象環境（本番 / ステージング）、操作の種別、対象リソースを含む。
  OPA への入力は、このオブジェクトをそのまま JSON 化したものを `input` として渡す。
- **第3層 → 実行層**: `allow: boolean` と、拒否時の理由（複数可）。
  理由は人間が読んで判断できる文言であること。

## 失敗時の共通フロー

どの層で失敗しても、扱いは共通化する。

1. 失敗を検知した層が、**握り潰さずに**エスカレーションイベントを生成する。
2. イベントには「どの層で」「何が」「元のリクエストは何だったか」を含める。
3. Slack に Block Kit で提示し、人間の判断を待つ。
4. 承認されたら該当ステップから再開、却下されたら中断。いずれもログに残す。

`except Exception: pass` のようなコードは、この PoC の検証対象そのものを破壊する。

## PoC のスコープ外

以下は本 PoC では扱わない。実運用化の際に別途設計が必要。

- 実際の破壊的操作の実行（実行層はログ出力 / dry-run に留める）
- Slack 承認者の権限管理・多段承認
- 監査ログの永続化とその保全
- エージェントのマルチターン化、長期記憶
- コスト最適化、レイテンシ最適化
