## 考察

### 1. 期限切れは「満了ジョブの都合」ではなく「承認可否の条件」だった

design.md 3.5 の表は、有効期限の責務を満了ジョブ（`slack/expire.py`）に置いていた。
実装してみると、**「期限は過ぎたがジョブがまだ掃いていない」窓で承認が通る**。
数分おきに走らせる前提のジョブなら、その窓は数分ある。

直したのは `approve()` の SQL を
`UPDATE ... WHERE status='pending' AND expires_at > ?` にしたことだけである。
期限の判定を CAS と同じ 1 文に入れると、**チェックと更新の間に窓が存在しない**。

対称に見えて非対称なのが却下で、こちらは期限後も通るようにした。
**人間が明示的に「やるな」と言う操作は、いつ押されても安全側である。**
承認と却下を同じ「ステート遷移」として実装すると、この非対称性を取りこぼす。

### 2. 押してみなければ出なかった不備が 4 件あった（単体テストは全部通っていた）

実装直後の時点で単体 140 件が通っていたが、実機で押した瞬間に 4 件出た。

- **RBAC ミドルウェアが 404 を返していた。** Bolt は `next()` を呼ばずに終えるとレスポンスを
  組み立てられず 404 になる。**Slack から見ると「失敗」なので再送の対象**であり、
  拒否するほど再送が来るという逆向きの挙動になっていた。拒否は正常な処理結果なので
  `BoltResponse(status=200)` を返す。副次的に、Bolt がリクエスト本文
  （Slack の verification token を含む）を警告ログへ出すのも止まった。
- **承認期限の表示が実効値でなかった。** TTL 15 分を表示しながら TOCTOU 5 分で `stale` に倒れる。
  **実効的な窓は短いほうで決まる**ので、`actionable_until()` = min(承認期限, 提案時刻 + TOCTOU) を
  表示に使う。Handoff 仕様書の既定値（TTL 15 分 / STALE 5 分）はこの矛盾を内包している。
- **`stale` の監査に「誰が押して弾かれたか」が残っていなかった。** 押した事実は結果と独立に残すべきである。
- **ストアの `approve` が期限を見ていなかった**（考察1）。

共通点は、**どれも「1 回の押下」ではなく「押下と状態の関係」に関する不備**であることだ。
単体テストは状態を自分で作ってから押すので、**表示と判定が食い違っていても気づけない**。
実機で押すことの価値は、UI とステートを同時に観測できる点にある。

### 3. 「UI を消すこと」を排他に使っていたら二重実行していた（E-04）

E-04 では `chat.update` だけを injector に向け、承認・実行は成立したまま UI が古い状態を作った。
読み戻すとボタンは残っており、**2 回目の押下が物理的に可能**である。
実際に押すと `handoff.conflict`（`actual=executed`）になり、`executed_at` は書き換わらなかった。

ここで効いているのは [D-024](../../decisions.md) の「排他はストアの条件付き更新に任せる」である。
ボタンを消すことを排他の手段にしていた場合、**消し損ねた瞬間に防御が消える**。
Slack の UI は「結果の表示」であって「ロック」ではない。

同時に、もう 1 つ重いことが分かった。2 回目の押下では競合を伝えるエフェメラルも injector 行きで失敗し、
**押した人間には何も返らない**。UI が古いときに人間が取れる手段が無いため、
実運用ではストアを問い合わせる経路（スラッシュコマンド等）が要る。

### 4. 切り詰めは表示の都合ではなく、送出できるかどうかだった

未決事項2 を実測して、Slack は上限超過を**黙って切らず `invalid_blocks` で拒否する**ことが分かった
（section 3001 文字 / header 151 文字 / blocks 51 個のいずれも拒否。json-pointer つき）。

つまり `slack/blocks.py` の `truncate()` が無ければ、
**reason が長いインシデントで通知が丸ごと失敗していた**。
それは E 系とまったく同じ状態、すなわち「遮断は成立したが誰にも届かない」である。

`reason` の長さは第2層の `max_length` でしか縛られておらず、LLM の出力次第で上限に届きうる。
**「表示を整える処理」だと思っていたものが、可用性の部品だった。**
S-05 を「切り詰めた旨が本文に出る」という判定基準にしていたのは結果的に正しかったが、
理由としては弱く、本来は「上限超過で送出が失敗しないこと」を見るべきだった。

### 5. 人間の承認が担保しているのは「押した事実」であって「押した内容」ではない（N-01）

ボタンの `value` を Trace ID だけにした（[D-020](../../decisions.md)）ことで、
Slack のペイロード詐称は無意味になった。では**ストアそのもの**を書き換えたらどうなるか。

- 型として不正な改変（`dry_run: false` → `"false"`）は `restore_failed` で確実に止まった。
  strict な再検証がそのまま効き、`ValidationError` の `loc` まで残る。
- **型として正しい別アクションへの改変は止まらない。**
  承認者が見たのは `payment-db-data` の削除だが、実行層に届いたのは `billing-db-data` だった。

これは第2層の責務境界（形しか見ない）の帰結であり、Phase 2 の N-01 と同じ構図である。
しかし帰結はより重い。**ストアへの書き込み権限を持つ者は、承認の意味を書き換えられる。**

一致させるには、通知した内容のダイジェストを押下時に照合するか（`value` に入れるのではなく、
ストアとは別系統で保持する）、ストアを追記のみの構造に倒す必要がある。提言3。

### 6. `timeout` を据え置いた理由が、第3層とは違う

実測は `chat.postMessage` で p50 0.220 / max 0.530 秒（n=50）。
`SLACK_TIMEOUT_SECONDS=10.0` は実測最大の約 19 倍で、3.0 秒でも約 6 倍の余裕がある。
それでも 10.0 を据え置いた。

第3層（Phase 3 L-01）も据え置きだったが、根拠は「52 倍の余裕」という**大きさ**だった。
ここでの根拠は**非対称性**である。エスカレーションの送出はインシデント処理の**最後**にあり、
ループの中ではない。1 回だけ余分に待つ害が小さい一方、短すぎると
「届いているのに失敗と判定する」偽の E-01 が起き、判定基準8 の観測そのものを壊す。

**「実測して決める」という規律が同じでも、決め方の論理は層ごとに違う。**
第1層は正常時レイテンシの分布と障害検知時間のトレードオフ、第3層は桁の余裕、
ここは失敗の向きの非対称性だった。

### 7. DM で検証したことの代償は「エフェメラルが届かない」ことだった

チャンネルを作らず Bot との DM で検証した。想定していた制約（チーム同期が見えない、
複数人の同時押下ができない）は design.md に書いたとおりだったが、
**想定していなかった制約が 1 つあった**。

`chat.postEphemeral` が DM では `invalid_arguments` で失敗する。
その結果、**A-05（RBAC 拒否）と競合の通知が本人に届かない**。監査には `denied_by_rbac` が
残っているので検証としては成立しているが、**押した人間から見ると無反応**である。
N-02（handler 停止）と区別がつかない状態を、正常系の RBAC 拒否でも作ってしまっている。

もう 1 つ、DM にしたことで `conversations.open` という API 呼び出しが 1 段増えた。
E 系で**最初に失敗したのは `chat.postMessage` ではなく `conversations.open`** だった。
チャンネル宛てには存在しない経路であり、**検証環境を「楽な形」にすると障害の発生箇所が動く**。

### 8. C-01: Socket Mode にすると何が検証できなくなるか

Socket Mode は公開 URL が不要で、トンネルの張り替えも Request URL の設定も要らない。
運用は明確に楽になる。失われるものは次のとおり。

| | HTTP + トンネル（採用） | Socket Mode |
| --- | --- | --- |
| 認証 | **リクエストごとの署名検証**（`v0=` HMAC + タイムスタンプ） | 接続時の app-level token（`xapp-`）のみ |
| G-01〜G-05 | 検証できる | **原理的に消える**（改変も リプレイも「リクエスト」が無い） |
| 到達経路 | 公開 URL → handler。**外から叩ける**ことが前提 | Slack から張った WebSocket の内側 |
| N-02 の形 | handler 停止 = 到達不能 | handler 停止 = **接続断**（Slack 側がボタンを無効化しうる） |

本 PoC の運用原則2 は「署名検証」と「`value` は Trace ID のみ」の 2 つからなる。
Socket Mode を選ぶと**前者が検証対象から消える**。消えるのは実装の手間であって脅威ではない
——ペイロード詐称の脅威は残り、それを防いでいるものが**見えなくなる**だけである。

本フェーズでは結果的に、押下を伴う検証の大半を**署名を自前で計算した直接 POST**で駆動できた。
つまり「トンネルが要るのは人間が実際に押すときだけ」であり、
**検証の容易さを理由に Socket Mode を選ぶ必要はなかった**。

### 9. C-02: 通知パターン1 を LiteLLM 自身の alerting で出す構成

Handoff 仕様書の通知パターン1（第1層の失敗）は、本フェーズのスコープ外とした（design.md 第0章）。
LiteLLM Proxy には Slack alerting があり、`general_settings.alerting` を設定すれば
フォールバックや失敗を Proxy 自身が通知できる。構成としては**層ごとに通知経路が分かれる**。

| | エージェント経由（本 PoC の 2〜4） | LiteLLM の alerting（1） |
| --- | --- | --- |
| 相関 ID | `trace_id` が全層を貫く（[D-016](../../decisions.md)） | Proxy のリクエスト ID。**エージェントの `trace_id` を知らない** |
| 粒度 | インシデント 1 件ごと | デプロイ・モデル単位の運用アラート |
| 人間への要求 | 承認・却下という**次の一手** | 「知っておけ」 |

分けること自体は妥当である。パターン1 は**インシデント対応ではなく基盤の運用通知**であり、
受け手も宛先も違う。問題は相関 ID が繋がらないことで、
第1層がフォールバックしたのと同じインシデントの通知が別経路で届いても、
**人間が手で突き合わせることになる**。
LiteLLM に `trace_id` をメタデータとして渡し、alerting のテンプレートに載せられるかは未確認。

### 10. 送出の失敗は残るが、受信の失敗は残らない

E 系（送出）とN-02（受信）はどちらも「Slack が使えない」だが、観測可能性がまったく違う。

- **送出の失敗**: 終了コード 5・`event=slack.failed`・ストアに `notify_failed`。
  エージェント側に 3 系統で残る。
- **受信の失敗**: ストアが**バイト単位で一致**し、監査ログにすら載らない。
  押した人間の側にも（DM では）何も出ない。

[D-019](../../decisions.md) で「送出と受信は非対称」と書いたのは実装形態の話
（同一プロセスのライブラリ / 独立した常駐プロセス）だったが、
**運用上の非対称はもっと重い**。多層防御の最外周には、その外側が無い。
承認待ちの監視は Slack ではなくストア側で行うしかなく、しかも満了ジョブが検知できるのは
「誰も押さなかった」ことだけで、「押されたが届かなかった」は**原理的に検知できない**。

### 11. `execution_failed` に `executed_at` が立つ（語彙と記録のずれ）

N-01a で `restore_failed` → `execution_failed` に落ちたエントリを見ると、
**`executed_at` に時刻が入っている**。実行層には到達していないので、
列名のとおりに読むと「実行した」ことになってしまう。

実害は無い。排他は `status` に対する CAS で行っており、`executed_at` は判定に使っていない。
しかし design.md 3.5.1 は `execution_failed` を「確定的な失敗・**再試行可**」と定義しており、
現実装には `execution_failed` から `pending` / `approved` に戻す遷移が無い。
**語彙としては再試行可だが、実装としては終端状態**である。

Phase 5 で実行が本物になれば `execution_failed` は「実行を試みて失敗した」に変わり、
そのとき `executed_at` は「試行時刻」として意味を持つ。
再試行（`retry_count`）は Phase 5 の課題として既に積んである。

## 実運用への提言

1. **Slack が停止したときの別経路を用意する。** 遮断は成立しているのに誰も知らない状態
   （E 系・終了コード 5）は、多層防御でもっとも危険な失敗である。
   終了コード 5 を監視システム側で拾い、PagerDuty 等の第二経路へ回す。
   **通知層を二重化するのではなく、通知層の失敗を監視対象にする**ほうが構造が素直になる。
2. **受信経路の死活監視を入れる。** N-02 は押下の事実すら残らない。
   handler へ合成リクエスト（署名つき・存在しない Trace ID）を定期送出し、
   `handoff.conflict` または 404 相当が返ることを確認する。トンネルを含めた経路全体が対象。
3. **承認の意味を固定する。** ストアを書き換えられると承認の内容が変わる（N-01）。
   通知時の Block Kit のダイジェストをストアとは別系統（追記のみの監査ログ）に保存し、
   実行直前に照合する。少なくとも**ストアへの書き込み権限とエージェントの実行権限を分離**する。
4. **承認者ロールは環境変数ではなく第3層に持たせる。** 本 PoC は
   `SLACK_APPROVER_USER_IDS` の一律判定にした（[D-021](../../decisions.md)）が、
   操作の危険度は第3層が `violated_rules` として既に返している。
   「どの違反なら誰が承認してよいか」は Rego に書けるし、書けば**承認要件もポリシーとして
   テストできる**。通知層に if 文を増やす方向に進まないこと。
5. **実行層を承認経路と共有し続けるかを Phase 5 で決める。** いまは `execute_dry_run()` を
   共有しており、`allow: true` の経路と承認経路でログ行が同形になる利点がある。
   実行が本物になると、**handler プロセスがクラスタへの書き込み権限を持つ**ことになり、
   「承認ボタンを押せる = handler の権限で実行できる」という結合が生まれる。
   実運用では Receiver（承認を受けてキューに積む）と Executor（権限を持って実行する）を分ける。
6. **TTL と TOCTOU 閾値は別物として提示する。** 実効的な承認窓は短いほうで決まるため、
   2 つの値を独立に設定できる形にすると表示が嘘になる（考察2）。
   設定として 1 つにするか、少なくとも**表示は常に実効値**にする。
7. **`policy_override` を保全する。** OPA の Decision Log には「人間が上書きした」事実が残らない。
   いまはストアの `audit_log` にしか無く、**ストアを消せば消える**。
   監査ログだけは別ストレージへ追記専用で送る。
8. **Block Kit の上限を入力側で縛る。** `invalid_blocks` は通知の全損であり、
   インシデント時に初めて踏む種類の失敗である（考察4）。
   第2層のスキーマの `max_length` と通知側の切り詰め上限を**一方が他方を保証する形**で対応づける。

## Phase 5 への申し送り

- **実行が本物になると壊れる前提が 3 つある**: (a) `ack()` の 3 秒ルール（考察・未決事項12）、
  (b) handler の権限（提言5）、(c) `execution_failed` の意味（考察11）。
- **Phase 4 で注入できなかったものが Phase 5 で注入できる**: 通知パターン5（実行時エラー）、
  `unknown` ステート、`execution_failed` からの再試行、承認待ち中に対象が変わる TOCTOU。
- **ngrok / cloudflared は Phase 5 でも要る。** k8s 操作は出ていく通信であり、
  入口が要るのは Slack のボタン押下だけという構造は変わらない。
- **検証の大半はトンネル無しで回せる**（考察8）。署名を自前で計算した直接 POST で
  handler の検証経路はそのまま通る。トンネルを張るのは「人間が実際に押す」ときだけでよい。
