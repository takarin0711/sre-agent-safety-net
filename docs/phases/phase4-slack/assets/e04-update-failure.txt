handler を SLACK_API_BASE_URL=http://localhost:8080/api で起動し直し、
署名つきの block_actions で承認を駆動した（ボタンの押下は G-06 と同じ手口で代替）。

── 2 回目の押下（古い UI は押せてしまう）
handoff.conflict actual=executed / 監査に lock_conflict。executed_at は 07:25:55.924062 のまま。
→ **UI が古くても二重実行にはならない。**排他は UI ではなくストアの条件付き更新が担保している。

── 所見
1. 判定基準6 の「送出の失敗と実行の失敗が別の値である」が、E-04 では
   さらに「更新の失敗」として 3 つ目に分かれた。slack.failed に method を載せているため、
   同じ event 名でも postMessage の失敗（E-01〜03・遮断が届いていない）と
   chat.update の失敗（届いており実行も済んでいる）を後から区別できる。
2. **UI を信じる実装だったら二重実行していた。** ボタンを消すことを排他の手段にすると、
   消し損ねた瞬間に防御が消える。D-024 の「排他はストアに任せる」はここで効いている。
3. 2 回目の押下で chat.postEphemeral も injector 行きになって失敗した。
   **競合の通知すら届かない**状態であり、押した人間には何も返らない。
   実運用では「UI が古い可能性」を前提に、ストアを問い合わせる経路（スラッシュコマンド等）が要る。
