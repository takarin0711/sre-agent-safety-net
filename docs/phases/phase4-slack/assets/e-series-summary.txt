E 系（Slack への送出障害）実機結果の抜粋 — 2026-10-01

escalate() を直接呼び、送出の失敗だけを切り出して観測した。
LLM と OPA は経路に関係しないため通していない。終了コード 5 への反映は単体で検証済み
（tests/test_escalation.py）。

注入の確認は「注入器が動いているか」ではなく **リクエストが実際にその経路を通ったこと**
で行う（docs/decisions.md D-018）。下記の injector アクセスログがその証拠。

── 所見
1. Slack は失敗しても HTTP 200 を返す。ステータスだけを見る実装は静かに沈黙する。
   第3層の X-04（OPA が 200 + result 無し）と同じ形の罠。
2. **最初に失敗したのは chat.postMessage ではなく conversations.open だった。**
   送出先を DM にしたことで API 呼び出しが 1 段増え、失敗点がそこに移っている。
   チャンネル宛てでは通らない経路。
3. 3 件とも「遮断は成立」かつ「人間に届いていない」が区別できている（D-022）。
