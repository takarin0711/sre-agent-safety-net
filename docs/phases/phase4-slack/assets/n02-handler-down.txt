N-02 限界の実演: handler を停止した状態でボタンを押す — 2026-10-01

通知経路の単一障害点を見る。送出（エージェント → Slack）と受信（Slack → handler）は
非対称で（D-019）、受信側は**常駐プロセスと外部から到達可能な URL**という前提の上に乗っている。
その前提が欠けたときに何が起きるかを実機で確認した。

── 条件
handler: 停止（:3000 に listener 無し / プロセス数 0）
トンネル: 停止（cloudflared のプロセス数 0）
対象: P-01 で実際に投稿された通知（trace_id=40d3ec87-5a0b-4c9c-a297-6a48ee2531bf）
      **status=pending のまま**。もし要求が届いていれば実行層まで到達する状態で押した
      （実行済みのエントリを押すと「競合で弾かれた」と見分けがつかない）

── エージェント側（押下の前後でストアを全件ダンプして比較）
before sha256: 3284f4402d089f00d0b1082ca9d60665da27da551b2b0584220acb20073fbec4
after  sha256: 3284f4402d089f00d0b1082ca9d60665da27da551b2b0584220acb20073fbec4
（n02-before.json / n02-after.json の値。ユーザ ID とチャンネル ID の匿名化後に取り直した。
  匿名化前の生ダンプでも両者は一致していた: d1434093bf96777f5af0801691a04c7c181e1d4cb05560086892948edbe770df）
バイト単位で一致。pending_actions 15 件 / audit_log 32 件とも増減なし。
対象エントリは status=pending / approved_by=None / executed_at=None のまま。
→ **押下の事実はどこにも残らない。** 監査ログにすら載らない。

── Slack 側
押下しても新たなエラー表示は現れず、メッセージは投稿時のまま残った
（最終行の context「実行内容は Trace ID をキーにサーバ側のストアから取得されます」が
そのまま見えている状態）。**押した人間に成否が返らない。**

── 所見
1. **これは「拒否」ではなく「無」である。** 第1層〜第3層の失敗はすべてエスカレーション層に
   手渡されて人間に届くが、**エスカレーション層自身の受信側が落ちたときに受け手がいない。**
   多層防御の最外周には、その外側が無い。
2. E 系（送出の失敗）は終了コード 5 と event=slack.failed で**エージェント側に残る**。
   N-02（受信の失敗）は**どちらにも残らない**。同じ「Slack が使えない」でも、
   送出と受信では観測可能性がまったく違う。D-019 の非対称性は運用上もここで効く。
3. したがって承認待ちエントリの監視は Slack ではなくストア側で行う必要がある。
   satisfy しているのは満了ジョブ（slack/expire.py）だけで、これは**期限切れを検知するだけ**であり、
   「押されたのに届いていない」は検知できない（押下の記録が無いため原理的に不可能）。
4. 実運用では受信経路の死活監視（handler への合成リクエスト）が要る。提言に回す。
