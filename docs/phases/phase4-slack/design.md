# Phase 4 設計: エスカレーション層 Slack Handoff と Human-in-the-Loop

> このドキュメントは**着手前**に確定させるもの。検証後に判定基準を書き換えない。
> 予想と異なる結果になった場合は [result.md](result.md) の「考察」に記録する。
>
> エスカレーション層は製品名 **Slack** で呼ぶ。第2層だけを役割名で呼ぶ理由は [D-013](../../decisions.md)。
> 本フェーズの検証対象は「人間に引き渡す経路が壊れないこと」であって、UI の見栄えではない。

## 0. Handoff 仕様書との対応（どこまでを Phase 4 で扱うか）

Phase 3 の design.md 第0章と同じ形で、仕様書「フォールバック & Handoff フロー図」の各要素を割り当てる。
Phase 3 は「図1 の第3層の 3 分岐」と「図3 の入口まで」を担当した。
**Phase 4 は図3 の本体（承認・却下・TTL・二重押下）と、通知パターン 2 / 3 / 4 の Block Kit を担当する。**

| 仕様書の要素 | Phase 4 で扱うか | 扱い方 / 先送りする理由 |
| --- | --- | --- |
| 通知パターン2（スキーマ検証失敗） | **扱う** | `kind="validation_failed"` から生成。ボタンなし |
| 通知パターン3（危険操作ブロック・承認要求） | **扱う（本フェーズの主戦場）** | `kind="policy_denied"` から生成。承認 / 却下ボタンつき。**違反を複数表示できる形にする**（Phase 3 考察6） |
| 通知パターン4（ポリシー評価不能・Fail-Closed） | **扱う** | `kind="policy_unavailable"` から生成。**ボタンを出さない**ことが検証対象 |
| 通知パターン1（インフラ全滅） | 扱わない | 仕様書自身が「【独立経路】」と定義しており、第1層（LiteLLM）自身の alerting の責務。エージェントは「どのエンドポイントが落ちたか」を原理的に知らない（3.13）。C-02 で構造だけ確認する |
| 通知パターン5（実行時エラー・再試行） | 扱わない | 実行層が dry-run のため注入できない（Phase 3 と同じ理由）。ストアは再試行を表現できる形にしておく（3.5） |
| 図3「承認して実行」 | **扱う** | ストアから復元 → 実行層（dry-run）→ `policy_override` の監査記録まで |
| 図3「却下」 | **扱う** | `closed_rejected` への遷移と `chat.update` |
| 図3「TTL 満了」 | **扱う** | 満了検知ジョブ（手動実行の CLI）で `closed_expired` にし、二次エスカレーションを通知する |
| 図3「ロック取得失敗（二重押下）」 | **扱う** | ストアの CAS で 1 回だけ実行されること |
| 運用原則1 思考プロセスの維持 | **扱う** | 本体は要約、全文はスレッド返信。**秘匿情報のマスキング**と長さの切り詰めを実装する（3.8） |
| 運用原則2 承認内容の同一性保証 | **扱う（本フェーズの主戦場）** | 署名検証 / `value` は Trace ID のみ / 実行内容はストアから復元（3.3・3.7） |
| 運用原則3 2段階確認 | **部分的に扱う** | confirm ダイアログは**全ての承認ボタンに一律で**付ける。Modal でのリソース名手入力は扱わない（3.4 の理由） |
| 運用原則4 承認ステートの一貫性 | **扱う** | SQLite で排他性・永続性・TTL・冪等性・追跡性・再試行の同一性を満たす（3.5） |
| 運用原則5 メッセージ状態の動的更新 | **扱う** | `chat.update` でボタンを消し、読み戻しで確認する |
| 付帯要件 RBAC | **部分的に扱う** | 承認者リスト（`user.id`）による一律の可否判定まで。**操作種別によるロールの出し分けは扱わない**（3.4 と同じ理由） |
| 付帯要件 TOCTOU | **扱う** | 提案・承認・実行の 3 時刻を分けて記録し、**提案からの**経過が閾値を超えたら実行中止（3.5） |
| 付帯要件 監査ログ | **扱う** | `policy_override` / `normal_approval` の区別を含めてストアに記録する（3.6） |
| 付帯要件 通知経路の障害 | **扱う** | Slack 不達を検知して終了コードに出す。**PagerDuty 等の別経路は実装しない**（3.9） |
| エージェント処理の中断・再開 | 扱わない | Phase 5。Phase 4 の承認は「ストアのアクションを実行層に流す」ところまでで、エージェントの思考は再開しない |

**この表の要点**: Phase 4 の合否は「人間に見えたか」ではなく、
**(a) 押せるボタンが正しい通知だけに出ること、(b) 押した内容と実行される内容が一致すること、
(c) 押されなかった / 届かなかったことが沈黙にならないこと** の 3 点で判定する。
見た目の良し悪しは判定基準に使わない。

## 1. 目的と非目的

### 証明すること

1. **各層の失敗が、人間が判断できる形で Slack に着地する。**
   第2層・第3層が生成する `EscalationEvent` の 3 種（`validation_failed` / `policy_denied` /
   `policy_unavailable`）が、それぞれ通知パターン 2 / 3 / 4 になる。
   とくに **`policy_unavailable` に承認ボタンを出さない**こと。
   評価できていない操作に承認ボタンを出すのは、Fail-Closed を UI で台無しにする行為である（[D-015](../../decisions.md)）。
2. **承認した内容と実行される内容が一致する。**
   ボタンの `value` は Trace ID のみで、実行内容は必ずサーバ側のストアから復元する。
   **復元したアクションは、実行の直前にもう一度第2層で検証する**（[D-020](../../decisions.md)）。
   Slack のペイロードを改変しても任意のコマンドを実行できないこと、
   そもそも署名検証を通らない要求が処理されないことを示す。
3. **承認ステートが一貫している。**
   二重押下しても実行は 1 回。TTL 満了後は承認できない。実行済みは再実行されない。
   誰がいつ承認し、いつ実行されたかが分けて記録され、**`policy_override`（人間が deny を上書きした事実）が残る**。
   これは OPA の Decision Log には残らない（Phase 3 提言7）。
4. **通知が届かなかったことが沈黙にならない。**
   Slack が落ちている・トークンが無効・レート制限、いずれでも
   **「遮断は成立しているが人間には届いていない」状態を検知して表面化させる**（[D-022](../../decisions.md)）。
   多層防御でもっとも危険な失敗は、止めたのに誰も知らないことである。
5. **Block Kit の生成がワークスペース無しで検証できる。**
   `EscalationEvent` → Block Kit は純関数であり、pytest で決定的に固められる（3.2）。
   Phase 2・3 と同じく「単体を先に固め、実機は経路の確認に使う」。

### 証明しないこと（意図的にスコープ外）

- **通知の見た目の良し悪し。** レイアウト・絵文字・文言の調整は判定基準に使わない。
- **Slack の可用性対策。** 別経路（PagerDuty 等）へのフォールバックは実装しない。
  第3層と同じく、**単一障害点であることを隠さずに測る**（[D-015](../../decisions.md) と同じ態度）。
- **不達通知の自動再送。** 送出に失敗したものを自動で送り直さない。
  再送を入れると「最終的に届いた」が確率的に起き、検知の決定性が測れなくなる（[D-012](../../decisions.md) と同じ構造）。
  TTL 満了時の二次エスカレーションだけは仕様書どおり行う（3.11）。
- **承認後のエージェント処理の再開。** Phase 5。Phase 4 の承認は実行層（dry-run）までで終わる。
- **実際の破壊的操作。** 承認されても実 `kubectl` は発行しない（CLAUDE.md）。
- **多段承認・承認者のロール階層。** 承認者リストによる一律判定まで（3.4）。
- **Slack のスレッド・ワークフロー機能を使った高度な UI。** Modal もスコープ外（3.4）。

## 2. 構成

### 2.1 エスカレーション層は送出と受信で非対称（[D-019](../../decisions.md)）

第2層はインプロセス、第3層は別プロセス（[D-010](../../decisions.md)）だった。
エスカレーション層は**ひとつの層の中で送出と受信の形が違う**。

```
  agents/main.py ──▶ agents/escalation.py ──▶ slack/notifier.py ──── HTTPS ───▶ Slack
   （インシデント処理）  （ハンドオフ経路の 1 本化）  │                              │
                                                  ▼                              │
                                          slack/store.py (SQLite)                │
                                        承認待ちを先に永続化してから送る            │
                                                  ▲                              ▼
                                                  │                        人間がボタンを押す
                                                  │                              │
  slack/handler.py  ◀──── HTTPS（署名つき）────────┴──────────────────────────────┘
   （独立プロセス。Bolt）
        │ ストアから復元 → 第2層で再検証 → 実行層（dry-run）
        ▼
  agents/execution.py
```

| | 送出（notifier） | 受信（handler） |
| --- | --- | --- |
| 実行形態 | エージェントと**同一プロセス**のライブラリ | **独立プロセス**（常駐サーバ） |
| 起動の契機 | インシデント処理のたび | 常駐。人間の操作を待つ |
| 外部境界 | Slack Web API への HTTPS | Slack からの HTTPS を**受ける**（公開 URL が要る） |
| 失敗の扱い | 終了コードに反映する（3.9） | HTTP ステータスで返す。署名不正は 401 |
| 「層自体のダウン」 | Slack 側のダウンとして現れる | **プロセスが落ちていると誰も気づけない**（N-02） |

送出をインプロセスにするのは、仕様書の図1 が通知を「【App 主導】」と定義しているためであり、
かつ**送出の失敗をそのインシデント処理の結果に反映させる必要がある**ため（3.9）。
受信を独立プロセスにするのは、承認が数分〜数時間後に来るからである
（仕様書「App プロセスは待機せず解放」）。

### 2.2 検証経路

```
正常系（通知）
  --incident ─▶ 第1層 ─▶ 第2層 ─▶ 第3層 deny ─▶ ストアへ永続化 ─▶ Slack へ送出   終了コード 3
  --incident ─▶ 第1層 ─▶ 第2層 ✗          ─▶ （ストア無し）  ─▶ Slack へ送出   終了コード 1
  --incident ─▶ 第1層 ─▶ 第2層 ─▶ 第3層 ✗ ─▶ （ストア無し）  ─▶ Slack へ送出   終了コード 4

承認フロー（独立プロセス）
  ボタン押下 ─▶ 署名検証 ─▶ RBAC ─▶ ストアの CAS ─▶ 第2層で再検証 ─▶ 実行層(dry-run) ─▶ chat.update

異常系（送出）
  --incident ─▶ …… ─▶ Slack へ送出 ✗ ─▶ ローカルログに残す              終了コード 5
```

**承認待ちとしてストアに入るのは `policy_denied` だけである。**
`validation_failed` と `policy_unavailable` は人間が承認して実行してよい状態ではないため、
ストアに承認待ちエントリを作らない。**「ストアにエントリがある」＝「承認ボタンが存在しうる」**
を 1 対 1 に保つことで、パターン4 に誤ってボタンを出す実装ミスがストアの状態にも現れる。

### 2.3 このフェーズで「信じないもの」

各フェーズは「何を信じないか」で定義されてきた。第2層は LLM の出力、第3層は OPA の応答。
Phase 4 で信じないものは 3 つある。

| 信じないもの | 具体的な対処 | 対応シナリオ |
| --- | --- | --- |
| **Slack から届く HTTP リクエスト** | 署名検証（`X-Slack-Signature`）。タイムスタンプの鮮度も見る | G-01〜G-05 |
| **ボタンのペイロードに入っている値** | `value` は Trace ID のみ。実行内容はストアから引く | S-07 / A-01 |
| **ストアから読み出したレコード** | `ProposedAction.model_validate_json()` で**再検証**してから実行層に渡す | T-07 |

3 つ目は過剰に見えるが、ストアはこの PoC で初めて登場する**可変の永続状態**である。
第2層が「LLM の出力を信じない」層であるなら、**時間をまたいで保存されたデータも同じ扱いにする**のが一貫している。
再検証のコストは関数呼び出し 1 回であり、失敗すれば実行されない（安全側）。

## 3. 設計

### 3.1 ファイル構成と依存の向き

```
agents/
├── escalation.py    # 追加。ハンドオフ経路の 1 本化（ログ出力 + ストア永続化 + 送出）
├── execution.py     # 追加。main.py の execute_dry_run() を切り出す（handler からも呼ぶため）
├── main.py          # 変更。escalation を呼ぶ / 終了コード 5 / --no-slack
├── validation.py    # 変更。log() 直呼びを escalate() に置き換える（出力は変えない）
└── policy.py        # 変更。同上

slack/
├── blocks.py        # EscalationEvent → Block Kit（純関数。Slack に触れない）
├── masking.py       # 秘匿情報のマスキング（純関数）
├── notifier.py      # chat.postMessage / chat.update / スレッド返信
├── store.py         # SQLite の承認ステートストア（Trace ID がキー）
├── handler.py       # Bolt アプリ（署名検証・block_actions の処理）
└── expire.py        # TTL 満了検知ジョブ（手動実行の CLI）
```

- **`slack/blocks.py` は Slack SDK を import しない。** 純粋に dict を組み立てるだけにする。
  ワークスペースが無くても pytest で全パターンを固められるようにするため（判定基準1）。
- **依存の向きは `agents/` → `slack/`（送出）と `slack/` → `agents/`（受信）の双方向になる。**
  循環を避けるため、`slack/handler.py` は誰からも import されない終端に置き、
  実行層は `agents/execution.py` に切り出す。
- **Phase 1〜3 のログ出力を 1 バイトも変えない。** `escalate()` は既存の `log()` 行を
  そのまま出力したうえで、送出結果を別の行（`event=slack.notified` / `slack.failed`）として追加する。
  Phase 2・3 の `assets/` と比較できなくなると、過去の判定が再現できなくなる。

### 3.2 Block Kit の生成は純関数にする

```python
# slack/blocks.py（設計イメージ）

def build_blocks(event: EscalationEvent) -> list[dict]:
    """EscalationEvent を Block Kit に変換する。Slack には触れない（純関数）。

    kind → 通知パターンの対応はここだけが知っている。EscalationEvent 側に
    パターン番号を持たせない設計（phase3 design.md 3.6）を受けている。
    """
```

`kind` → パターンの対応表を 1 箇所に閉じ込める。**承認ボタンを出す条件は `kind == "policy_denied"` のみ**とし、
それ以外の分岐（環境・操作・違反の種類による出し分け）を書かない。条件が 1 つなら、
「パターン4 にボタンが出てしまった」という事故が構造的に起こり得ない。

### 3.3 ボタンの `value` は Trace ID のみ（運用原則2 / [D-020](../../decisions.md)）

```jsonc
{"type": "button", "action_id": "approve_action", "style": "danger",
 "value": "0f1e2d3c-...",            // Trace ID だけ。コマンド文字列は入れない
 "confirm": { ... }}
```

- 操作の種別は **`action_id`** が担う（`approve_action` / `reject_action`）。
  `value` から操作内容を除いても、受信側の分岐に必要な情報は失われない（仕様書 運用原則2）。
- 受信側は `value` を **ストアの主キーとしてのみ**使う。ストアに無ければ何もしない。
- **ストアから復元した `action` は `ProposedAction.model_validate_json()` を通してから実行層に渡す。**
  ストアが壊れていた／誰かが書き換えていた場合、実行ではなく `ValidationError` に倒れる。

判定基準3 は「全パターンの Block Kit を機械的に走査し、`value` が Trace ID 以外を含まないこと」で確認する。
目視ではなくテストで守る（人間のレビューに依存する防御は、Phase を重ねるほど緩む）。

### 3.4 確認強度を操作の種別で出し分けない（[D-021](../../decisions.md)）

仕様書の運用原則3 後段は「本番の PVC/PV 削除については Modal でリソース名を手入力させる」と定める。
これを実装すると、通知層に **`if environment == "production" and operation in destructive:`** が生まれる。
これは Phase 3 の判定基準7（ポリシーの語彙を `agents/` に書かない）が禁じたものと同じ形であり、
**ポリシーの判定が `agents/` から `slack/` に移っただけ**になる。

したがって Phase 4 では次の線引きを採る。

| 通知層がすること | 可否 | 理由 |
| --- | --- | --- |
| `environment` / `operation` / 対象名を confirm の文面に**埋め込む** | **する** | 値の提示であって判定ではない。CLAUDE.md が `schemas.py` / `prompts.py` に認めている例外と同じ線 |
| `environment` / `operation` の値で確認 UI を**出し分ける** | **しない** | 危険度の判定であり、第3層の責務。ここに書くと二重管理になる |
| confirm ダイアログを承認ボタンに**一律で**付ける | **する** | 分岐が無いので語彙が漏れない |
| Modal でのリソース名手入力 | **しない** | 出し分けが前提の機能であり、上記に抵触する。加えて「confirm が形骸化する」という前提そのものが 1 回の PoC では観測できない |

RBAC も同じ線引きにする。**承認者リストに含まれるかどうか**の一律判定までとし、
「本番の破壊的操作は上位ロール」という出し分けはしない。
出し分けが必要なら、**その危険度は第3層が `violated_rules` として既に返している**のだから、
Rego 側に承認要件を持たせる形（`required_approver_role` 等）が筋になる。
これは実装せず、result.md の提言に書く。

### 3.5 ステートストア（`slack/store.py`。運用原則4）

SQLite を採る。**コンテナを増やさず、標準ライブラリだけで排他・永続・TTL・監査を同一ファイルに置ける**ため。
「分散」ロックではないという限界は隠さず明示し、提言に書く（[D-001](../../decisions.md) の態度と同じ）。

```sql
-- 承認待ちアクション（Trace ID が主キー）
CREATE TABLE pending_actions (
  trace_id       TEXT PRIMARY KEY,
  status         TEXT NOT NULL,   -- 3.5.1 の語彙
  event_json     TEXT NOT NULL,   -- EscalationEvent 全体。承認対象はここから復元する
  channel        TEXT,            -- chat.update の宛先
  message_ts     TEXT,            -- 同上。送出に失敗したときは NULL（更新できない状態を表せる）
  created_at     TEXT NOT NULL,
  expires_at     TEXT NOT NULL,   -- created_at + TTL
  approved_by    TEXT,
  approved_at    TEXT,            -- 承認時刻と実行時刻を分けて持つ（TOCTOU 検証のため）
  executed_at    TEXT,
  execution_result TEXT
);

-- 監査記録（追記のみ。承認・却下・実行・期限切れをすべて残す）
CREATE TABLE audit_log (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  trace_id       TEXT NOT NULL,
  occurred_at    TEXT NOT NULL,
  actor          TEXT,            -- Slack の user.id と表示名
  action         TEXT NOT NULL,   -- approve / reject / execute / expire / denied_by_rbac / lock_conflict
  override_kind  TEXT,            -- policy_override / normal_approval
  detail_json    TEXT
);
```

| 運用原則4 の要件 | 実現方法 | 検証 |
| --- | --- | --- |
| 排他性 | `UPDATE ... SET status='approved' WHERE trace_id=? AND status='pending'` の**更新件数が 1 のときだけ**先に進む（CAS）。`BEGIN IMMEDIATE` で書き込みを直列化する | T-01 / A-03 |
| 永続性 | ファイルに残る。エージェントプロセスの終了後も承認できる | A-01 |
| 有効期限 | `expires_at` を超えたら承認を受け付けない。満了検知ジョブが `expired` にする | T-03 / A-04 |
| 冪等性 | `executed_at` が入っているエントリへの要求は無視する。**実行成功時にのみ**立てる | T-04 |
| 追跡性 | `created_at` / `approved_at` / `executed_at` を分けて記録。**`created_at` から 5 分**を超えたら実行中止 | T-05 |
| 再試行の同一性 | 実行内容は常に `event_json` から復元。Slack のペイロードからは再構成しない | T-06 |

**TOCTOU は「承認 → 実行」ではなく「提案 → 実行」で測る。** 承認ボタンの押下から実行層までは
同一ハンドラ内の数ミリ秒であり、ここを測っても何も検知できない。
変化しうるのは**インシデントが起きてからクラスタが辿った時間**のほうである。
`approved_at` も記録はするが（実行をキューで分離したときに意味を持つ）、
**中止の判定に使うのは `created_at` からの経過時間**とする。

### 3.5.1 ステートの語彙

ステートは閉じた語彙として**いま決め切る**。Phase 4 で到達しないものも含めて定義するのは、
[D-023](../../decisions.md) で `normal_approval` を残したのと同じ理由である。
**後から語彙を足すと、既存レコードの意味が変わる**（`failed` が「送出の失敗」か「実行の失敗」かは、
後から見分けられない）。

| ステート | 意味 | 遷移元 | Phase 4 で到達するか |
| --- | --- | --- | --- |
| `pending` | 承認待ち（初期状態） | — | **する** |
| `approved` | 承認済み（実行へ進む） | `pending` | **する** |
| `executed` | 実行完了（dry-run ログの出力まで） | `approved` | **する** |
| `rejected` | 却下 | `pending` | **する** |
| `expired` | 承認期限超過（満了ジョブ） | `pending` | **する** |
| `stale` | TOCTOU 閾値超過により実行中止 | `approved` | **する**（T-05） |
| `notify_failed` | **通知の送出**に失敗した（遮断は成立している） | `pending` | **する**（E 系） |
| `execution_failed` | 実行を試みて確定的に失敗した | `approved` | しない（実行層が dry-run） |
| `unknown` | **実行されたかどうかが分からない** | `approved` | しない（同上） |

**`execution_failed` と `unknown` を分けて定義しておくことが重要である。**
実 API がタイムアウトしたとき、コマンドが実行されたかどうかは例外からは判別できない。
`kubectl delete pvc` のような非冪等な操作でこれを一律に「失敗」として再試行可能にすると、
**二重実行を招く**。実行されたか分からないものは人間が確認するしかなく、
システムが推測して再試行ボタンを出してはならない。
Phase 4 の実行層は dry-run ログなので両者には到達しないが、**語彙だけは今のうちに分けておく**。
これは第3層の deny / 評価不能の分離（[D-015](../../decisions.md)）と同じ形の判断である。

**監査レコードは運用ステートより寿命が長い。** 本 PoC は両者を同じ SQLite ファイルに置くが、
`pending_actions` は終端ステートに達した時点で役目を終えるのに対し、`audit_log` は
`policy_override` の証跡として残り続ける。**終端ステート到達時に監査基盤へ移送する**のが
実運用の形であり、同居は PoC の割り切りである。提言に書く。

**書き込みの順序を「ストア → Slack」に固定する。** 逆にすると、送出は成功したのに
ストアに無いエントリのボタンが押される（＝押しても何も起きない、理由も分からない）状態が作れる。
ストアが先なら、最悪でも「エントリはあるが通知が無い」という、**満了ジョブが拾える**状態で止まる。

### 3.6 承認時に第3層へ再問い合わせしない（[D-023](../../decisions.md)）

人間が承認するのは「第3層が deny したアクション」である。ここで OPA に問い合わせ直せば、当然また deny が返る。
仕様書はこの状況を **`policy_override`（ポリシー違反を人間が上書きした事実）** として記録することを求めている。

- 承認・実行時に第3層へは問い合わせない。
- 監査に `override_kind = "policy_override"` を必ず記録する。
  Phase 4 の承認はすべて `policy_denied` に対するものなので、実際には全件が `policy_override` になる。
  それでも `normal_approval` との区別をスキーマに残すのは、Phase 5 で
  「deny ではないが人間の確認を挟む」経路が出てきたときに、**後から意味を変えないため**。
- **OPA の Decision Log には override は残らない**（Phase 3 提言7）。ここで記録しなければどこにも残らない。

### 3.7 署名検証と RBAC（運用原則2 / 付帯要件）

- **署名検証は Bolt に任せる**（`App(signing_secret=...)`）。自前で書かない。
  検証は「Bolt が弾くこと」ではなく「**弾かれた要求が 1 件も処理に到達しないこと**」で行う（G 系）。
- Slack は 5 分より古いタイムスタンプをリプレイとみなす。これも検証対象に含める（G-04）。
- **G-05 として、署名検証を無効化した場合に改変ペイロードが通ることを対比で示す。**
  防御を外すと何が起きるかを見せるのは Phase 2 の `strict=True` の議論と同じ形であり、
  「署名検証を必須とする」という仕様書の記述に実測の裏付けを与える。
  **この対比は検証用のフラグでのみ行い、既定の経路には無効化の手段を残さない。**
- RBAC は `SLACK_APPROVER_USER_IDS`（カンマ区切り）に含まれる `user.id` のみ承認・却下を実行できる。
  含まれない場合はエフェメラルメッセージで拒否し、`audit_log` に `denied_by_rbac` を残す。
  **押せてしまったことも記録に残す**（押下自体は Slack 側では止められないため）。

### 3.8 長さの切り詰めと秘匿情報のマスキング（運用原則1）

Phase 2 の積み残し「`raw_output` の切り詰め（Block Kit のテキスト長上限）」をここで解消する。

前提とする上限（着手時に実測で確認する。未決事項2）:

| 対象 | 上限 |
| --- | --- |
| `header` の `plain_text` | 150 文字 |
| `section` の `text` (mrkdwn) | 3,000 文字 |
| `section` の `fields`（各要素 / 個数） | 2,000 文字 / 10 個 |
| `button` の `text` / `value` | 75 文字 / 2,000 文字 |
| 1 メッセージの blocks | 50 個 |
| `confirm` の `title` / `text` | 100 文字 / 300 文字 |

方針:

- **本体は要約のみ。** 対象環境・操作・対象リソース・違反規則・Trace ID・`reason` の先頭。
- **全文はスレッド返信**（`thread_ts`）に置く。それでも上限を超える場合は切り詰め、
  **「切り詰めた」ことを本文に明示する**（黙って切ると、人間は全部を見たと誤解する）。
- **Slack は保管先ではない。** 正本はストア（`event_json`）とローカルの構造化ログである。
  この位置づけを明示しておかないと、通知の長さ制限がエビデンスの欠落に直結する。
- **マスキングは送出前に必ず通す**（`slack/masking.py`）。対象は AWS のアクセスキー ID /
  シークレット・`Bearer` トークン・`xox[baprs]-` で始まる Slack トークン・
  URL に埋め込まれた `user:password`。LLM の `reason` や `raw_output` に混入しうる。
  マスキングは純関数として pytest で固める（S-06）。
  **マスキングはストアには適用しない**（監査の正本は原文であるべきで、隠すのは送出先だけ）。

### 3.9 通知の失敗は遮断の成立と分けて扱う（[D-022](../../decisions.md)）

Slack への送出が失敗しても、**第2層・第3層の判定は成立している**。
アクションは実行されていないし、ログとストアには残っている。失敗しているのは「人間に届けること」だけである。
しかし運用上、これはもっとも危険な状態になりうる。**止めたことを誰も知らない**からである。

- 送出の例外は握り潰さない。`event=slack.failed` を構造化ログに出し、ストアの `status` を
  `notify_failed` に、`message_ts` を NULL のままにする（実行の失敗と区別する。3.5.1）。
- **終了コード 5 を追加する。** 5 > 4 > 3 > 1 > 0 の順で重い（`--repeat` は最も重いものを返す）。
  「遮断はできたが人間に届いていない」を、遮断できたこと（3 / 4）と区別して表面化させる。
- **自動再送はしない**（1. 非目的）。別経路（PagerDuty 等）へのフォールバックも実装せず、提言に書く。
- `SLACK_BOT_TOKEN` が未設定のときは送出せず、`event=slack.skipped` を出して**終了コードは変えない**。
  未設定は障害ではなく構成であり、Phase 1〜3 の経路をそのまま再現できる必要がある。

### 3.10 メッセージ状態の動的更新（運用原則5）

押下直後に `chat.update` で `actions` ブロックを**削除**し、
`[承認済み] 担当: <@U…> (14:02)` のような context 行に差し替える。非活性化ではなく削除を採る
（Block Kit のボタンに disabled 状態が無く、「押せるように見えるが押せない」が最悪の UI になるため）。

`chat.update` に失敗した場合、**ストアの状態を正とする**。UI が古いまま残るが、
次の押下は CAS で弾かれるので二重実行にはならない。この非対称（状態は正しいが表示が古い）を
E-04 で観測し、UI を状態機械の正本にしてはいけないことの実例として記録する。

### 3.11 TTL 満了検知ジョブ（`slack/expire.py`）

仕様書の注記どおり、**ストアからの能動通知ではなく、走査ジョブが期限切れを拾う**形にする。
PoC では cron を使わず手動実行の CLI とする（検証の再現性のため）。

```bash
python -m slack.expire          # 期限切れを closed_expired にし、二次エスカレーションを送る
python -m slack.expire --dry-run  # 対象の一覧だけ出す
```

- TTL は 15 分（`SLACK_APPROVAL_TTL_SECONDS`）。承認者の稼働時間帯で調整すべき値であることは提言に書く。
- 満了したエントリは `chat.update` で `[期限切れ / 未実行]` に更新し、**再通知を送る**。
- 再通知は TTL 満了のときだけ行う。送出に失敗したエントリ（`status='notify_failed'`）の再送はしない（3.9）。

### 3.12 障害注入（`agents/` と `slack/` を変更しない）

Phase 1〜3 と同じ原則。**異常系はエージェントと通知層の外側の設定だけで作る**。

| シナリオ | 注入方法 | 注入が効いていることの確認（[D-018](../../decisions.md)） |
| --- | --- | --- |
| E-01 Slack 不達（timeout） | `SLACK_API_BASE_URL` を `mocks/fault_injector.py`（`FAULT_MODE=timeout`）に向ける | injector のアクセスログに `chat.postMessage` の行があること |
| E-02 Slack 5xx | 同上（`FAULT_MODE=server_error`） | 同上 |
| E-03 無効トークン | `SLACK_BOT_TOKEN` に無効値を入れる（Slack が 200 + `{"ok": false, "error": "invalid_auth"}` を返す） | 応答本文に `invalid_auth` が記録されていること |
| E-04 `chat.update` 失敗 | 送出は実 Slack、更新だけ injector に向ける（押下後に `SLACK_API_BASE_URL` を差し替えて handler を再起動） | injector のアクセスログに `chat.update` があること |
| G-05 署名検証の無効化（対比） | 検証用フラグ | **無効化した状態で改変ペイロードが通ること**を記録する |
| G-06 Slack の再送 | 同一 payload を署名つきで 2 回投入し、2 回目に再送ヘッダを付ける | 2 回とも handler に到達したこと（受信ログ 2 行）と、`executed_at` が 1 回しか書かれないこと |
| A-04 TTL 満了 | `SLACK_APPROVAL_TTL_SECONDS=60` で短縮 | ストアの `expires_at` が実際に過去であること |
| T-05 TOCTOU | ストアに `created_at` を過去の値で直接書き込む | 書き込んだ値を `SELECT` で確認してから承認する |

`mocks/fault_injector.py` は**改修しない**。Slack Web API は `POST` に応答すればよく、
既存の `timeout` / `server_error` モードはパス非依存に応答するため、`base_url` を向けるだけで流用できる。
Phase 1〜3 のモードには一切手を入れない（再現性を保つ）。

**注入が効いていることの確認は「届いたこと」で行う**（[D-018](../../decisions.md)）。
Phase 3 では `restart` で設定が切り替わらず偽の不合格が出た。Phase 4 は
`SLACK_API_BASE_URL` をホスト側の環境変数で切り替えるためコンテナの再生成は不要だが、
**handler は常駐プロセスなので、環境変数を変えたら必ず再起動する**。これが同じ罠の Phase 4 版である。

### 3.13 CLI と終了コード

`--prompt`（Phase 1）と `--incident`（Phase 2・3）の呼び出し方は変えない。

```bash
python -m agents.main --incident "..."              # 送出する（SLACK_BOT_TOKEN があれば）
python -m agents.main --incident "..." --no-slack   # 送出しない（Phase 3 の経路を再現する）
python -m slack.handler                             # 受信プロセス（常駐）
python -m slack.expire                              # TTL 満了検知ジョブ
```

| 終了コード | 意味 | 変更 |
| --- | --- | --- |
| 0 | `allow: true` → 実行層（dry-run）まで到達 | — |
| 1 | 第1層の呼び出し失敗、または第2層の `ValidationError` | — |
| 2 | 環境変数の設定不足 | — |
| 3 | 第3層が `allow: false`（通知は成功） | — |
| 4 | 第3層が評価不能（通知は成功） | — |
| **5** | **エスカレーションの送出に失敗した（遮断は成立している）** | **Phase 4 で追加** |

**通知パターン1（第1層の全滅）を扱わない理由**を終了コードの観点から書いておく。
第1層が全経路で失敗したとき、エージェントが知っているのは「呼び出しが失敗した」ことだけであり、
**どのエンドポイントがどう落ちたかは LiteLLM の内側にある**。
仕様書がパターン1 を「【独立経路】」としているのはそのためで、
これは LiteLLM 自身の alerting（`general_settings.alerting`）が担うべきものである。
エージェント側から「インフラ全滅アラート」を組み立てると、**持っていない情報を推測して書く**ことになる。
C-02 で構造だけ確認し、実装は提言に回す。

### 3.14 Slack の 3 秒ルールと二重配信（[D-024](../../decisions.md)）

Slack は Webhook の応答が **3 秒**を超えるとタイムアウトとみなし、**同じペイロードを再送する**
（`X-Slack-Retry-Num` / `X-Slack-Retry-Reason` ヘッダが付く）。
**人間が 1 回しか押していなくても、受信側には複数回届きうる。**
これはキューの at-least-once 配信と同じ構造の問題が、**キューを置かなくても起きる**ということである。

- **`ack()` を最初に呼ぶ。** 署名検証の直後、ストアに触る前に応答を返す。
- **再送は二重押下と同じ経路で弾く。** ストアの CAS が守る（3.5）。
  再送を異常として扱わない。Slack 側の正常な動作である。
- **二重押下の検証は、人間の連打より再送のほうが決定的に再現できる。**
  A-03（実機の連打）はタイミング依存だが、**G-06（再送ヘッダつきの同一 payload）は pytest で固定できる**。
  判定基準の主軸は G-06 に置き、A-03 は実機での確認に留める。

**受信と実行を分けない**（[D-024](../../decisions.md)）。実運用の構成では、
受信（署名検証・ステート更新）と実行（インフラ API 呼び出し）をキューで分離し、
受信側が常に数百ミリ秒で応答できるようにする。本 PoC で分けないのは、
**実行層が dry-run ログの出力だけで、3 秒に対して桁が 5 つ違う**ためである。
分離しない前提が崩れる条件を明示しておく: **実行が実 API 呼び出しになった時点で成立しなくなる**。
Phase 5 で実行が本物になるなら、そこで分離の設計が要る。

## 4. 検証シナリオ

### 4.1 Block Kit 生成（S 系。pytest・Slack 不要・決定的。判定基準の主軸）

ワークスペースを一切使わずに実行できることが 1.「証明すること」5 の主張そのものなので、
**単体を先に完成させる**（Phase 2・3 と同じ順序）。

| ID | 内容 | 期待 |
| --- | --- | --- |
| S-01 | `validation_failed` から生成（通知パターン2） | ヘッダ・Trace ID・エラー種別・`raw_output` の要約を含む。**`actions` ブロックが無い** |
| S-02 | `policy_denied`・違反 1 件（パターン3） | 環境 / 提案コマンド / 違反規則 / 理由 / Trace ID が揃い、承認・却下ボタンがある |
| S-03 | `policy_denied`・違反 **複数件**（B-01 の実データ） | 違反が**すべて**表示される（箇条書きの section。1 件に要約しない）。Phase 3 考察6 への回答 |
| S-04 | `policy_unavailable` から生成（パターン4） | 失敗モードと不達先を含む。**`actions` ブロックが無い**（判定基準2） |
| S-05 | 上限に当たる入力（`reason` 1,000 文字 / `raw_output` 数千文字 / 違反 6 件） | 各ブロックが上限内、blocks ≤ 50、**切り詰めた旨が本文に出る** |
| S-06 | 秘匿情報を含む `reason` / `raw_output`（AWS キー・Bearer・`xoxb-`・URL 埋め込み認証） | 生成された JSON 全体を走査して**原文が 1 箇所も残っていない** |
| S-07 | 全パターンの生成物を走査 | `value` が Trace ID **のみ**。コマンド文字列・namespace・operation が `value` に入っていない |
| S-08 | 生成物の構造 | 既知の `type` のみ / 必須キーが揃う / Block Kit Builder に貼って表示できる（目視は補助） |

### 4.2 ステートストア（T 系。pytest・Slack 不要・決定的）

| ID | 内容 | 期待 |
| --- | --- | --- |
| T-01 | `pending` のエントリに対し、**同時に 2 つの承認**を投入 | 成功は 1 つだけ。もう一方は競合として扱われる |
| T-02 | 却下 | `rejected` に遷移し、以降の承認を受け付けない |
| T-03 | TTL 満了後の承認 | 受け付けない。満了ジョブで `expired` になる |
| T-04 | 実行済み Trace ID への再要求 | 無視される（`executed_at` が立っている） |
| T-05 | `created_at` が 5 分より前のエントリの承認 | **実行中止**（TOCTOU）。`stale` に遷移し、理由が記録される |
| T-06 | 再試行時のアクション復元 | 常に `event_json` から復元される。ペイロードの値は使われない |
| T-07 | `event_json` を壊したエントリの承認 | 実行層に到達せず `ValidationError`（[D-020](../../decisions.md) の再検証が効く） |

### 4.3 署名検証（G 系。pytest。Slack 不要）

handler に HTTP リクエストを直接投入して確認する。

| ID | 内容 | 期待 |
| --- | --- | --- |
| G-01 | 正しい署名 | 処理される（200） |
| G-02 | 署名ヘッダが無い | 401。ストアは一切変化しない |
| G-03 | 本文を改変（署名は元のまま） | 401。ストアは一切変化しない |
| G-04 | タイムスタンプが 5 分より古い（リプレイ） | 401 |
| G-05 | **対比**: 署名検証を無効化した状態で G-03 と同じ改変要求を送る | **通ってしまう**ことを記録する（防御の効果を実測で示す） |
| G-06 | 同一の正当な payload を **`X-Slack-Retry-Num: 1` つきで再送**（Slack の 3 秒ルールによる再送） | 実行は **1 回だけ**。2 回目は CAS で弾かれ、`executed_at` が書き換わらない |

### 4.4 実機の正常系（P 系。実ワークスペース）

| ID | 入力 | 期待挙動 |
| --- | --- | --- |
| P-01 | Phase 3 の B-01（本番 PVC 削除）を `--incident` 経路で | パターン3 が投稿される。ストアに `pending` が 1 件。終了コード 3 |
| P-02 | Phase 2 の V-01（散文）を `FAULT_MODE=malformed` 経路で | パターン2 が投稿される。**ストアにエントリが作られない**。終了コード 1 |
| P-03 | Phase 3 の X-01（OPA 停止） | パターン4 が投稿される。**ボタンが無い / ストアにエントリが作られない**。終了コード 4 |

### 4.5 実機の承認フロー（A 系。実ワークスペース）

| ID | 操作 | 期待挙動 |
| --- | --- | --- |
| A-01 | P-01 の通知で ［承認して実行］ → confirm で実行 | ストアから復元 → 第2層で再検証 → `event=execution.dry_run` が出る → `chat.update` でボタンが消える → 監査に `policy_override` |
| A-02 | ［提案を却下］ | `rejected`。`chat.update` で却下済み表示。実行層のログは出ない |
| A-03 | 同一通知を**連打 / 2 人で同時に**押す | 実行は 1 回だけ。2 回目には競合の警告が返る |
| A-04 | TTL を 60 秒に縮め、放置してから `python -m slack.expire` | `expired` に遷移し、`chat.update` と**二次エスカレーションの再通知**が出る |
| A-05 | 承認者リストに無いユーザが押下 | 実行されない。エフェメラルで拒否され、監査に `denied_by_rbac` が残る |

### 4.6 異常系・限界・決定性・計測・比較

| ID | 分類 | 内容 | 期待 | 判定基準に使うか |
| --- | --- | --- | --- | --- |
| E-01 | 送出障害 | Slack API が無応答（timeout） | 終了コード 5。`event=slack.failed`。**遮断は成立**（実行層のログが無い） | **使う** |
| E-02 | 送出障害 | Slack API が 5xx | 同上 | **使う** |
| E-03 | 送出障害 | 無効トークン（`ok: false`） | 同上。`ok:false` を成功と誤認しないこと | **使う** |
| E-04 | 更新障害 | `chat.update` だけ失敗 | 承認・実行は成立し、UI だけが古い。ストアが正であること | **使う** |
| N-01 | 限界 | ストアの `event_json` を直接書き換えてから承認する | 再検証で弾ける改変（型違反）と、**弾けない改変（型として正しい別アクション）**があることを示す | **使う**（限界の明示） |
| N-02 | 限界 | handler プロセスを停止した状態でボタンを押す | Slack 側は「エラー」表示。**エージェント側には何も残らない**（通知経路の単一障害点） | **使う**（限界の明示） |
| D-01 | 決定性 | 固定した `EscalationEvent` から Block Kit を 10 回生成（別プロセスを含む） | SHA-256 が完全一致 | **使う** |
| L-01 | 計測 | `chat.postMessage` のレイテンシを実測（n ≥ 20）し、Slack API の `timeout` を決める | — | 使わない（計測） |
| C-01 | 比較 | Socket Mode にすると何が検証できなくなるか | — | 使わない（考察） |
| C-02 | 比較 | 通知パターン1 を LiteLLM 自身の alerting で出す構成 | — | 使わない（考察） |

**L-01 の位置づけ**: Phase 2 で「`timeout` はワークロードごとに実測して決める」、
Phase 3 で「実測した結果、変える必要がないこともある」を得ている。
Slack Web API は外部 SaaS であり、第1層（秒）と第3層（ミリ秒）の中間にあるはずだが、
**桁を仮定せずに実測してから決める**。短すぎれば届いているのに失敗と判定し、
長すぎればインシデント処理が通知待ちで止まる。

**C-01 の位置づけ**: Socket Mode は公開 URL が不要で運用は楽だが、
**署名検証という検証対象が原理的に消える**（WebSocket + app-level token になるため）。
運用原則2 の半分が検証できなくなることを構造の比較として記録する。
「楽な構成を選ぶと、何を証明できなくなるか」は本 PoC の主要な論点である。

### 4.7 実施順序

S 系（Block Kit 単体）→ T 系（ストア単体）→ G 系（署名検証）→ P 系（実機の通知）
→ A 系（承認フロー）→ E 系（送出障害）→ N 系（限界）→ D-01（決定性）→ L-01（計測）→ C 系（考察材料）。

単体を先に固める。実機から始めると、通知が出ない原因が Block Kit の構造なのか、
スコープなのか、ngrok なのか、署名なのかを切り分けられなくなる（Phase 2・3 と同じ理由）。

## 5. 判定基準

以下を**すべて**満たしたとき Phase 4 合格とする。

1. **S-01〜S-08 と T-01〜T-07 が pytest で全件パスする。**
   Block Kit とステート遷移が、**ワークスペース無しで**決定的に検証できること。
2. **通知パターンの作り分けが正しい。** `policy_denied` にだけ承認・却下ボタンがあり、
   `validation_failed` と `policy_unavailable` には `actions` ブロックが存在しない。
   **パターン3 には違反が複数件そのまま表示される**（1 件に要約しない。Phase 3 考察6）。
   パターン4 にボタンが 1 つでもあれば不合格（[D-015](../../decisions.md) を UI で崩すことになる）。
3. **ボタンの `value` が Trace ID のみである。** 全パターンの生成物を機械的に走査し、
   実行内容（operation / namespace / リソース名）が `value` に含まれないこと。
4. **G-01〜G-04 が期待どおりで、署名検証を通らない要求によってストアが 1 レコードも変化しない。**
   G-05（無効化時の対比）が記録されていること。
5. **A-01 で、実行されるアクションがストア由来である。** 承認から実行層（dry-run）まで到達し、
   `policy_override` が監査に残ること。Slack のペイロードの値が実行に使われていないことを、
   T-06 と合わせて示せること。
6. **承認ステートが一貫している。** **G-06（Slack の再送）と A-03（連打）のどちらでも実行は 1 回だけ**、
   A-04 で満了後は承認できず、T-04 で実行済みは再実行されない。
   ステートの語彙（3.5.1）が実装と一致し、**送出の失敗（`notify_failed`）と実行の失敗が別の値である**こと。
7. **A-01 / A-02 の直後に `chat.update` でボタンが消え、`conversations.history` の読み戻しで確認できる。**
8. **E-01〜E-03 で、送出失敗が握り潰されない。** 終了コード 5 と `event=slack.failed` が出力され、
   かつ **実行層のログが出ていない**（遮断そのものは成立している）こと。
9. **D-01 で、同一イベントから生成した Block Kit が完全に一致する。**

**判定基準に使わないもの**: L-01（計測）、C-01 / C-02（構造比較）、通知の見た目、
実 LLM が生成する `reason` の内容（非決定的。経路が繋がることだけを見る）。

| プロセスの終了コード | `echo $?` | 判定基準8 |
| injector のアクセスログ | `chat.postMessage` / `chat.update` が実際に注入先へ届いたこと | E 系すべての前提（D-018） |
| ngrok の Inspector（`http://127.0.0.1:4040`） | Slack から来た生リクエスト（ヘッダを含む） | G 系の裏取り |

### 「届いたこと」の証拠を先に決める（[D-018](../../decisions.md) の Phase 4 版）

Phase 3 の申し送り「Slack 経路でも『届いたことの証拠』を先に決めてから実行する」への回答。

| 方向 | 「送った / 受けた」の弱い証拠 | **採用する証拠** |
| --- | --- | --- |
| 送出 | `chat.postMessage` が例外を投げなかった | 応答の `ok: true` と `ts`、**かつ `conversations.history` で同じ `ts` の blocks を読み戻せること** |
| 受信 | handler のプロセスが起動している | **受信した payload の生 JSON がログにあり、その `value` が該当 Trace ID であること** |
| 更新 | `chat.update` が例外を投げなかった | 読み戻した blocks に `actions` が**無い**こと |
| 注入 | injector のコンテナが起動している | injector のアクセスログに当該メソッドの行があること |

**`ok: false` を成功と誤認しないこと。** Slack Web API は失敗しても HTTP 200 を返す。
これは Phase 3 の X-04（OPA が 200 + `result` 無しを返す）と同じ形の罠であり、
**HTTP ステータスだけを見る実装は、静かに沈黙する**。E-03 はこれを踏むためのシナリオである。

生データは `assets/` に置き、result.md から参照する。**ファイル名は使い回さない**（Phase 1 の失敗）。
**Slack のトークン・署名シークレット・ワークスペースの実 ID・実ユーザ名は `assets/` に貼る前に除去する**
（docs/README.md 運用ルール2）。ngrok の Inspector の出力には署名ヘッダがそのまま含まれる。

## 7. 未決事項・確認事項

着手時に確認し、判明した内容は result.md に記録する。設計判断が変わる場合は decisions.md を更新する。

1. **Slack Web API のレイテンシと `timeout` の確定値。** → L-01 で実測。初期値は 10.0 秒。
2. **Block Kit の実際の上限**（3.8 の表）と、超過時の Slack の挙動（`invalid_blocks` で 400 か、黙って切るか）。
   黙って切られる場合、S-05 は「切り詰めが効いていること」を別の方法で示す必要がある。
3. **必要な Bot スコープ。** `chat:write` は確定。読み戻しに `channels:history`（public）か
   `groups:history`（private）か、エフェメラル送信に何が要るか、スレッド返信に追加が要るかを確認する。
4. **Bolt の組み込みサーバ（`App.start()`）で足りるか。** Flask 等の Web フレームワークを増やしたくない
   （[D-001](../../decisions.md) と同じ態度）。足りない場合に何を足すかを決める。
5. **署名検証を単体テストからどう呼ぶか。** `slack_sdk.signature.SignatureVerifier` を直接使うのか、
   handler に HTTP を投げるのか。**G 系は「弾かれること」ではなく「処理に到達しないこと」を見たい**ので、
   ストアの変化まで観測できる呼び方を選ぶ。
6. **SQLite の同時アクセス。** Bolt が複数スレッドで処理する場合の `check_same_thread` と
   ロック待ち（`timeout`）の扱い。T-01 の「同時 2 つ」を何で再現するか（スレッド / プロセス）。
7. **ngrok の URL が変わるたびに Slack App の Request URL を張り替える必要があるか。**
   毎回張り替えるなら、シナリオの実施順序に影響する（検証を止めずに一気に流せるか）。
8. **`chat.update` の対象 `ts` を送出失敗時にどう扱うか。** `message_ts` が NULL のエントリは
   更新できない。満了ジョブがこれを拾ったときの挙動（新規投稿にするか、スキップするか）を決める。
9. **エフェメラルメッセージ（RBAC 拒否）が Interactivity の `response_url` で送れるか**、
   `chat.postEphemeral` が要るか。後者ならスコープが増える。
10. **実行層を handler プロセスから呼ぶことの是非。** `agents/execution.py` を切り出して共有するが、
    **エージェント本体と承認経路で「実行」の意味が同じであること**を確認する。
    Phase 5 で実行が本物になったとき、この共有が正しい形かを見ておく。
11. **`EscalationEvent` に承認期限・承認者ロールの判定材料を足すか**（Phase 3 確認事項6 の宿題）。
    本設計ではストア側に持たせた（`expires_at`）。イベントに足さなくて足りたかを結論づける。
12. **Bolt の組み込みサーバで `ack()` がいつ返るか**（3.14）。リスナー内で `ack()` を呼んだ時点で
    応答が返るのか、ハンドラの戻りまで待つのか。後者なら実行層が重くなったときに 3 秒を超える。
    PoC の dry-run では超えないが、挙動は確認して記録する。
13. **`X-Slack-Retry-Num` の再現方法**（G-06）。実機で意図的に 3 秒を超えさせるのは難しいため、
    pytest から再送ヘッダつきの同一 payload を投入する形で足りるかを確認する。
    実機で再送が観測できた場合はログを残す。
14. **通知パターン3 の違反表示。** 複数件を section の箇条書きで並べたとき、
    実際に読みやすいか（Phase 3 考察6 は前者を推奨としたが、実機で確認していない）。
