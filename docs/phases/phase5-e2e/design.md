# Phase 5 設計: E2E 統合と実行層の実体化

> このドキュメントは**着手前**に確定させるもの。検証後に判定基準を書き換えない。
> 予想と異なる結果になった場合は [result.md](result.md) の「考察」に記録する。
>
> 本フェーズで初めて**実行層が本物になる**。これまで 4 フェーズは「止めること」を検証してきたが、
> Phase 5 は「通したものが本当に世界を変えること」と、**変えた／変えていないが分からない状態**を扱う。

関連: [D-001](../../decisions.md) フレームワークを入れない（本フェーズで再検討する）/
[D-002](../../decisions.md) 構造検証と権限判定の分離 /
[D-012](../../decisions.md) 自動修復リトライを入れない /
[D-015](../../decisions.md) deny と評価不能を構造的に分ける /
[D-018](../../decisions.md) 注入は「届いたこと」で確認する /
[D-020](../../decisions.md) 承認内容はストアから復元し再検証する /
[D-021](../../decisions.md) 出し分けを操作の種別で行わない /
[D-024](../../decisions.md) 受信と実行を分けない（**本フェーズで前提が崩れる**）/
本フェーズで確定させる判断: **D-026**（破壊的操作の禁止を実クラスタに限定する）/
**D-027**（Slack の受信プロセスに実行権限を持たせない）/
**D-028**（実行結果を 3 分類し、実行有無が不明なものを自動再試行しない）/
**D-029**（再開はエージェントの思考ではなくアクションの実行から行う）/
**D-030**（実行層は kubectl のサブプロセスではなく Kubernetes API クライアントで実装する）

## 0. Handoff 仕様書との対応（どこまでを Phase 5 で扱うか）

Phase 3 は「図1 の第3層の 3 分岐」と「図3 の入口まで」、Phase 4 は「図3 の本体と通知パターン 2 / 3 / 4」を担当した。
**Phase 5 は残り全部**である。すなわち実行層の実体、通知パターン5、中断・再開、そして通しの E2E。

| 仕様書の要素 | Phase 5 で扱うか | 扱い方 / 扱わない理由 |
| --- | --- | --- |
| 図1 の全経路を**通しで**流す | **扱う（本フェーズの主題）** | 1 本のインシデントが入口から実クラスタの状態変化まで到達する（Z 系） |
| 実行層（インフラ API の発行） | **扱う（本フェーズの目玉）** | 使い捨ての kind クラスタに対して**実際に発行する**（[D-026](../../decisions.md)） |
| 通知パターン5（実行時エラー・再試行） | **扱う** | `kind="execution_failed"` / `"execution_unknown"` から生成。**再試行ボタンが出るのは前者だけ** |
| 図3「中断・再開」 | **扱う** | 再開は**承認済みアクションの実行**から行う。LLM は呼び直さない（[D-029](../../decisions.md)） |
| 運用原則4「再試行の同一性」 | **扱う** | `retry_count` を持ち、再試行も必ずストアから復元して再検証する（[D-020](../../decisions.md) のまま） |
| 付帯要件 TOCTOU | **扱う（実体を伴う形で）** | Phase 4 は経過時間だけで測った。Phase 5 は**承認待ちの間に実際にクラスタを変える**（Z-06 / N-01） |
| 付帯要件 RBAC（クラスタ側） | **扱う** | 第3層が許可しても ServiceAccount の権限が無ければ実行できない（R 系。Phase 3 提言5 の実証） |
| 受信と実行の分離 | **扱う** | [D-024](../../decisions.md) の「分離しない前提」が実行の実体化で崩れる。[D-027](../../decisions.md) で分離する |
| 通知パターン1（インフラ全滅） | **扱わない（が、E2E では流す）** | 実装しない理由は Phase 4 3.13 と同じ。ただし **E2E で第1層を全滅させ、「Slack に何も出ない」ことを記録する**（Z-05）。多層防御のうち人間に届かない唯一の層であることを、通しで見て初めて言える |
| 運用原則1〜3・5 | 扱わない（Phase 4 で完了） | 回帰として流すだけ。判定基準は Phase 4 のものを使う |
| エージェントのマルチターン化・再計画 | **扱わない** | [D-029](../../decisions.md)。再開で LLM を呼び直すと、承認した内容と実行内容が変わる（運用原則2 違反） |

**この表の要点**: Phase 1〜4 は「層が単体で効くこと」を証明してきた。Phase 5 の固有の問いは
**層を重ねたときに初めて現れるもの**だけである。すなわち (a) 通した結果が本当に世界を変えるか、
(b) 変えたかどうかが分からない状態をどう扱うか、(c) 止めたものを人間が通すときに**最後の砦が残っているか**。

## 1. 目的と非目的

### 証明すること

1. **1 本のインシデントが、入口から実クラスタの状態変化まで全層を通って完結する。**
   第1層 → 第2層 → 第3層 → 実行層が繋がり、**クラスタ側から観測できる変化**が起きる（Z-01）。
   「ログに出た」ではなく「`kubectl` で見える」ことをもって到達とする（層の外側からの裏取り。[D-009](../../decisions.md)）。
2. **各層の失敗が、E2E でも対応する通知に着地し、人間の押下で安全に再開・中断する。**
   パターン 2 / 3 / 4 / 5 が実際の層の失敗から出ること。そして**止まっている間、クラスタは 1 ミリも動いていない**こと。
3. **実行が本物になっても、安全網の最後の 1 枚が残っている。**
   第3層が `allow: true` を返しても、人間が `policy_override` で承認しても、
   **ServiceAccount に権限が無ければ実行されない**（R 系）。
   これは Phase 3 の N-01（エージェントは `environment` を詐称できる）に対する構造的な回答である。
4. **実行の結果が「成功」「確定的な失敗」「実行有無が不明」の 3 つに分かれる。**
   そして**不明なものを自動で再試行しない**（[D-028](../../decisions.md)）。
   Phase 4 は語彙だけ決めて到達しなかった `execution_failed` / `unknown` に、ここで実際に到達する。
5. **中断・再開がフレームワーク無しで成立する。**
   再開に必要なのはストアの 1 列であって、思考のチェックポイントではない（[D-029](../../decisions.md)）。
   これは [D-001](../../decisions.md)（フレームワークを入れない）の「Phase 5 で再検討」に対する結論になる。
6. **承認を受ける権限と、実行する権限が分離されている。**
   `slack/handler.py` はクラスタの資格情報を持たない。
   「承認ボタンを押せる = handler の権限で何でもできる」という結合が存在しないこと（[D-027](../../decisions.md)）。

### 証明しないこと（意図的にスコープ外）

- **実運用クラスタでの動作。** 対象は使い捨ての kind のみ。`kind delete cluster` で消せることが前提（[D-026](../../decisions.md)）。
- **エージェントのマルチターン化・再計画・長期記憶。** LLM は 1 インシデントにつき 1 回しか呼ばない（[D-029](../../decisions.md)）。
- **キュー製品の導入。** 受信と実行は分離するが、間に置くのは既存の SQLite であって SQS ではない（3.4 / C-01）。
- **分散ワーカー。** Executor は 1 プロセス。複数ワーカーでの排他は提言に回す。
- **k8s 操作の網羅。** 第2層の語彙にある 7 操作だけ。新しい操作を足すことは本フェーズの目的ではない。
- **ロールバック・補償トランザクション。** 失敗した実行を元に戻す機構は作らない。
- **通知パターン1 の実装**（0 章の表）。
- **Phase 1〜4 の再検証。** 回帰として流すが、各シナリオの判定基準はそれぞれの design.md のものを使う。
  Phase 5 の判定基準は「重ねても壊れていないこと」だけを見る。

## 2. 構成

### 2.1 E2E の全体像

```
  [人間] インシデント記述
      │
      ▼
  agents/main.py ──▶ 第1層 LiteLLM ──▶ 第2層 JSON Validator ──▶ 第3層 OPA
      │                   ✗                    ✗                     ✗ / deny
      │                   │                    │                     │
      │             （通知しない）        パターン2            パターン3 / 4
      │              Z-05 で記録           ボタン無し        承認ボタン / ボタン無し
      │                                        │                     │
      │ allow: true                            └────────┬────────────┘
      ▼                                                 ▼
  agents/execution.py ──────────▶ kind クラスタ      Slack（人間）
      │  （自律経路。main が呼ぶ）      ▲                  │ ［承認して実行］
      │                                 │                  ▼
      │ 実行失敗                        │          slack/handler.py
      ▼                                 │            （資格情報を持たない）
   パターン5 ◀────────────────┐         │                  │ approved にするだけ
                              │         │                  ▼
                              │         └──── agents/executor.py ◀── ストア（SQLite）
                              └───────────────  （唯一 kubeconfig を持つ常駐プロセス）
```

**実行の入口は 2 つあるが、実行そのものは 1 つの関数に集約する**（`agents/execution.py`）。
自律経路（`main`）と承認・再試行経路（`executor`）で「実行」の意味が変わってはいけない（Phase 4 未決事項10 の継続）。

### 2.2 プロセスと権限

| プロセス | 役割 | クラスタ資格情報 | 常駐 |
| --- | --- | --- | --- |
| `agents/main.py` | 第1層〜第3層 + 自律経路の実行 | **持つ** | いいえ（1 インシデントで終了） |
| `slack/handler.py` | Slack Interactivity の受信・ステート遷移 | **持たない**（[D-027](../../decisions.md)） | はい |
| `agents/executor.py` | 承認済み・再試行待ちの実行 | **持つ** | はい |
| `slack/expire.py` | 承認期限の満了検知 | 持たない | いいえ（CLI） |
| kind クラスタ | 検証対象のインフラ | — | はい |
| LiteLLM / OPA / fault-injector | 第1層・第3層・障害注入 | — | はい（Docker Compose） |

**エージェント本体（LLM を呼ぶプロセス）が資格情報を持つことは許す。** architecture.md の図どおり、
実行層はエージェントの下流にある。分離の主張は「**Slack の受信プロセスが実行できないこと**」に限定する。
これは Phase 4 提言5 の文言そのものである。

### 2.3 このフェーズで「信じないもの」

| 信じないもの | 具体的な対処 | 対応シナリオ |
| --- | --- | --- |
| **クラスタの状態** | 提案時と実行時で変わっている前提で扱う。TOCTOU 閾値で古い承認を落とす | Z-06 / N-01 |
| **自分の権限** | `allow: true` は「ポリシー上許される」であって「実行できる」ではない。403 を正常な結果として扱う | R 系 |
| **実行の結果** | 例外が出なかった＝成功ではない。**応答が無かった＝実行されていない、でもない** | X 系 / [D-028](../../decisions.md) |

3 つ目が本フェーズの核心である。第2層は LLM の出力を、第3層は OPA の応答を、Phase 4 はストアを信じなかった。
Phase 5 で信じないのは **「実行が成功した／失敗した」という自分自身の認識**である。
クライアントから見えるのは応答の有無だけであり、**サーバが何をしたかは原理的に分からない**。

## 3. 設計

### 3.1 ファイル構成と依存の向き

```
agents/
├── execution.py     # 変更。dry_run ログ → **実 API の発行**。実行結果を 3 分類して返す
├── k8s.py           # 追加。operation × kind → API 呼び出しのディスパッチ表（判定を書かない）
├── executor.py      # 追加。approved を拾って実行する常駐プロセス（Receiver から分離）
├── main.py          # 変更。自律経路の実行結果を終了コード 6 / 7 に反映
├── schemas.py       # 変更。EscalationEvent の kind に execution_failed / execution_unknown を追加
└── escalation.py    # 変更。パターン5 もストアにエントリを作る（3.6 の不変条件）

slack/
├── blocks.py        # 変更。パターン5 の生成。**ボタンの有無は kind と status だけで決まる**
├── handler.py       # 変更。**agents.execution を import しない**（D-027。pytest で強制する）
└── store.py         # 変更。executing / abandoned の追加、retry_count、execution_started_at

mocks/
└── k8s_proxy.py     # 追加。実行層の異常系（5xx）を注入する。kubeconfig の server を向ける

k8s/                 # 追加。検証用クラスタの定義（マニフェスト。agents/ からは参照しない）
├── kind-cluster.yaml
├── workloads.yaml   #   prod / staging / dev の Deployment・PVC
└── rbac.yaml        #   ServiceAccount sre-agent と最小権限の Role / RoleBinding
```

- **`slack/handler.py` から `agents.execution` への import を外す。** これが [D-027](../../decisions.md) の
  構造的な実体であり、`tests/` で import グラフを検査して固定する。
  Phase 3 で「ポリシーの語彙を `agents/` に書かない」を pytest で強制したのと同じ形。
- **`agents/k8s.py` に `if environment == "production"` を書かない。** 実行層もポリシーを持たない
  （[D-002](../../decisions.md) / [D-021](../../decisions.md) と同じ線）。実行層が知ってよいのは
  「operation と kind から、どの API を呼ぶか」だけである。
- **`k8s/` のマニフェストは `agents/` から参照されない。** クラスタの構成は検証環境の設定であり、
  アプリの関心事ではない（`litellm/` `opa/` と同じ位置づけ）。

### 3.2 実行層の実体化（[D-030](../../decisions.md)）

実行は **Kubernetes の Python API クライアント**で行う。`kubectl` のサブプロセス起動にはしない。

| | API クライアント（採用） | `kubectl` サブプロセス |
| --- | --- | --- |
| コマンド文字列の組み立て | **不要**（引数は型付きで渡す） | 必要。第2層を通った値とはいえ文字列結合が残る |
| 失敗の判別 | **HTTP ステータスが取れる**（403 / 404 / 409 / 5xx） | 終了コードと stderr の文字列解析 |
| 実行有無の判別 | 応答の有無で分けられる（3.5） | タイムアウト時に何が起きたか分からない |
| server-side dry-run | `dry_run="All"` パラメータ | `--dry-run=server` |
| `describe` | **API に存在しない**（3.3） | 存在する（クライアント側の整形） |

採用理由は**失敗の分類が決定的になる**ことに尽きる。本フェーズの中心的な主張（[D-028](../../decisions.md)）は
「実行されたかどうかが分かるか」であり、それを文字列解析に依存させるとその主張自体が確率的になる。
第2層で `strict=True` を選んだのと同じ理由である。

ディスパッチは表で持つ。

```python
# agents/k8s.py（設計イメージ）
DISPATCH: dict[tuple[Operation, str], Callable] = {
    (Operation.GET,        "pod"):        read_pod,
    (Operation.LOGS,       "pod"):        read_pod_log,
    (Operation.DELETE_POD, "pod"):        delete_pod,
    (Operation.SCALE,      "deployment"): patch_deployment_scale,
    ...
}
```

**表に無い組み合わせは実行しない。** 第2層の `Operation` は allow-list であり（`schemas.py`）、
`kind` も `Literal` である。両者の直積のうち意味を持つものだけを表に書く。
表に無い組み合わせ（例: `kubectl_scale` × `pod`）は**確定的な失敗**として扱い、実行を試みない。

### 3.3 `dry_run` が初めて意味を持つ

第2層のスキーマには当初から `dry_run: bool` があり、第3層には `REQUIRE_DRY_RUN_IN_PRODUCTION` がある。
しかし Phase 1〜4 の実行層はログ出力だけだったため、**この値は一度も意味を持っていなかった**。

- `dry_run: true` → API に `dry_run=All` を付けて発行する。**API サーバまで届き、認可も検証も通るが、永続化されない。**
- `dry_run: false` → 通常どおり発行する。**実際にリソースが変わる。**

server-side dry-run を採るのは、クライアント側で「送らない」のでは**何も検証したことにならない**ためである。
送らなければ RBAC も admission も通らず、`dry_run: true` の通知を人間が見て安心する根拠が無い。

**参照系（`get` / `logs`）に `dry_run` は適用されない。** 読み出しに副作用が無いため API にパラメータが無い。
この非対称は実装のコメントと result.md に記録する。

**`kubectl_describe` は API に存在しない。** `describe` は kubectl がリソースと Event を取得して整形する
クライアント側の機能である。実行層では `read_namespaced_*` + 当該リソースの Event 取得で代替し、
**「語彙が kubectl のサブコマンド名に引きずられている」ことを限界として記録する**（未決事項3）。
語彙そのものは変えない。第2層のスキーマを変えると Phase 2・3 の fixture とエビデンスが無効になる。

### 3.4 受信と実行を分離する（[D-027](../../decisions.md)。[D-024](../../decisions.md) の前提が崩れたため）

Phase 4 は受信と実行を同一プロセスに置いた。その根拠は明示されていた
（[D-024](../../decisions.md)「実行が実 API 呼び出しになった時点で成立しない」）。Phase 5 で成立しなくなる。

```
  押下 ─▶ handler ─▶ 署名検証 ─▶ RBAC ─▶ store.approve()（CAS）─▶ chat.update ─▶ 応答
                                                │
                                                │ （ここで終わり。実行はしない）
                                                ▼
                                          ストア（approved）
                                                │ ポーリング
                                                ▼
                                          executor ─▶ store.claim()（CAS）─▶ 実行層 ─▶ 結果を記録
```

- handler の仕事は**ステートを進めることだけ**になる。3 秒ルールに対する余裕は Phase 4 と同じまま保たれ、
  実行の所要時間が handler の応答時間に影響しなくなる（Phase 4 未決事項12 への構造的な回答）。
- **executor は `approved` を `executing` に変える CAS で 1 件を占有してから実行する**（3.5）。
- ポーリング間隔は `EXECUTOR_POLL_SECONDS`（既定 2 秒）。
  **キューではなくポーリングにする**のは、部品を増やさないため（[D-001](../../decisions.md) と同じ態度）。
  実運用でキューに置き換える条件は C-01 に書く。

**分離の証拠は「executor を止めると実行されないこと」ではない**（それは単に動いていないだけ）。
**handler プロセスの環境にクラスタの資格情報が無い状態で承認が成立し、実行が起きること**を証拠とする
（判定基準6）。あわせて import グラフを pytest で固定する（3.1）。

### 3.5 実行結果の 3 分類とステート（[D-028](../../decisions.md)）

**分類は「サーバからの応答があったか」だけで行う。**

| 実行層から見えるもの | 解釈 | ステート | 自動再試行 |
| --- | --- | --- | --- |
| 2xx | 実行された | `executed` | — |
| 4xx（403 / 404 / 409 / 422 / 429 …） | **実行されていない**（サーバが処理しなかったことを応答が示している） | `execution_failed` | しない（人間が再試行を押す） |
| 5xx | **不明**（サーバは受け取ったが、結果を保証していない） | `unknown` | **しない** |
| 応答なし（timeout / 接続断 / TLS エラー） | **不明** | `unknown` | **しない** |
| ディスパッチ表に無い組み合わせ | 実行していない（送っていない） | `execution_failed` | しない |

**接続拒否も `unknown` に倒す。** 「接続が拒否されたのだからリクエストは届いていない」は多くの場合正しいが、
クライアントのライブラリは「接続前の失敗」と「送信後に切られた」を常に区別できるとは限らない。
**過剰に `unknown` に倒すコストは『人間が確認する』だけであり、逆の誤りのコストは二重実行である。**
非対称なコストに対しては、安定して重いほうを避ける。これは第3層の Fail-Closed（[D-015](../../decisions.md)）と同じ形の判断である。

ステートの語彙に 2 つ足す。**既存の値の意味は変えない。**

| ステート | 意味 | 遷移元 | Phase 5 で追加する理由 |
| --- | --- | --- | --- |
| `executing` | 実行を開始したが、結果がまだ記録されていない | `approved` | **これが無いと、executor が実行中に落ちたとき `approved` のまま残り、再起動で再実行される**（＝二重実行） |
| `abandoned` | 実行を試みたあと、人間が「もうやらない」と決めた | `execution_failed` | `rejected`（実行を試みていない状態での却下）と混ぜない。**実行を試みたかどうかは監査上の別事実である** |

列も 2 つ足す。

- `execution_started_at` — 実行を**開始した**時刻。Phase 4 の積み残し（`execution_failed` なのに
  `executed_at` が立つ。考察11）をここで解消する。`executed_at` は**成功時にのみ**立てる。
- `retry_count` — 再試行の回数（3.6）。

**起動時に `executing` のまま残っているエントリは `unknown` に倒す。** executor のクラッシュリカバリは
これだけで足りる。「`executing` のまま残っている」＝「実行を開始した記録はあるが結果が無い」＝
定義どおり実行有無が不明、である。**推測して `approved` に戻してはならない。**

### 3.6 再試行と、再試行してはいけないもの

```
execution_failed ──［再試行］──▶ approved（retry_count + 1）──▶ executing ──▶ …
                 ──［中止］────▶ abandoned
unknown          ──（ボタン無し。終端）
```

- **再試行でも実行内容はストアから復元し、第2層で再検証する**（[D-020](../../decisions.md) のまま）。
  Slack のペイロードからは再構成しない。これが運用原則4「再試行の同一性」である。
- 上限は `EXECUTION_MAX_RETRIES`（既定 3）。超えたら再試行ボタンを出さない。
- **`unknown` には再試行ボタンを出さない。** これは「評価できていない操作に承認ボタンを出さない」
  （[D-015](../../decisions.md) / Phase 4 判定基準2）とまったく同じ形である。
  **実行有無が分からないものに再試行ボタンを出すのは、Fail-Closed を UI で台無しにする行為**である。
- **操作ごとの冪等性で再試行可否を変えない。** `kubectl_delete_pod` は概ね冪等だが
  `kubectl_delete_pvc` は（同名の PVC が再作成されていれば）そうではない。
  この手の分岐を実行層や通知層に書くと、[D-021](../../decisions.md) が禁じた形になる。
  **再試行の可否はステートだけで決まる**。操作ごとの冪等性をポリシーとして持たせる案は提言に書く。

**ボタンの有無を決める条件は、Phase 4 の `kind` に `status` が 1 つ増えるだけ**にする。

| kind | status | ボタン |
| --- | --- | --- |
| `policy_denied` | `pending` | ［承認して実行］［却下］ |
| `execution_failed` | `execution_failed` かつ `retry_count < 上限` | ［再試行］［中止］ |
| `execution_failed` | 上限到達 | ［中止］のみ |
| `execution_unknown` | `unknown` | **なし** |
| `validation_failed` / `policy_unavailable` | （エントリ無し） | **なし** |

### 3.7 ストアの不変条件を一般化する

Phase 4 は「**ストアにエントリがある ⇔ 承認ボタンが存在しうる**」を 1 対 1 に保っていた
（`policy_denied` だけがエントリを作る）。Phase 5 ではパターン5 にもボタンが出るため、これを一般化する。

> **ストアにエントリがあるのは、人間の操作（承認・却下・再試行・中止）を待つものだけである。**

- `validation_failed` / `policy_unavailable` は引き続きエントリを作らない（人間が押せるものが無い）。
- `policy_denied` は従来どおり `pending` で作る。
- **自律経路の実行失敗**（`allow: true` だったのに失敗した）は、`execution_failed` または `unknown` の
  ステートでエントリを作る。`unknown` はボタンが無いのにエントリを作ることになるが、
  **終端ステートの記録として必要**であり、ボタンの有無はステートが決める（3.6 の表）ので矛盾しない。
  この緩みは意図的なものとして明示し、result.md で結論づける（未決事項10）。
- **自律経路の実行成功はエントリを作らない。** 人間の操作を待たないため。

**実行の証跡は `audit_log` に残す。** `audit_log` は `pending_actions` への外部キーを持たない追記テーブルであり、
エントリの無い Trace ID についても記録できる。Phase 4 の設計（3.5.1）が述べた
「監査レコードは運用ステートより寿命が長い」が、ここで実際に効く。

| テーブル | 入るもの |
| --- | --- |
| `pending_actions` | 人間の操作を待つもの（終端に達したら役目を終える） |
| `audit_log` | **すべての実行**（自律・承認・再試行）と、すべての人間の操作 |

### 3.8 中断・再開（[D-029](../../decisions.md)）

仕様書の「エージェント処理の中断・再開」を、本 PoC は次の意味で実装する。

- **中断** = エージェントのプロセスが終了すること。第2層・第3層の失敗でも deny でも同じ（Phase 3 から不変）。
- **再開** = **承認済みアクションを実行すること**。エージェントの思考は再開しない。**LLM を呼び直さない。**

理由:

1. **再開時に LLM を呼ぶと、人間が承認した内容と実行される内容が変わりうる。** 運用原則2
   （承認内容の同一性保証）は、ボタンの `value` を Trace ID に絞るところまで徹底している。
   その同じ経路の末端で LLM に再生成させたら、徹底した意味が無い。
2. **非決定性が戻ってくる。** [D-012](../../decisions.md)（`ValidationError` から再プロンプトしない）と同じ構造。
3. **思考を再開するために必要な機構（チェックポイント・状態機械）は、本 PoC の再開には要らない。**
   再開に必要なのは「どのアクションを、どの状態まで進めたか」だけであり、**ストアの `status` 1 列で足りる**。

3 が [D-001](../../decisions.md)（フレームワークを入れない。「Phase 5 の設計時に再検討の余地あり」）への結論である。
**LangGraph 等の checkpointer が解くのは『思考の再開』であって、本 PoC が必要としているのは『アクションの再開』である。**
両者を混同すると、承認フローに非決定性を持ち込むことになる。C-03 で構造比較として記録する。

**検証可能な形にする**: 承認から実行までの間に、**第1層へのリクエストが 1 本も出ていないこと**を
LiteLLM のログで確認する（判定基準8）。「呼んでいないつもり」ではなく外側から裏取りする。

### 3.9 通知パターン5

`EscalationEvent.kind` に 2 つ足し、`layer` に `"execution"` を足す。

| kind | 出る条件 | 通知に載せるもの |
| --- | --- | --- |
| `execution_failed` | 4xx / ディスパッチ不能 | 何をしようとしたか / HTTP ステータスと理由 / **実行されていないこと** / 再試行回数 |
| `execution_unknown` | 5xx / 応答なし | 同上 + **実行されたかどうか分からないこと** / **クラスタを人間が確認する必要があること** |

- **「実行されていない」と「分からない」を文面で明確に分ける。** ここを曖昧にすると、
  3 分類を実装した意味がすべて消える。パターン5 は 1 種類ではなく 2 種類である。
- 承認経路から出たパターン5 は**元メッセージのスレッドに返す**か新規投稿にするかを決める（未決事項9）。
  Trace ID で辿れることが条件。
- マスキング・切り詰めは Phase 4 の `slack/masking.py` / `truncate()` をそのまま通す。
  **API サーバのエラーメッセージにはトークンや内部ホスト名が混ざりうる**ため、例外はしない。

### 3.10 クラスタと RBAC（Phase 3 提言5 の実証）

kind で 1 クラスタを作り、`prod` / `staging` / `dev` の 3 namespace を置く
（`opa/data.json` の `environment_namespaces` と一致させる。ここを食い違わせると
第3層の `REQUIRE_NAMESPACE_ENVIRONMENT_MATCH` が常時発火して検証にならない）。

ワークロード（`k8s/workloads.yaml`）:

| namespace | 置くもの |
| --- | --- |
| `prod` | Deployment `payment-api`（replicas 2）/ PVC `payment-data` |
| `staging` | Deployment `payment-api`（replicas 1）/ PVC `payment-data` |
| `dev` | Deployment `payment-api`（replicas 1）/ PVC `payment-data` |

ServiceAccount `sre-agent` に与える権限（`k8s/rbac.yaml`）:

| namespace | 参照（get/list, pods/log） | patch deployments + scale | delete pods | delete pvc |
| --- | --- | --- | --- | --- |
| `dev` | ○ | ○ | ○ | **×** |
| `staging` | ○ | ○ | ○ | **×** |
| `prod` | ○ | ○ | **×** | **×** |
| `kube-system` ほか | **×** | **×** | **×** | **×** |

**PVC の削除はどの環境でも与えない。** 第3層の `PROHIBIT_PVC_DELETE` と意図的に重ねる。
人間が `policy_override` で承認しても、**最後に RBAC が止める**ことを示すため（R-01）。
これが「多層防御」の主張の最後の 1 枚であり、**エージェントの自己申告を信じない唯一の防御**でもある
（Phase 3 の N-01 で示した詐称の限界は、クラスタ側の権限でしか塞げない）。

**RBAC の設定を `agents/` から読まない。** エージェントは自分が何をできるかを事前に知らず、
やってみて 403 を受け取る。先に権限を確認する実装にすると、**同じ判定が 2 箇所に生まれる**
（[D-002](../../decisions.md) と同じ形の二重管理）。`SelfSubjectAccessReview` を使わない理由も同じ。

### 3.11 障害注入（`agents/` と `slack/` を変更しない）

Phase 1〜4 の注入経路はそのまま使う。実行層の注入だけが新規。

| シナリオ | 注入方法 | 注入が効いていることの確認（[D-018](../../decisions.md)） |
| --- | --- | --- |
| Z-02（第2層） | 既存。`FAULT_MODE=malformed` + `FAULT_FIXTURE=v01_prose` | injector のアクセスログ |
| Z-04（第3層） | 既存。`docker compose stop opa` | 接続エラーが `PolicyUnavailableError` になっていること |
| Z-05（第1層全滅） | 既存。`config.fault.yaml` + 両デプロイを injector に向ける | injector のアクセスログに 2 系統分の行 |
| **Z-01 の決定性確保** | **既存機構の流用**。`FAULT_MODE=malformed` に**正常な fixture** を指定して content を固定する | injector のアクセスログ。モード名は malformed だが注入内容は fixture 次第 |
| X-01（`unknown` / 応答なし） | **`EXECUTION_TIMEOUT_SECONDS` を極小値にする**（例 0.05） | **クラスタ側で変更が実際に起きていること**。「実行されたのに unknown」になる |
| X-02（`unknown` / 5xx） | `mocks/k8s_proxy.py` を挟み、kubeconfig の `server` を向ける | proxy のアクセスログに当該パスの行 |
| X-03（`unknown` / 接続断） | `docker stop <kind-control-plane>` | クラスタが停止していること |
| R 系（4xx） | **注入しない。本物の RBAC 403 を使う** | API サーバの監査ログ、または 403 の応答本文 |
| Z-06（TOCTOU） | 承認待ちの間に `kubectl delete pod` で対象を消す | 消えたことを `kubectl get` で確認してから承認する |

**X-01 が本フェーズでもっとも重要な注入である。** タイムアウトを極小にすると、
**リクエストは API サーバに届いて実行され、クライアントだけが結果を知らない**状態が決定的に作れる。
`unknown` が「起こりうる」ではなく「現に起きて、しかもクラスタは変わっている」ことを実機で示せる。
proxy を使う X-02 より証拠能力が高く、追加の部品も要らない。

**`mocks/fault_injector.py` は改修しない**（Phase 1〜4 の再現性を保つ）。
実行層の注入は別ファイル（`mocks/k8s_proxy.py`）に置く。注入部品を `mocks/` に置く方針は [D-006](../../decisions.md) と同じ。

### 3.12 CLI と終了コード

```bash
python -m agents.main --incident "..."        # 第1層 → 第2層 → 第3層 → 実行層（本物）
python -m agents.executor                     # 常駐。approved / 再試行を拾って実行する
python -m agents.executor --once              # 1 周だけ（検証用。最も重い結果を終了コードにする）
python -m slack.handler                       # 受信（**資格情報を持たない**）
python -m slack.expire                        # 承認期限の満了検知
```

終了コードを 2 つ足す。**値が大きいほど重い**という既存の規律を保つ。

| 終了コード | 意味 | 変更 |
| --- | --- | --- |
| 0 | `allow: true` → 実行まで到達し、成功した | **意味が変わる**（dry-run ログ → 実行成功） |
| 1 | 第1層の呼び出し失敗、または第2層の `ValidationError` | — |
| 2 | 環境変数の設定不足 | — |
| 3 | 第3層が `allow: false`（通知は成功） | — |
| 4 | 第3層が評価不能（通知は成功） | — |
| 5 | エスカレーションの送出に失敗した（遮断は成立している） | — |
| **6** | **実行を試みて確定的に失敗した**（4xx） | **Phase 5 で追加** |
| **7** | **実行の有無が不明**（5xx / 応答なし） | **Phase 5 で追加** |

**6 / 7 を 3 / 4 / 5 より重くする理由**: 3〜5 はいずれも「実行していない」ことが確定している状態である。
6 は実行していないが**世界を変えようとして失敗した**状態、7 は**世界が変わったかどうか分からない**状態であり、
人間が次に取る行動（クラスタを見に行く）が質的に違う。7 を最重とするのは、
**唯一「今の状態が分からない」状態だから**である。

**終了コード 0 の意味が変わることを明示しておく。** Phase 1〜4 の `--incident` 経路の 0 は
「dry-run ログまで到達した」だった。Phase 5 では「実クラスタで成功した」になる。
**過去の assets と終了コードを直接比較しない**（Phase 1 の「ファイル名を使い回さない」と同じ性質の注意）。

### 3.13 Phase 1〜4 の回帰

E2E フェーズの責務として、**層を重ねても過去の判定が崩れていないこと**を確認する。

- `pytest` 全件（Phase 2・3・4 の単体 145 件 + Phase 5 の追加分）

Phase 5 が見るのは「壊れていないこと」だけである。

## 4. 検証シナリオ

> シナリオ ID はフェーズごとに閉じている（Phase 3 の X 系、Phase 4 の E 系などと記号が重複するが別物）。

### 4.1 実行層の単体（K 系。pytest・クラスタ不要・決定的）

API クライアントをモックし、ディスパッチと結果分類を固める。**実機より先にここを固める**（Phase 2〜4 と同じ順序）。

| ID | 内容 | 期待 |
| --- | --- | --- |
| K-01 | 7 操作 × 対応する `kind` の全組み合わせ | ディスパッチ表の想定どおりの API が、想定どおりの引数で呼ばれる |
| K-02 | 表に無い組み合わせ（`kubectl_scale` × `pod` など） | **API を呼ばずに** `execution_failed` |
| K-03 | `dry_run: true` / `false` | 前者だけ `dry_run="All"` が渡る。参照系には渡らない |
| K-04 | 2xx / 403 / 404 / 409 / 422 / 429 / 500 / 503 を返すモック | 3.5 の表どおりに `executed` / `execution_failed` / `unknown` に分かれる |
| K-05 | タイムアウト・接続断・TLS エラー | **すべて `unknown`**（`execution_failed` に倒れない） |
| K-06 | 実行層に `environment` による分岐が無いこと | `agents/k8s.py` と `agents/execution.py` に `production` 等の語彙が出現しない（Phase 3 判定基準7 と同じ検査） |
| K-07 | `slack/handler.py` の import グラフ | `agents.execution` / `agents.k8s` / kubernetes クライアントに到達しない（[D-027](../../decisions.md)） |

### 4.2 ステートと再試行（W 系。pytest・クラスタ不要・決定的）

| ID | 内容 | 期待 |
| --- | --- | --- |
| W-01 | `approved` の占有（`claim`） | 2 つの executor が同時に拾っても実行は 1 回。CAS で 1 件だけが `executing` になる |
| W-02 | `executing` のまま残ったエントリの再起動時の扱い | **`unknown` に倒れる。`approved` に戻らない**（3.5） |
| W-03 | `execution_failed` → ［再試行］→ `approved` | `retry_count` が 1 増える。`event_json` は不変 |
| W-04 | 再試行の内容 | 復元 → **第2層で再検証** → 実行。ペイロードの値は使われない（[D-020](../../decisions.md)） |
| W-05 | `retry_count` が上限に達した状態 | 再試行ボタンが生成されない |
| W-06 | `unknown` のエントリ | **再試行ボタンが 1 つも生成されない**（判定基準4） |
| W-07 | `execution_failed` → ［中止］ | `abandoned`。`rejected` とは別の値 |
| W-08 | `executed_at` と `execution_started_at` | 成功時のみ `executed_at` が立つ。失敗・不明では `execution_started_at` だけ（Phase 4 考察11 の解消） |

### 4.3 実行の RBAC（R 系。kind クラスタが要る）

**第3層の判定と実行権限が独立であることを示す。**

| ID | 入力 | 第3層 | 実行 | 期待 |
| --- | --- | --- | --- | --- |
| R-01 | `production` / `kubectl_delete_pvc` / `prod/payment-data` | **deny** | 承認して実行 | **403 で止まる**。`execution_failed`・終了コード 6 相当・パターン5。PVC は**存在したまま** |
| R-02 | `production` / `kubectl_delete_pod` / `prod/payment-api-*` | **deny** | 承認して実行 | **403 で止まる**。Pod は残っている |
| R-03 | `development` / `kubectl_delete_pod` / `dev/payment-api-*` | **allow** | 自律経路 | **成功する**。Pod が消え、ReplicaSet が作り直す |
| R-04 | `development` / `kubectl_delete_pvc` / `dev/payment-data` | **deny** | 承認して実行 | **403**。「環境が緩くても PVC 削除は権限で止まる」 |

**R-01 が本フェーズの中心的なシナリオである。** 第3層が拒否し、人間がそれを上書きし、
それでも実行されない。`policy_override` が監査に残り、かつ**クラスタは変わっていない**。

### 4.4 E2E 通し（Z 系。全プロセスを起動）

| ID | 注入 | 経路 | 期待 |
| --- | --- | --- | --- |
| Z-01 | なし（正常系） | 第1層 → 第2層 → 第3層 allow → 実行 | **クラスタの状態が実際に変わる**（`kubectl` で裏取り）。終了コード 0。Slack には何も出ない |
| Z-02 | 第2層（散文の注入） | 第2層 ✗ | パターン2。ボタン無し。ストアにエントリ無し。**クラスタ無変化**。終了コード 1 |
| Z-03 | なし（本番 PVC 削除の指示） | 第3層 deny | パターン3 → 承認 → executor が実行 → R-01 の結果。`policy_override` が監査に残る |
| Z-04 | 第3層（OPA 停止） | 第3層 ✗ | パターン4。**ボタン無し**。クラスタ無変化。終了コード 4 |
| Z-05 | 第1層（両デプロイ障害） | 第1層 ✗ | **Slack に何も出ない**。終了コード 1。クラスタ無変化。**この欠落を記録する**（0 章） |
| Z-06 | TOCTOU | 承認待ちの間に対象 Pod を `kubectl delete` | 承認 → 実行 → **404** → `execution_failed`・パターン5。閾値内でも**クラスタが先に変わっていた**ことが実行の失敗として現れる |

**Z-01 の決定性**: 実 LLM が何を提案するかは確率的であり、判定基準に使わない（Phase 2 の規律）。
したがって Z-01 は 2 回実施する。(a) 実 LLM で経路が繋がること、(b) **content を fixture で固定**して
（3.11）同じ経路を決定的に流すこと。**判定に使うのは (b)**。

### 4.5 実行の異常系（X 系）

| ID | 内容 | 期待 | 判定基準に使うか |
| --- | --- | --- | --- |
| X-01 | `EXECUTION_TIMEOUT_SECONDS` を極小にして実行 | `unknown`。**かつクラスタ側では実際に変更が起きている**（「実行されたのに不明」） | **使う** |
| X-02 | proxy で 5xx を返す | `unknown`。`execution_failed` に倒れない | **使う** |
| X-03 | API サーバ停止中に実行 | `unknown`（接続断も不明側に倒す。3.5） | **使う** |
| X-04 | 実行中に executor を強制終了し、再起動する | `executing` が `unknown` に倒れる。**自動再実行されない** | **使う** |
| X-05 | `unknown` のエントリに対して人間が操作を試みる | 再試行ボタンが存在しない。通知に「クラスタを確認せよ」とある | **使う** |

### 4.6 限界・決定性・計測・比較

| ID | 分類 | 内容 | 期待 | 判定基準に使うか |
| --- | --- | --- | --- | --- |
| N-01 | 限界 | 承認待ちの間に対象 Pod を**同名で作り直す**（削除 → 再作成） | **実行が成功してしまう**（別の実体を消す）。時間ベースの TOCTOU 閾値では防げない | **使う**（限界の明示） |
| N-02 | 限界 | `environment` を詐称し、namespace も揃えた入力（Phase 3 N-01 の続き） | 第3層は通る。**RBAC が止める**（prod の delete pod）。詐称に対する最後の砦がクラスタ側にあることを示す | **使う** |
| N-03 | 限界 | executor を停止したまま承認する | ストアは `approved` のまま滞留する。**Slack 上は「承認済み」に見える** | **使う**（限界の明示） |
| D-01 | 決定性 | 同一アクションから組み立てた API 呼び出し（引数まで）を 10 回生成。パターン5 の Block Kit も同様 | SHA-256 が完全一致 | **使う** |
| L-01 | 計測 | 実行層のレイテンシを実測（n ≥ 20。操作別）し `EXECUTION_TIMEOUT_SECONDS` を決める | — | 使わない（計測） |
| C-01 | 比較 | ストアのポーリングを SQS 等のキューに置き換える構成 | — | 使わない（考察） |
| C-02 | 比較 | 同じ Rego を Admission Controller（Gatekeeper / Kyverno）としてクラスタ側に置く構成 | — | 使わない（考察） |
| C-03 | 比較 | 「思考の再開」（LangGraph の checkpointer 等）と「アクションの再開」（本 PoC）の違い | — | 使わない（考察。[D-001](../../decisions.md) の結論） |

**L-01 の位置づけ**: Phase 2 は「実測して決める」、Phase 3 は「実測した結果、変えなくてよい」、
Phase 4 は「外部 SaaS なので桁を仮定しない」を得てきた。Phase 5 の `timeout` は性格が違う。
**この値が `unknown` の発生率を直接決める。** 短すぎれば実行されたものを「不明」と記録し、
長すぎれば承認フローが詰まる。**timeout を誤ると、安全側の誤りが運用コストとして跳ね返る**唯一の層である。

**C-02 の位置づけ**: Phase 3 の N-01（詐称は検知できない）と Phase 5 の N-02 は同じ問題の表裏である。
エージェントの自己申告に依存しない防御は、**判定をクラスタ側に移す**しかない。
同じ Rego がそのまま使える構成は、本 PoC の主張（ポリシーを外部化したことの効用）の
もっとも強い裏付けになる。実装はせず、構造比較として記録する。

### 4.7 実施順序

K 系（実行層の単体）→ W 系（ステート・再試行）→ クラスタ構築 → R 系（RBAC）
→ Z 系（E2E 通し）→ X 系（実行の異常）→ N 系（限界）→ D-01 → L-01 → C 系 → 回帰（3.13）。

**単体を先に固める。** E2E から始めると、失敗の原因が LLM なのか、ポリシーなのか、
RBAC なのか、ディスパッチ表なのか、kind の設定なのかを切り分けられなくなる。
これは Phase 2・3・4 で一貫して効いている順序であり、**層が 5 つに増えた Phase 5 でもっとも効く**。

## 5. 判定基準

以下を**すべて**満たしたとき Phase 5 合格とする。

1. **K 系・W 系が pytest で全件パスする。** 実行層のディスパッチと結果分類、ステート遷移と再試行が、
   **クラスタ無しで**決定的に検証できること。
2. **Z-01 で、インシデント記述からクラスタの状態変化までが 1 本で繋がる。**
   到達の証拠は構造化ログではなく、**`kubectl` で観測できるクラスタ側の変化**であること。
3. **Z-02 / Z-04 で止まったとき、クラスタが 1 ミリも変わっていない。**
   通知パターンが正しいだけでは不十分で、**実行層に到達していないことをクラスタ側から確認する**。
4. **実行結果が 3 分類に正しく落ちる。** 2xx → `executed` / 4xx → `execution_failed` /
   5xx・タイムアウト・接続断 → `unknown`。そして **`unknown` に再試行ボタンが 1 つも出ない**（W-06 / X-05）。
   `execution_failed` と `unknown` が別の値として記録されていること。
5. **R-01 で、第3層が deny し人間が `policy_override` で承認したアクションが、RBAC によって実行されない。**
   `policy_override` が監査に残り、かつ**対象の PVC が存在したまま**であること。
6. **Slack の受信プロセスが実行権限を持たない。** `slack/handler.py` を**クラスタの資格情報が無い環境で**
   起動した状態で承認が成立し、executor が実行する。K-07（import グラフ）も満たすこと。
7. **X-04 で、実行中に落ちた executor を再起動しても自動再実行されない。**
   `executing` が `unknown` に倒れ、`approved` に戻らないこと。
8. **再開が LLM を呼び直さずに成立する。** 承認から実行までの間に第1層へのリクエストが
   **1 本も出ていない**ことを、LiteLLM 側のログで確認できること。
9. **再試行が同一のアクションで行われる。** `retry_count` が増え、`event_json` が不変で、
   復元時に第2層の再検証を通っていること（W-03 / W-04）。上限で止まること（W-05）。
10. **D-01 で、同一アクションから組み立てた API 呼び出し（引数まで）と、パターン5 の Block Kit が完全に一致する。**
11. **N 系で「防げないこと」が記録されている。** N-01（同名で作り直された対象を消してしまう）、
    N-02（詐称は RBAC でしか止まらない）、N-03（executor 停止中の承認は滞留する）。
    **成功してしまった記録・滞留した記録を残すことをもって満たす**（Phase 4 の N 系と同じ扱い）。
12. **Phase 1〜4 の判定基準が引き続き満たされる**（3.13）。pytest 全件・`opa test` 全件・代表シナリオ 4 本。

**判定基準に使わないもの**: L-01（計測）、C-01〜C-03（構造比較）、
**実 LLM がどの操作を提案するか**（非決定的。Z-01 は fixture 固定版で判定する）、通知の見た目。

## 6. 観測方法（エビデンスの取り方）

| 手段 | 内容 | 用途 |
| --- | --- | --- |
| `pytest -v` の出力 | K 系 / W 系の結果一覧 | 判定基準1・4・9 |
| **`kubectl get/describe` の出力（実行の前後）** | Deployment の `generation` と `restartedAt`、Pod の UID、PVC の存在 | **判定基準2・3・5 の主エビデンス**。層の外側からの裏取り |
| **kind の API サーバ監査ログ** | どのリクエストがどの ServiceAccount で来て、どう判定されたか | 判定基準5・6。403 が RBAC によるものである裏取り |
| エージェント / executor の構造化ログ `event=execution.applied` / `execution.failed` / `execution.unknown` | 操作・対象・HTTP ステータス・所要時間 | 判定基準4 |
| ストアの `SELECT` | `status` 遷移、`execution_started_at` / `executed_at` / `retry_count`、`audit_log` 全行 | 判定基準4・7・9 |
| LiteLLM のアクセスログ | **承認から実行までの区間にリクエストが無いこと** | 判定基準8 |
| handler プロセスの環境 | `env` に kubeconfig が無いこと、import グラフの検査結果 | 判定基準6 |
| Slack の `conversations.history` | パターン5 の blocks、再試行ボタンの有無 | 判定基準4 |
| プロセスの終了コード | `echo $?` | 3.12 |
| injector / proxy のアクセスログ | 注入が経路を通ったこと | X 系の前提（[D-018](../../decisions.md)） |

### 「変わっていないこと」の証拠を先に決める

Phase 3 は「届いたこと」、Phase 4 は「送れた／受けた」の証拠を先に決めた。
**Phase 5 で必要なのは『変わっていないこと』の証拠である。** これは性質が違う。

| 主張 | 弱い証拠 | **採用する証拠** |
| --- | --- | --- |
| 実行していない | 実行層のログが無い | **シナリオの前後で `kubectl get -o yaml` を取り、`resourceVersion` と `generation` が一致すること** |
| 実行された | 例外が出なかった | **対象リソースの観測可能な変化**（Pod の UID が変わった / PVC が消えた / `restartedAt` が更新された） |
| 権限で止まった | 403 が返った | **API サーバの監査ログに `forbidden` の判定があること** + 対象が無変化であること |
| 実行有無が不明 | 例外が出た | **例外の種別が応答なし／5xx であること** + クラスタ側の実際の状態（X-01 では**変わっている**） |

**「ログに出ていない」は「起きていない」の証拠にならない。** Phase 4 の N-02（受信の失敗はどこにも残らない）で
同じ構造を踏んでいる。実行層では**観測対象がクラスタ側にある**ため、今回は外側から取れる。

生データは `assets/` に置き、result.md から参照する。**ファイル名は使い回さない。**
`assets/` に貼る前に、**kubeconfig の埋め込みトークン・ServiceAccount トークン・クラスタの CA 証明書**を除去する
（docs/README.md 運用ルール2）。`kubectl config view` は既定でトークンを伏せない。

## 7. 未決事項・確認事項

着手時に確認し、判明した内容は result.md に記録する。設計判断が変わる場合は decisions.md を更新する。

1. **kind のバージョンとノードイメージの固定値。** ホストに kind が入っていない（`kubectl` のみ）。
   導入方法とバージョン固定の方針を決める（OPA を `1.21.0` に固定したのと同じ規律）。
2. **ServiceAccount のトークンの作り方と寿命。** k8s 1.24 以降、Secret 経由の永続トークンは自動生成されない。
   `kubectl create token`（短命）か、`type: kubernetes.io/service-account-token` の Secret を明示的に作るか。
   **検証中に失効すると、RBAC 403 と区別がつかない失敗が出る**（Phase 1 の SSO 失効と同じ罠）。
3. **`kubectl_describe` を API で何に対応づけるか**（3.2）。read + Event の取得で足りるか。
4. **server-side dry-run が `delete` に効くか。** 効かない場合、`dry_run: true` の削除をどう扱うか
   （実行しないのか、エラーにするのか）を決める。**黙って実行しないのは最悪**である。
5. **Python クライアントのタイムアウト指定方法**（`_request_timeout`）と、
   タイムアウト時にリクエストが送信済みかどうかをクライアント側で判別できるか。
   **判別できないことが分かれば、それ自体が [D-028](../../decisions.md) の裏付けになる。**
6. **`mocks/k8s_proxy.py` を標準ライブラリだけで書けるか**（HTTPS 終端と上流への転送）。
   書けない場合、X-02（5xx）の注入方法を変える。X-01 / X-03 は proxy 無しで実施できる。
7. **executor のポーリング間隔と、人間が感じる遅延。** 承認してから実行結果の通知が出るまでの体感。
   短くするとストアへのアクセスが増える。実測して決める。
8. **kind の API サーバ監査ログを有効にする方法**（`kind-cluster.yaml` の `kubeadmConfigPatches`）。
   有効にできない場合、403 が RBAC によるものである裏取りを何で取るか。
9. **パターン5 の投稿先。** 承認経路では元メッセージのスレッドか新規投稿か。
   自律経路（元メッセージが無い）では必ず新規投稿になるため、**経路によって形が変わる**。
10. **ストアの不変条件の緩み**（3.7）。`unknown` はボタンが無いのにエントリを持つ。
    「エントリがある ⇔ ボタンがある」を諦めて「エントリがある ⇔ 終端していない or 人間の確認待ち」に
    言い換えるべきかを、実装後に結論づける。
11. **`retry_count` の上限に達したエントリの終端。** `abandoned` に自動遷移させるか、
    人間が押すまで `execution_failed` のまま置くか。**自動で閉じると「誰も見ていない失敗」が増える。**
12. **`agents/main.py`（自律経路）に kubeconfig を与えることの是非**（2.2）。
    与えないなら自律経路も executor 経由になり、終了コード 0 の意味が「キューに積んだ」に変わる。
    **Phase 1〜4 のエビデンスとの比較可能性を優先して「与える」としたが、実装後に再評価する。**
13. **複数の executor を同時に起動した場合**（W-01 は単体で確認する）。
    SQLite の `BEGIN IMMEDIATE` で足りるか、実機で 2 プロセス起動して確認する。
14. **Deployment の `generation` と Pod の UID のどちらを「変化」の指標にするか。**
    `rollout_restart` は `generation` が増え、`delete_pod` は UID が変わる。操作ごとに指標が違うため、
    **シナリオごとに「何を見れば変化したと言えるか」を先に表にしておく**（6 章の方針）。
