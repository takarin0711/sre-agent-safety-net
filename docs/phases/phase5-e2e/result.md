## 考察

### 1. 「実行されたのに不明」は作り話ではなかった（X-01b）

[D-028](../../decisions.md) は「5xx と無応答を `unknown` に倒す」ことを、**二重実行のコストが
確認のコストより重い**という非対称性から決めた。設計時点ではこれは論理的な主張であって、
実例ではなかった。

X-01b で実例が出た。プロキシが上流へ要求を転送し、API サーバが **200 を返し、
Deployment の `generation` が 2 から 3 に変わった**うえで、応答だけがクライアントに届かなかった。
記録は `unknown`、終了コードは 7。

**ここで「5xx や無応答は失敗だから再試行可」としていたら、本番の Deployment を 2 回再起動していた。**
HTTP の慣習（5xx は再試行可）は冪等な読み出しを前提にしており、
非冪等な破壊的操作にそのまま持ち込むと事故になる。

### 2. もっとも重要な注入が、設計どおりには効かなかった

design.md 3.11 は X-01（`EXECUTION_TIMEOUT_SECONDS` を極小にする）を
「本フェーズでもっとも重要な注入」と書いた。追加の部品が要らず証拠能力が高いという理由だった。

実際にやると、**タイムアウトは「実行されたのに unknown」を作れなかった**。
kind は localhost にあり、L-01 の実測で p50 1.2 ms / max 20.9 ms である。
これより短いタイムアウトは**リクエストが API サーバに届く前に**切れるため、
`unknown` にはなるがクラスタは変化しない。0.01 / 0.005 / 0.002 秒のいずれでも同じだった。

**「送った後に切る」ことが要るのであって、「早く諦める」ことではなかった。**
そのため `mocks/k8s_proxy.py` に `drop_response`（上流へ転送してから応答を握り潰す）モードを置き、
X-01b として実施した。design.md は書き換えていない。

この差は距離の問題である。実クラスタがネットワークの向こうにあれば、
タイムアウトが「送信後」に落ちる確率はずっと高い。
**ローカルで検証すると、再現しにくくなる障害がある。**

### 3. 多層防御の最後の 1 枚は、ポリシーの外にあった（N-02）

R-01 は「第3層が deny したものを人間が承認しても RBAC が止める」ことを示した。
これは設計どおりである。より効いたのは N-02 のほうだった。

`opa/data.json` の 1 行（`development` の namespace 一覧に `prod` を足す）だけで、
第3層は**本番 Pod の削除に `allow: true` を返した**。`environment` を `development` と
申告しているので `PROHIBIT_PRODUCTION_DESTRUCTIVE` は発火せず、
namespace の対応チェックも通ってしまう。人間の承認すら挟まらず、自律経路でそのまま実行に向かった。

止めたのは RBAC だけである。

Phase 3 の N-01 は「第3層は input の真正性を検証できない」という限界を示した。
Phase 5 の N-02 はその一段先にある。**ポリシーが正しく書かれていても、
ポリシーが参照するデータが間違っていれば同じことが起きる。**
そして第3層は自分のデータが間違っていることを検知できない。

M-01（Phase 3）で「ポリシーをアプリと独立に変更できる」ことを利点として示したが、
**独立に変更できるということは、独立に壊せるということでもある。**

### 4. 受信と実行を分けたら、新しい状態が 1 つ必要になった

[D-027](../../decisions.md) で handler から実行を外したとき、分離の目的は権限だった。
実装してみると、**`executing` という状態を持たざるを得ない**ことが分かった。

同一プロセスなら「実行したが結果を記録する前に落ちた」は追跡できない。
プロセスを分けてストアを挟むと、その窓が可視になる。X-04 で実際に `SIGKILL` したところ、
エントリは `executing` のまま残った。これを `approved` に戻せば再実行され、
戻さなければ永久に止まる。**どちらも間違いで、正解は「不明と記録して人間に渡す」だった。**

分離は権限のために選んだが、**付いてきたのは「落ちたことを観測できる」という性質**だった。

### 5. Phase 4 のテストを書き換える必要が出たが、性質は変えずに済んだ

承認と実行が別プロセスになったため、Phase 4 の T-05 / T-06 / T-07 / G-01 / G-05 / G-06 が落ちた。
いずれも `handler.approve()` の戻り値が `executed` であることを前提にしていたためである。

確かめたい性質（押した内容と実行内容の一致・壊れたレコードが実行層に到達しないこと・
再送でも実行は 1 回）は**プロセスの分け方に依らない**ので、
テストを「承認 → `executor.run_once()`」の通しに変えて同じ主張を維持した。

結果として**判定はむしろ厳しくなった**。Phase 4 は「実行層のログが出ていない」ことで
非実行を示していたが、Phase 5 は **`FakeApis` の呼び出し履歴が空であること**で示す。
ログは出し忘れうるが、呼び出し履歴は偽れない。

### 6. `dry_run` が 4 フェーズぶん遅れて意味を持った

`ProposedAction.dry_run` は Phase 2 から存在し、第3層には `REQUIRE_DRY_RUN_IN_PRODUCTION` がある。
しかし実行層がログ出力だけだった Phase 1〜4 のあいだ、**この値は一度も意味を持っていなかった**。

Phase 5 で server-side dry-run に対応づけたところ、
`dryRun=All` は **200 を返し、監査ログにも残り、しかしリソースは変化しない**ことを実測できた。
クライアント側で「送らない」実装にしていたら、認可も admission も通らず、
`dry_run: true` の通知を人間が見て安心する根拠が無かった。

**「スキーマにあるが到達しないフィールド」は、到達した瞬間に意味が決まる。**
Phase 4 のステート語彙（`execution_failed` / `unknown`）を到達前に決め切ったのと同じ構造の問題で、
あのときは語彙を先に決めたから意味が揺れなかった。

### 7. 自動修正ツールが、変更禁止のファイルを書き換えた

`ruff --fix` が `mocks/fault_injector.py` の `# noqa: N802` を 2 箇所削除していた。
design.md が「改修しない」と明示したファイルである（Phase 1〜4 の再現性を保つため）。
`git status` で気づいて revert した。

**規律をドキュメントに書いても、ツールはそれを読まない。**
`--fix` の対象をディレクトリ単位で渡したことが原因で、
変更してはいけないファイルを機械的な処理の範囲に入れないという運用が要る。

### 8. エビデンス生成スクリプトが、静かに全件 `no` を返した

`kubectl auth can-i` の結果を表にする処理が、全 32 行を `no` で出力した。
zsh が未クォートの変数展開を単語分割しないため、`kubectl auth can-i "get pods" ""` という
呼び出しになっていた。**「権限が一切付いていない」という誤った証拠を `assets/` に保存する寸前だった。**

Phase 2 の教訓（「障害注入が効いていないと静かに正常系になる。全部合格しているときほど疑う」）の変奏である。
今回は逆向きで、**全部が同じ値のときほど疑う**ほうが正しい。
判定の向きに関わらず、**揃いすぎた結果は検証の失敗を示唆する**。

### 9. C-01: ストアのポーリングをキューに置き換える条件

本 PoC の executor は SQLite を 2 秒間隔でポーリングする。
`approved` の CAS が排他を担っているので、**ワーカーを増やしても二重実行は起きない**（W-01）。

キュー製品に置き換える必要が出るのは次の 3 つのいずれかが成立したときである。

1. **ワーカーが別ホストに分かれる。** SQLite のロックはファイルシステムに閉じている。
2. **実行待ちの件数がポーリング間隔に対して多い。** 1 周で拾う件数（既定 20）に収まらなくなる。
3. **実行が長時間かかる。** `executing` の窓が広がり、クラッシュ時の `unknown` が増える。

逆に言えば、**この 3 つが成立しないうちはキューを置く理由が無い**。
Phase 4 で [D-024](../../decisions.md) がキューを置かなかったのと同じ判断であり、
今回はその前提が崩れる条件を数えられるようになった。

### 10. C-02: 同じ Rego をクラスタ側に置く構成

N-02 が示したのは「ポリシーがエージェントの自己申告を評価している」という構造的な限界である。
これを塞ぐ方法は 1 つしかない。**判定をクラスタ側に移すことである。**

Gatekeeper / Kyverno は Admission Controller として、**実際の API 要求**に対して判定する。
`environment` の申告ではなく、要求が到達した namespace そのものを見る。
本 PoC の `opa/policy.rego` は `input.action` の形に依存しているので
そのままは動かないが、**ルールの構造（違反が無いことで allow を決める・理由を同時に返す）は
そのまま移せる**。

本 PoC の第3層と Admission Controller は競合しない。役割が違う。

| | 本 PoC の第3層 | Admission Controller |
| --- | --- | --- |
| 判定の材料 | エージェントの**申告** | 実際の API 要求 |
| 判定の時点 | 実行**前**（提案の段階） | 実行の瞬間 |
| 拒否したときに返せるもの | 理由・承認ボタン・思考ログ | API エラーのみ |
| 人間への引き渡し | できる | できない |

**前者は「人間に渡すために拒否する」、後者は「とにかく通さない」。**
多層防御としては両方要る。

### 11. C-03: 「思考の再開」と「アクションの再開」（[D-001](../../decisions.md) の結論）

[D-029](../../decisions.md) で「再開は承認済みアクションの実行から行う」と決めた。
実装してみて必要だったのは、ストアの `status` 列 1 つと、そこに `executing` を足すことだけだった。
会話履歴も、チェックポイントも、状態機械のシリアライズも要らなかった。

[D-001](../../decisions.md) は「Phase 5 の中断・再開は自前で状態を持つ必要がある」と
フレームワーク不採用の**代償**として書いていた。結論としては代償ではなかった。

**フレームワークの checkpointer が解くのは「非決定的な計算の途中状態の復元」であり、
本 PoC が必要としていたのは「確定した 1 件の実行をどこまで進めたかの記録」である。**
前者を導入していたら、承認フローに「承認後に再計画させる」という選択肢が存在してしまった。
それは運用原則2（承認内容の同一性保証）を、ボタンの `value` を絞ってまで守ってきた努力と正面から衝突する。

**選ばなかったことが設計を守った**数少ない例である。

## 実運用への提言

1. **承認の同一性を名前ではなく UID で保証する。** N-01 のとおり、同名で作り直された対象は
   時間ベースの TOCTOU 閾値を通過する。提案時に対象の `uid` と `resourceVersion` を
   ストアへ記録し、実行直前に照合して食い違えば `stale` に倒す。
   これは Phase 4 の提言3（Block Kit のダイジェストを別系統で保存する）と同じ形の対策である。
2. **ポリシーが参照するデータを、ポリシー本体と同じ厳しさで扱う。** N-02 は `opa/data.json` の
   1 行で本番の破壊的操作が許可された。データにも
   レビュー・テスト（`opa test` にデータの不変条件を書く）・署名付き bundle 配布が要る。
   **「ポリシーをアプリと独立に変更できる」は「独立に壊せる」と同義である。**
3. **Admission Controller と併用する。** 本 PoC の第3層は人間に渡すための拒否、
   Admission Controller は通さないための拒否（考察10）。
   エージェントの自己申告に依存しない防御は後者にしか置けない。
4. **`unknown` の運用手順を先に決める。** 本 PoC は「人間がクラスタを確認する」としか言っていない。
   実運用では **誰が・何分以内に・何を見るか**を決めておかないと、
   `unknown` は「誰も触らないチケット」になる。確認の結果を
   `executed` / `execution_failed` に確定させる操作（人間が押すボタン）も要る。
5. **`EXECUTION_TIMEOUT_SECONDS` は実クラスタで測り直す。** L-01 の値（max 20.9 ms）は
   localhost の kind のものであり、実運用のネットワーク越しでは桁が変わる。
   **短すぎる値は `unknown` を量産し、`unknown` は人間の確認作業になる。**
   タイムアウトは可用性の設定ではなく、**運用コストの設定**である。
6. **承認待ちと実行待ちの両方を監視する。** N-03 のとおり executor が止まっていると
   `approved` のまま滞留し、Slack 上は「承認済み・実行待ち」に見える。
   Phase 4 の N-02（受信の死活監視）と合わせて、**ストアの各状態に滞留時間の上限**を置く。
7. **実行の監査を外部へ送る。** `audit_log` はすべての実行（自律・承認・再試行）を記録しているが、
   ストアと同じ SQLite ファイルにある。Phase 4 の提言7 と同じく、
   `policy_override` と実行記録だけは追記専用の別ストレージへ移送する。
8. **操作ごとの冪等性をポリシーとして持たせる。** 本 PoC は「`unknown` は一律再試行しない」とした
   （[D-028](../../decisions.md)）。実運用で自動再試行を入れるなら、
   その可否は通知層や実行層の `if` ではなく **Rego 側の属性**として持たせる。
   そうすれば `opa test` で冪等性の宣言そのものをテストできる。
9. **承認画面の可読性を、実行層側の描画関数で取り戻す。** 本 PoC は提案アクションを
   汎用の整形（`operation  kind/name @ namespace (env)  dry_run=`）で表示している。
   `kubectl` 風のコマンド文字列にしない理由は 3 つあり、どれも今も有効である——
   (a) 操作ごとのテンプレートが通知層に入り [D-021](../../decisions.md) に抵触する、
   (b) 発行しないコマンドを人間に見せることになる、
   (c) [D-030](../../decisions.md) で実行層は API クライアントになったため、
   **`kubectl` の行はどこにも存在せず、表示すれば実行の近似ですらない創作になる。**

   しかしこの選択は**可読性を捨てている**。深夜に起こされた承認者にとって
   `kubectl rollout restart deploy/payment-api -n prod` のほうが速く読めるのは、ほぼ確実である。
   design.md 1. は「通知の見た目は判定基準に使わない」としたが、
   **承認 UI の可読性は安全性の一部**であり、本来そこで切り離すべきではなかった（本フェーズの反省）。

   取り戻すなら、**実行層に「このアクションを人間向けに描画する」関数を 1 つ置き、
   通知層はそれを呼ぶだけにする。** 実際に API 呼び出しを組み立てている場所が描画も持つので、
   表示と実行が構造的にずれない。通知層には分岐が入らないので (a) も守れる。
   **やってはいけないのは、通知層に `kubectl` 風テンプレートを置くこと**で、
   分岐が漏れたうえ、実行と乖離しても誰も気づけない。
